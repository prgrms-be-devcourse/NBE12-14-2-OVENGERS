# 인증·인가 고도화 단계별 계획

> 상태: 함께 구체화할 초안 · 일정·담당자·정책 수치 미확정  
> 관련 문서: [도입 범위](01-redis-adoption-scope.md) / [Redis 인증 설계](02-redis-auth-design.md)

## 1. 목표와 범위

기존 Kotlin 마이그레이션에서 동작을 보존한 뒤, 다음을 단계적으로 개선한다.

- 로그아웃·계정 상태 변경 후 기존 인증의 차단
- Refresh Token 회전과 재사용 탐지
- 기존 객체 수준 인가의 누락 점검 및 테스트 강화
- 로그인·재발급 API 요청 제한
- OAuth2/OIDC 기반 플랫폼 로그인과 계정 연결
- 위 기능을 지원하는 회원·인증 데이터 모델, 쿠키 보호, 장애 복구

Redis 전면 도입, 예약·결제 저장소 변경, 모든 API 캐시, 인증 방식의 세션/BFF 전면 전환은 이번 기본 범위에서 제외한다. 성능 개선은 별도 측정 과제로 관리한다.

## 2. 우선순위와 작업 순서

| 단계 | 작업 | 완료 산출물 | 우선순위 |
| --- | --- | --- | --- |
| 0 | Kotlin 기준선·현재 인증 및 인가 조사 | 흐름도, API 권한표, 회귀 테스트, 기준 지표 | 필수 |
| 1 | 인증 정책·모델·토큰 전달 방식 설계 | 정책 결정표, ERD·API 변경안 | 필수 |
| 2 | 기존 객체 수준 인가와 쿠키·CSRF 점검 | 누락 보완, 권한·브라우저 보안 테스트 | 필수 |
| 3 | Redis 기반 Access 폐기·계정 차단 | 로그아웃·정지·복구 테스트 | 필수 |
| 4 | 로그인 세션과 Refresh Rotation | 회전·재사용·동시성·응답 유실 테스트 | 필수 |
| 5 | 인증 API 요청 제한 | 한도·429·복구·부하 결과 | 필수 |
| 6 | 플랫폼 1개 로그인·계정 연결 | 신규/기존 계정 통합 로그인 | 기능 확장 |
| 7 | 장애·배포 전환·통합 검증 | 운영 절차, 측정표, 팀 발표 자료 | 필수 |

순서는 의존관계를 기준으로 한 초안이다. 모델과 정책은 먼저 설계하되 실제 스키마 변경은 필요한 단계에서 작게 적용한다. 기능 범위가 커지면 플랫폼 수를 늘리기보다 한 플랫폼의 가입·연결·탈퇴를 완성한다.

## 3. 단계 0: 현황과 기준선

- [ ] 최신 Kotlin 브랜치와 분석한 Java ZIP의 차이를 확인한다.
- [ ] 로그인·재발급·로그아웃·탈퇴·관리자 정지 흐름을 그린다.
- [ ] 토큰 전달 위치, 유효기간, 쿠키 설정, CORS와 프론트 재발급 방식을 확인한다.
- [ ] API별 비회원 / 본인 USER / 다른 USER / ADMIN 권한표를 작성한다.
- [ ] 기존 성공·실패 시나리오와 응답 코드를 회귀 테스트로 남긴다.
- [ ] 인증 및 대표 보호 API의 지연·오류율·SQL 수를 기준선으로 측정한다.

완료 기준: 무엇이 이미 있고 무엇을 바꾸는지 코드와 테스트로 구분할 수 있다. 성능 목표값은 기준선과 예상 사용량을 본 뒤 정한다.

## 4. 단계 1: 회원·인증 모델 설계

### 현재 Member에서 확인한 필드

`id`, `email`, `passwordHash`, `nickname`, `role`, `status`, `balance`, `withdrawnAt`과 상속 시간 필드가 있다. `email`은 UNIQUE·NOT NULL, `passwordHash`도 NOT NULL이다. “닉네임과 이름만 저장한다”는 전제는 사용하지 않는다.

### 추가·분리 후보

| 모델 / 필드 | 목적 | 제안 |
| --- | --- | --- |
| `Member.authVersion` | 회원 전체의 기존 인증 무효화 | 영속 원본 후보, 정지·권한 변경과 연계 |
| `emailVerifiedAt` 또는 검증 상태 | 이메일 신뢰 여부 표현 | 검증 흐름과 함께 추가. 임의로 기존 회원 전체를 검증 완료 처리하지 않음 |
| `passwordChangedAt` | 자격 증명 변경 감사·재인증 정책 | 비밀번호 변경 기능 범위와 함께 결정 |
| `lastLoginAt` | 최근 로그인 정보 | 선택. 요청마다 갱신하지 않음 |
| `OAuthAccount` | 여러 외부 계정과 내부 회원 연결 | `memberId`, `provider`, `providerUserId`, `linkedAt` 등 |
| 로그인 세션 기록 | 기기·로그인별 Refresh 계열 및 폐기 | `sid`, `memberId`, 생성·만료·폐기 상태 등. Redis 보관 후보 |
| 보안 감사 이벤트 | 정지·연결·재사용 탐지 등의 추적 | 기존 감사 구조 재사용 가능성 확인 |

`OAuthAccount(provider, providerUserId)`에는 복합 UNIQUE를 둔다. OIDC 식별자를 사용하면 발급자(issuer)와 subject의 조합을 제공자 식별 규칙에 반영한다. 이메일을 외부 계정의 유일한 식별자로 삼지 않는다.

소셜 전용 계정에 비밀번호가 없다면 현재 NOT NULL 제약과 로그인·탈퇴 로직을 바꿔야 한다. 후보는 로컬 자격 증명을 별도 모델로 분리하거나 `passwordHash`의 부재를 명시적으로 허용하는 방식이다. 임의 비밀번호를 넣어서 기존 제약을 우회하지 않는다.

외부 제공자가 이메일을 주지 않는 경우 추가 입력을 요구할지, 내부 이메일 필수 정책을 변경할지 결정한다. 사용 목적 없는 생년월일·전화번호 등은 수집하지 않는다. 외부 API를 계속 호출할 요구가 없으면 제공자 토큰을 장기 저장하지 않는다.

완료 기준: 기존 memberId 및 예약 연결을 보존하는 마이그레이션, 기존 일반 가입과 소셜 전용 계정의 로그인·탈퇴 정책을 함께 설명할 수 있다.

## 5. 단계 2: 객체 수준 인가 및 브라우저 보안

### 객체 수준 인가(Object-level Authorization)

“객체 기반 인증”보다 정확한 이름은 **객체 수준 인가**다. 로그인 여부·USER 역할만 확인하는 것과 특정 예약이 그 사용자의 것인지 확인하는 것은 다르다.

업로드된 코드에서는 다음 경로에 이미 소유권 검사가 있다.

- `ReservationQueryService.getMyReservation()`
- `ReservationCancelService.cancel()`
- `ReservationPaymentConfirmService.confirm()`
- `ReservationExtendService.extend()`

이를 신규 취약점 발견으로 과장하지 않는다. 출입 토큰 발급·폐기, 예약 이력, 목록, 기타 ID를 받는 API에도 같은 정책이 일관되게 적용되는지 조사한다.

- [ ] memberId는 요청 본문이 아닌 검증된 Principal에서 가져온다.
- [ ] 본인 여부를 조회 조건 또는 명시적 비교로 확인한다.
- [ ] ADMIN은 별도 경로와 허용 범위를 명시한다. 무조건 모든 검사 우회로 구현하지 않는다.
- [ ] 타인 예약 요청 거절 시 잔액·상태·슬롯·출입 토큰도 변경되지 않는지 검증한다.
- [ ] 목록·이력에 타인 데이터가 섞이지 않는지 확인한다.
- [ ] 403/404 선택과 존재 여부 노출 정책을 일관되게 적용한다.

### 쿠키·CSRF·CORS

현재 Refresh Token은 브라우저가 자동 전송하는 쿠키다. JWT를 사용한다는 이유만으로 모든 경로의 CSRF 위험이 사라지는 것은 아니다.

- 운영 HTTPS와 Refresh 쿠키의 Secure·HttpOnly·SameSite·Path를 확인한다.
- 프론트·API의 실제 배포 도메인에 맞춰 CORS 허용 origin과 credentials를 제한한다.
- refresh·logout 등 쿠키 기반 변경 요청에 CSRF 토큰 또는 적절한 Origin 검증 등의 방어를 설계하고 공격 출처 테스트를 수행한다. SameSite만으로 충분하다고 단정하지 않는다.
- 쿠키 삭제 시 발급 때의 Path·Domain 등 범위가 맞는지 확인한다.
- Access Token의 프론트 보관 위치와 XSS 노출을 점검한다. 브라우저 영속 저장소에 토큰을 장기 보관하는 방식을 기본값으로 삼지 않는다.

완료 기준: 정상 프론트 요청은 성공하고, 허용하지 않은 출처·타인 리소스 요청은 차단된다.

## 6. 단계 3: Access 폐기·계정 차단

- [ ] jti 발급 및 폐기 조회를 추가한다.
- [ ] 로그아웃 API가 폐기할 Access Token과 Refresh 관계를 검증하게 변경한다.
- [ ] 첫 단계가 “해당 토큰 하나”의 차단인지 “로그인 세션 전체”인지 API 계약에 명시한다.
- [ ] 정지·탈퇴·전체 로그아웃·역할 변경 시 기존 인증 버전 무효화 정책을 적용한다.
- [ ] 정지 해제 후 옛 토큰이 살아나지 않음을 검증한다.
- [ ] Redis 장애와 DB 동기화 실패의 완료·재시도·복구 기준을 구현한다.

완료 기준: 차단 반영 이후 토큰 재사용 거절, 부분 실패를 성공으로 보고하지 않음, 장애 시 인증 우회 없음. 상세 키·유실 정책은 [설계 문서](02-redis-auth-design.md)를 따른다.

## 7. 단계 4: Refresh 회전과 로그인 세션

- [ ] 현재 기기 로그아웃이 필요하면 sid 모델과 Access 연계를 구현한다.
- [ ] 새 Refresh 발급·기존 토큰 소모를 원자적으로 처리한다.
- [ ] 사용한 토큰 재사용을 식별할 제한된 이력을 둔다.
- [ ] 재사용 시 폐기 범위와 기존 Access Token 차단 여부를 명시한다.
- [ ] 프론트에서 중복 refresh를 합치고 다중 탭 경합을 검증한다.
- [ ] 응답 유실·네트워크 재시도·동시 로그아웃·계정 정지 경합을 검증한다.
- [ ] Redis 전환 시 기존 Refresh를 만료할지, 단계 이전할지 결정한다.

완료 기준: 같은 Refresh의 교체는 의도한 횟수만 성공하고 이전 토큰은 다시 유효해지지 않는다. 실패 정책에 따라 재로그인 안내가 일관된다.

## 8. 단계 5: 인증 API 요청 제한

- [ ] 로그인·재발급부터 적용한다. 회원가입·이메일 발송 제한은 해당 기능 도입 시 확장한다.
- [ ] IP·계정·경로별 기준, 시간 창, 허용 횟수를 합의한다.
- [ ] Redis Lua 등으로 확인·기록을 원자화한다.
- [ ] 429와 Retry-After, 정상 복구, 동시 요청 한도를 테스트한다.
- [ ] 공유망 오차단, 프록시 IP 위조, 무작위 키 증가를 검증한다.
- [ ] Redis 장애 시 정책과 추가 지연·메모리를 측정한다.

완료 기준: 동시 요청에도 정책 한도를 지키며 제한 해제 시 정상 사용이 가능하다. 이 기능은 업무의 결제 멱등성 검사를 대체하지 않는다.

## 9. 단계 6: OAuth2/OIDC 플랫폼 로그인

플랫폼은 우선 하나만 선택한다. OAuth2는 권한 위임 프로토콜이고 OIDC는 그 위의 신원 확인 계층이다. OIDC 지원 제공자는 검증된 ID Token을, 그 외 제공자는 공식 사용자 정보 API와 로그인 정책을 이용한다.

### 흐름

1. 로그인 요청을 시작하고 state 및 필요한 PKCE·nonce 등의 흐름 상태를 보관한다.
2. 콜백에서 요청과 응답의 연결을 검증한다.
3. 제공자별 공식 방식으로 외부 사용자를 검증한다.
4. `(provider, providerUserId)`로 연결된 내부 회원을 찾는다.
5. 신규 가입·기존 계정 연결 정책에 따라 처리한다.
6. 내부 회원 상태를 확인한 뒤 SlotKey의 공통 Access·Refresh 정책으로 로그인한다.

### 구현·검증 항목

- [ ] Spring Security OAuth2 Client 지원을 활용하고 직접 프로토콜 구현을 최소화한다.
- [ ] redirect URI를 제한하고 state, 적용되는 PKCE, OIDC issuer·audience·서명·만료·nonce 검증을 구성한다.
- [ ] 현재 STATELESS 설정과 외부 로그인 진행 상태 저장 방식을 조정한다. 짧은 Redis 상태 보관 등은 후보이며 일회 사용과 TTL을 둔다.
- [ ] 이메일이 같다는 이유만으로 기존 계정을 자동 연결하지 않는다. 기존 계정의 재인증·명시적 동의를 요구하는 정책을 우선 검토한다.
- [ ] 연결·해제는 민감 작업으로 취급하고 마지막 로그인 수단 제거를 방지한다.
- [ ] 소셜 전용 회원의 탈퇴는 기존 비밀번호 확인을 그대로 요구하지 않고 최근 플랫폼 재인증 등 별도 정책을 사용한다.
- [ ] 콜백 URL·브라우저 기록·로그에 자체 토큰을 노출하지 않는 프론트 전달 방식을 정한다.
- [ ] 동시 최초 로그인에서 중복 회원·연결이 생기지 않도록 DB 제약과 충돌 처리를 검증한다.
- [ ] 취소·실패·이미 연결된 계정·정지 회원·연결 해제 시나리오를 테스트한다.

완료 기준: 일반 로그인과 소셜 로그인이 동일한 내부 회원·토큰 정책을 사용하고, 외부 계정 연결로 타인의 계정을 가져올 수 없다.

## 10. 추가할 만한 항목과 우선순위

| 항목 | 우선순위 | 이유 / 범위 |
| --- | --- | --- |
| JWT claim·키 관리 | 필수 점검 | 허용 알고리즘 고정, 만료와 필요한 issuer/audience 검증, 비밀키 환경별 분리·로그 제외 |
| 보안 감사 로그 | 기본 범위 | 로그인 실패·회전 재사용·정지·계정 연결 등 사건 기록. 토큰·비밀번호 원문 제외, 보관 기간 합의 |
| 민감 작업의 최근 재인증 | 계정 연결·해제에 우선 | 탈취된 로그인 상태만으로 로그인 수단 변경을 하지 못하도록 제한 |
| 이메일 검증 | 이메일을 신뢰 수단으로 쓸 때 | 소유 확인 없이 계정 연결·복구 수단으로 신뢰하지 않음 |
| 비밀번호 변경·재설정 | 다음 확장 | 일회성·단기 토큰, 계정 존재 노출 완화, 발송 제한, 기존 로그인 폐기와 연계 |
| 활성 기기 조회·개별 로그아웃 | sid 구현 후 선택 | 사용자가 의심 로그인 종료. 기기 표시는 식별의 절대 증거로 사용하지 않음 |
| 관리자 MFA | 후순위 | 민감 권한 보호 가치가 있으나 초기 범위에서는 일정 고려 |

이 항목을 모두 한 번에 구현하지 않는다. 우선 토큰 수명·폐기, 인가 누락, 쿠키 보호, 장애 정책을 완성하고 확장한다.

## 11. 최종 검증과 측정

| 분야 | 대표 시나리오 | 증거 |
| --- | --- | --- |
| 인증 | 잘못된 토큰, 로그아웃·정지·복구 후 재사용 | 성공/거절 응답, 접근 기록 |
| 인가 | A가 B의 조회·취소·결제·출입 기능 호출 | 접근 거절 + 데이터 변경 없음 |
| 재발급 | 동시 교체·재사용·응답 유실 | 한 번의 교체, 일관된 폐기 범위 |
| 요청 제한 | 시간 창·동시 요청·제한 해제 | 429·Retry-After·실제 허용 횟수 |
| 소셜 로그인 | 신규·기존·연결 충돌·정지·탈퇴 | 동일 내부 회원 매핑과 안전한 실패 |
| 장애 | Redis 중단·재시작·데이터 유실·동기화 실패 | 정책대로 차단·복구, 차단 토큰 부활 없음 |
| 비용 | 동일 환경의 도입 전후 부하 | p50/p95/p99·성공 RPS·오류율·Redis 지연·메모리 |

보안 검사 추가로 지연이 증가해도 측정값을 그대로 제시한다. 조회 성능은 Kotlin 기준선, SQL 개선, 필요 시 캐시 추가를 각각 비교해 인증 비용과 섞이지 않게 한다. 배포 전환 시 기존 토큰 처리, 롤백 시 폐기 정보 보존, 재로그인 안내까지 기록한다.
