# V3: Redis 인증 상태 전환 설계 초안

> 상태: 설계 초안, 구현·측정 미완료 / 2026-10-15  
> 선행조건: V2의 DB 기반 보안 동작과 측정 기준선  
> 기준: [V2 계획](v2-plan.md), [인증 정책](../../decisions/authentication-policy.md)  
> 기존 Redis 도입 범위·설계 문서의 논점을 V1 → V2 → V3 순서에 맞춰 재구성했다.

## 1. 목적

V3의 목적은 V2와 같은 보안 요구사항을 유지하면서, 수명이 제한된 인증 상태의 저장과 동시 처리를 Redis로 전환하는 것이다. V2의 DB 조회·잠금 비용과 V3의 Redis 호출·메모리·동기화 비용을 비교한다.

현재 Redis 인증 구현이나 성능 개선 결과는 없다. 아래 키 구조와 알고리즘은 구현 후보이며, V2에서 확정한 정책에 맞춰 조정한다.

## 2. 이전 범위와 유지 범위

| 데이터 | V3 방향 | 주의점 |
| --- | --- | --- |
| 활성 로그인 세션 | Redis 이전 대상 | 세션 누락을 인증 성공으로 해석하지 않음 |
| RT 현재 상태·사용 기록 | Redis 이전 대상 | 재사용 탐지 기록 보존 |
| API 제한 상태 | Redis 이전 대상 | V2와 같은 알고리즘·기준 유지 |
| 인증 Challenge·Grant | Redis 이전 대상 | 최종 DB 업무와 원자성 재설계 |
| 인증 Guard | 이전 대상 | 최종 잠금·장기 실패 단계의 유실 방지 |
| Member·LocalCredential | DB 유지 | 회원·자격 증명 원본 |
| 감사·업무 기록 | DB 등 영속 저장 유지 | 보존 및 조회 정책 |
| 예약·결제·크레딧 | 기존 DB 중심 유지 | 인증 개선과 별도 범위 |

Redis를 사용한다는 이유로 모든 상태에 짧은 TTL을 설정하지 않는다. 최종 관리자 잠금은 단순한 3분 코드와 다르며, TTL 만료나 데이터 유실로 해제되면 정책 위반이다.

예약·결제 분산락, 일반 조회 캐시, 예약 상태 전이는 기본 범위에서 제외한다. 기존 DB 동시성 장치를 대체할 근거가 필요하다.

## 3. 저장소 경계

인증 정책과 저장 기술이 강하게 결합되지 않도록 세션 조회·폐기, RT 교체, 요청 제한 판정을 명시적인 작업 단위로 분리하는 방안을 검토한다.

DB의 엔티티 CRUD를 그대로 Redis 명령으로 치환하는 것만으로는 충분하지 않다. “유효성 검사와 RT 교체”, “횟수 검사와 증가”처럼 함께 원자적으로 수행되어야 하는 경계를 인터페이스 수준에서 표현한다.

V2와 V3에 같은 외부 시나리오를 적용하되 DB 내부 조회에 결합된 테스트는 저장소 구현 테스트와 분리한다. 공개 API의 보안 의미를 유지하는 것이 기준이다.

## 4. 로그인 세션과 AT

V2에서 sid 기반 세션을 선택했다면 V3에서도 같은 식별 의미를 유지한다. 보호 API는 JWT 검증 후 Redis의 활성 세션과 필요한 회원 보안 정보를 확인한다.

### 키 후보

| 키 후보 | 값 | 수명 기준 |
| --- | --- | --- |
| auth:session:{sid} | 회원 연결·생성·만료·폐기 상태 | 세션 절대 수명과 정리 정책 |
| auth:member-sessions:{memberId} | 회원의 세션 식별자 목록 | 세션 정리와 일관성 유지 |
| auth:refresh:{hash} | sid·상태·만료·사용 기록 | 계열 유효 기간·탐지 보존 |
| auth:member:{memberId} | 상태·역할·보안 버전 후보 | 누락·동기화 정책 별도 |
| auth:limit:{scope}:{key} | 요청 제한 상태 | 윈도·버킷 정책 |

위 표는 개념적 후보다. Redis Cluster에서 여러 키를 한 원자 연산에 묶으려면 실제 hash tag와 슬롯 배치를 별도로 설계한다. 원문 토큰·이메일을 그대로 키에 넣는 방식은 피하고 식별자 또는 키용 보호값을 검토한다.

### sid와 jti 선택

과거 설계에는 jti별 AT denylist가 있었다. 하지만 토큰 하나를 차단하는 것과 한 로그인 세션에서 발급한 모든 AT를 차단하는 것은 다르다.

V2가 sid 기반으로 완성되면 이를 V3로 옮기는 것을 우선 검토한다. 별도 jti denylist는 개별 AT만 폐기해야 하는 요구가 있을 때 도입한다. 두 방법을 이유 없이 중첩하지 않는다.

## 5. RT Rotation의 원자성

유효한 현재 RT인지 검사하고, USED로 전환하고, 새 토큰 기록과 현재 포인터를 등록하는 절차는 하나의 원자적 작업으로 묶는다. Lua 등의 방식은 선택 후보이며 실제 키 구조와 함께 검토한다.

원자적 Redis 연산이 DB 회원 상태 변경까지 자동으로 포함하지는 않는다. 회원 정지와 refresh가 경합할 때, 정지 완료 후에도 새 토큰이 유효하게 남지 않는 조건을 별도로 설계해야 한다.

재사용 토큰의 기록은 바로 삭제하지 않는다. 현재 토큰만 남기면 알 수 없는 값과 이미 쓴 값을 구분하기 어려워진다. 보존 수명은 계열 수명과 탐지 요구에 맞춘다.

같은 RT 동시 제출 시 한 번만 갱신 성공한다는 V2 기준을 유지한다. 재사용 탐지 후 family/sid 폐기 범위, 응답 유실·다중 탭 처리도 V2와 같은 정책을 사용한다.

## 6. 요청 제한

V2와 동일한 정책을 Redis의 원자적 처리로 구현한다. 예를 들어 이동 윈도 로그를 선택했다면 오래된 기록 제거·현재 개수 확인·새 요청 기록·TTL 설정을 하나의 작업으로 처리한다.

정책을 유지하려면 다음 항목이 같아야 한다.

- 어떤 요청을 세는가: 전체 요청인지, 실패 요청인지.
- 키: IP·정규화 이메일·세션 등 어떤 범위인가.
- 허용 횟수, 시간 창, burst, 재허용 시점.
- 응답 상태와 재시도 안내.
- 서버 간 시간 기준과 창 경계 처리.

V2 고정 윈도와 V3 이동 윈도를 비교하면 저장소와 알고리즘 변화가 섞인다. 알고리즘 개선을 하려면 별도 실험으로 구분한다.

키 개수와 메모리 사용량, 정리 비용을 관찰한다. 랜덤 이메일 요청으로 제한 키가 과도하게 늘어나는 경우도 검토한다.

## 7. 이메일 인증 임시 상태의 이전

Challenge의 번호 수명, Grant의 수명·단일 사용, Guard의 누적 실패·차단을 V1 정책 그대로 유지한다. 기존 DB 잠금이 보호하던 발급·검증·소비의 경계를 Redis 원자 연산으로 다시 표현한다.

### 7.1 Guard의 수명

일시 차단이 끝났다고 blockStage까지 사라지면 사용자가 반복해서 1차 차단만 받게 된다. 최종 adminLocked가 키 삭제로 해제되어서도 안 된다.

장기 보안 상태를 DB에 영속 유지할지, Redis 영속성 및 복구 절차로 관리할지 결정한다. 이전 대상이라는 방향과 모든 Guard 데이터를 휘발 상태로 둔다는 결정은 다르다.

### 7.2 Grant 소비와 DB 업무의 원자성

V1·V2에서는 DB 트랜잭션 하나로 가입·비밀번호 변경과 grant 소비를 묶을 수 있다. grant를 Redis로 옮기면 이 보장이 그대로 유지되지 않는다.

| 순서 | 발생 가능한 문제 |
| --- | --- |
| Redis에서 먼저 소비 → DB 변경 | DB 실패 시 유효 grant가 사라져 재시도 불가 |
| DB 변경 → Redis 소비 | 소비 실패·경합으로 동일 grant 재사용 가능 |
| Redis 사용 예약 → DB 변경 → 확정 | 예약 유실·타임아웃·복구·중복 재시도 정책 필요 |

후보는 DB에 최종 소비·멱등 처리 영수증을 남기는 방식, 사용 예약과 복구 상태를 두는 방식, 최종 grant 소비만 DB에 유지하는 방식이다. 마지막 후보를 택하면 Redis 이전 범위의 변경을 명시해야 한다.

어떤 방식을 선택해도 “업무 실패 시 재시도 가능, 성공 후 재사용 불가”라는 외부 의미를 검증한다. Redis TTL만으로 이 문제를 해결했다고 설명하지 않는다.

## 8. DB 회원 상태와 Redis의 일관성

DB의 회원 상태 변경과 Redis의 세션 폐기는 하나의 로컬 트랜잭션이 아니다. DB 정지는 성공했지만 Redis의 기존 세션이 활성인 경우, Redis만 읽는 인증 경로가 잘못 허용할 수 있다.

결정해야 할 사항은 다음과 같다.

1. 정지·재설정 API가 언제 폐기 완료를 응답하는가.
2. Redis 반영 실패 시 요청을 실패·대기·복구 중 무엇으로 처리하는가.
3. 오래된 인증 상태가 남은 구간의 보호 요청을 어떻게 거부하는가.
4. 재시도 기록과 중복 처리·보상 절차는 어디에 보관하는가.

outbox나 재시도는 변경 전달을 복구하는 후보다. 재시도가 있다는 사실만으로 반영 전 구간의 즉시 차단이 보장되지는 않는다. Kafka 도입을 이 문제의 필수 조건으로 삼지 않는다.

DB authVersion과 Redis의 현재 버전을 사용하는 안도 후보다. 복구 때 버전을 되돌리지 않으며, Redis의 버전이 오래됐을 때 감지·차단하는 경로가 필요하다.

## 9. 장애·유실 정책

확정 방향은 “인증 판정이 불가능한 보호 요청은 허용하지 않는다”이다. 최종 HTTP 오류 계약은 구현 시 정한다.

| 상황 | 처리 방향 |
| --- | --- |
| 서명 오류·만료·폐기 인증 | 인증 거부 |
| Redis 접속 불가·타임아웃 | 인증 조회 우회 금지, 503 등 장애 응답 구분 |
| 활성 세션 키 부재 | 성공으로 해석하지 않음 |
| 재시작 후 저장 데이터 유실 | 재로그인 또는 명시적 복구 경로 |
| 폐기 기록만 유실 | 이전 토큰이 다시 유효해지지 않도록 세대·활성 세션 정책 |
| 메모리 부족·쓰기 실패 | 폐기·교체 성공으로 응답하지 않음 |
| DB에는 있으나 Redis에는 폐기된 RT | 무조건 DB fallback으로 재허용하지 않음 |

denylist만 쓰면 키 부재가 “폐기되지 않음”인지 “폐기 기록 유실”인지 구분되지 않는다. 활성 세션 존재를 요구하는 방식은 유실 시 거부하도록 설계할 수 있지만 가용성 비용을 갖는다.

접속 실패에 대한 fail-closed만으로 정상 접속되는 Redis의 오래된 데이터까지 감지할 수 있는 것은 아니다. 동기화 검증과 장애 처리를 구분한다.

## 10. 전환 전략

간단한 프로젝트 전환 후보는 배포 시 기존 세션·RT·미완료 인증을 무효화하고 재로그인·재인증을 요구하는 방식이다. 사용자 영향은 있지만 두 저장소 간 이중 검증의 복잡도가 줄어든다.

무중단 이전을 선택하면 토큰 버전별 검증 원본, 전환 기간, 폐기 이벤트 전달, 전환 종료와 롤백을 설계한다. DB 또는 Redis 중 어느 한쪽에서 유효하면 통과시키는 정책은 사용하지 않는다.

전환 방식은 아직 확정되지 않았다. 로컬·발표 환경의 재로그인 허용과 실제 운영 중 전환을 별도로 결정한다.

## 11. 성능 비교 실험 설계

| 통제 항목 | 기록 내용 |
| --- | --- |
| 코드 | V2·V3 정확한 SHA |
| 정책 | 토큰 수명·제한 알고리즘·폐기 의미 |
| 환경 | 앱 인스턴스 수·CPU·메모리, DB·Redis 사양, 네트워크 |
| 부하 | 동일 스크립트, 사용자·세션 수, 요청률, 데이터 규모 |
| 실행 | 워밍업·측정 시간, 반복 횟수, 실행 순서 |
| 관측 | p50/p95/p99, 처리량, 오류율, 2xx/401/429/5xx |
| 저장소 | DB 쿼리·연결·잠금 대기, Redis 호출 지연·메모리 |

시나리오는 보호 API 반복, 정상 RT 갱신, 같은 RT 경합, 로그인·인증 요청 제한, 이메일 인증 작업으로 나눈다. 메일 외부 전송 비용은 포함 여부를 명확히 하여 저장소 비교를 왜곡하지 않도록 한다.

성능은 기대값을 결과처럼 적지 않는다. 같은 보안을 유지했는지 먼저 확인하고, 개선 폭·변동 폭·병목 이동·운영 복잡도를 함께 보고한다.

## 12. AWS 검증

개인 AWS 환경에서 앱·MySQL·Redis 연결과 네트워크·보안 설정을 직접 구성하고 측정하는 것이 후속 목표다. 구체적인 서비스·사양·비용은 배포 시점에 확인한다.

로컬 Docker Redis 테스트와 관리형 Redis 운영은 별도 경험이다. 재시작·장애·백업·연결 풀·비밀값·관측 지표를 검증한다. 현재 팀 배포 상태와 개인 실습 계획을 혼동하지 않는다.

## 13. V3 수용 기준

- [ ] V2와 동일한 11개 보안 시나리오 및 회귀 테스트 통과
- [ ] RT 재사용·응답 유실·동시성 결과가 V2 정책과 일치
- [ ] Guard 단계·최종 잠금 유실 방지
- [ ] grant와 DB 최종 작업의 재시도·중복 방지
- [ ] 회원 변경과 Redis 폐기 동기화 실패 시 인증 우회 없음
- [ ] Redis 중단·재시작·키 유실·쓰기 실패 검증
- [ ] 전환·롤백 절차 및 기존 인증 처리 확정
- [ ] V2/V3 동일 조건 측정과 한계 기록

## 14. 기존 문서와의 관계

기존 docs/authorization-improvement-plan/01-redis-adoption-scope.md와 02-redis-auth-design.md의 범위·책임·장애·재사용 논점을 통합한 초안이다. 과거의 “AT jti 차단부터 바로 Redis 도입” 순서는 현재 로드맵의 선행 단계가 아니다.

원본 문서를 이동·삭제하기 전에는 외부 링크와 팀 문서 참조를 확인한다. 이 문서 작성만으로 Redis 설계가 최종 승인되거나 구현된 것은 아니다.
