# SlotKey 인증 고도화 문서 지도

> 작성일: 2026-10-15 (KST)  
> 구현 기준: PR #302 / `auth/v1-frontend-integration` / `5c60fa444dfc427016954fdacc44d3dfd293c004`  
> 상태: V1 구현 검토 기준 문서. V2·V3는 계획이며, PR은 작성 시점에 dev에 병합되지 않았다.

## 1. 이 작업의 목표

SlotKey의 이메일 기반 가입과 복구 절차를 명확히 하고, 로그인 이후 인증 수단의 수명과 폐기를 서버가 관리하도록 개선한다. 먼저 DB에서 보안 요구사항을 만족시킨 뒤, 같은 요구사항을 Redis로 구현하여 성능과 운영 복잡도를 비교한다.

개발 결과는 기능 목록만으로 설명하지 않는다. 각 변경을 “기존 동작 → 문제를 재현하는 테스트 → 선택한 설계 → 개선 결과 → 남는 비용과 한계”로 연결한다. 이 문서 묶음은 구현자와 리뷰어가 같은 기준으로 코드를 읽기 위한 자료다.

## 3. 권장 읽기 순서

1. 로드맵에서 현재 단계와 최종 목표를 확인한다.
2. 인증 정책에서 이미 확정한 동작과 미결정 항목을 구분한다.
3. V1 구현 해설을 보며 실제 클래스를 따라 읽는다.
4. 보안 테스트에서 V1의 한계를 확인한다.
5. V2 계획의 결정표를 채우고 기능 단위로 개발한다.
6. V2 검증과 기준선 측정 후 V3 설계를 구체화한다.

## 4. 상태 표기 규칙

| 표기 | 뜻 |
| --- | --- |
| 구현 확인 | 기준 커밋의 소스에서 동작을 확인 |
| 테스트 확인 | 해당 시나리오의 실행 결과를 확인 |
| 확정 방향 | 사용자와 합의한 목표이며 구현 완료를 뜻하지 않음 |
| 설계 후보 | 선택지 또는 추천안. 합의 없이 확정 정책으로 사용하지 않음 |
| 결정 필요 | 구현 전에 의미·범위·수치를 정해야 함 |
| 검증 필요 | 코드가 있거나 계획이 있어도 실행·운영 근거가 부족함 |

테스트가 통과했다는 표현에는 대상 범위를 함께 적는다. 빌드 성공, 기능 테스트 통과, 실제 배포 검증은 서로 다른 근거다.

- 의도적 실패를 기본 테스트에 유지하는 것이 현재 프로젝트의 선택이다. CI 실패를 숨기거나 자동으로 성공 처리하지 않는다.
- 문서 작성 과정에서 테스트를 다시 실행한 것은 아니다. 위 수치는 검토한 CI 실행의 기록이다.

## 6. 문서별 원본 책임

정책은 `authentication-policy.md`, 구현 구조는 `auth-v1-implementation.md`, 테스트 의미는 `auth-security-tests.md`를 기준으로 한다. 로드맵에는 이 내용을 반복하지 않고 상태와 링크를 유지한다.

정책 변경 시 정책 문서와 관련 테스트를 함께 갱신한다. 구현만 바뀌고 외부 동작이 유지되면 구현 문서를 갱신한다. 테스트 결과를 새로 측정하면 커밋·환경·실행 명령·실행 링크를 추가한다.

V1 구현 문서는 V2 이후에도 비교 근거로 보존한다. 다만 “현재 구현”으로 혼동되지 않도록 V1 기준점 표시를 유지한다.

## 7. 인수인계 주의사항

- Google 소셜 로그인은 V1~V3 이후에 추가한다.
- 과거 인계서의 “V1에 Google 포함” 및 “바로 Redis 도입” 순서는 현재 계획이 아니다.
- 과거의 `21b3a13`, `auth-v1-baseline` 표기는 당시 기록이다. 원격 태그 존재와 재현 가능성은 별도 확인하며, 현재 소스 기준은 위 전체 커밋 SHA다.
- 레드 테스트는 발표용 개선 전후 증거이면서 V2의 수용 기준이다. 실패 개수를 유지하려고 올바른 구현을 되돌리지 않는다.
- 로컬 ZIP, PR head, dev, 운영 배포 상태를 서로 같은 것으로 간주하지 않는다.
