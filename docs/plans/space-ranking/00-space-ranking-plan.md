# 베스트 공간 랭킹 구현 계획

> 작성: 2026-10-16. 범위·순서의 기준 문서다. 이유와 trade-off는 [decisions/space-ranking.md](../../decisions/space-ranking.md)에 있고 여기에 복사하지 않는다. API 규칙은 [api-spec §14](../../api/api-spec.md), 테이블은 [erd.md](../../architecture/erd.md)의 `space_ranking_snapshot`을 본다.

## 1. 범위

| 포함 | 제외 (한계는 결정 문서 §6) |
| --- | --- |
| 공간별·지역별 일간/주간/월간 랭킹 (순매출, 예약 건수, 예약 슬롯 수) | 오늘·이번 주·이번 달 임시 순위, 가동률·취소율 지표 |
| 매일 00:01 확정 배치 + 시작 시 빠진 기간 보충 | 다중 서버 중복 계산 방지 락, 늦게 반영된 거래의 재확정 |
| 오늘 상태별 건수를 서버 집계 API로 이전 | 기존 운영 대시보드의 다른 클라이언트 집계 이전 |
| `spaces.location` enum 검증(판교·강남·하남) | `region` 테이블, 지역 관리 화면, 공간 등록일 표시 |

## 2. 단계

한 번에 한 단계만 구현한다. 각 단계는 테스트를 먼저 쓰고 실패를 확인한 뒤 구현한다. 단계 보고는 `docs/lab/notes/space-ranking/step-{번호}.md`에 둔다.

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| 1 | 지역 enum 검증: 공간 등록·수정 요청의 `location`을 판교·강남·하남으로 제한. 마이그레이션 전에 기존 데이터가 세 값뿐인지 확인(아니면 멈추고 질문) | 잘못된 값 400 테스트, 기존 데이터 확인 결과 보고 |
| 2 | Flyway V22: `space_ranking_snapshot` 테이블, 집계용 인덱스(`reservation(status, start_time, space_id)`, `credit_transaction(type, created_at, reservation_id)`) | 마이그레이션 적용, 실행 계획 확인 |
| 3 | 집계 쿼리 + 확정 서비스: 기간 계산(KST·월요일 시작·반열린 구간), 순매출(현금주의)·건수·슬롯 수 계산, 0 행 제외, 덮어쓰기 저장 | 결정 문서 §5의 계산·경계 테스트 통과 |
| 4 | 스케줄러(매일 00:01 KST, 주간·월간 포함)와 시작 시 빠진 기간 보충. 최초 보충 범위(기본안: 최근 31일)를 확정 | 멱등·보충 테스트 통과 |
| 5 | 조회 API: 공간 랭킹, 지역 랭킹(공간 행 합산), 상태 `CONFIRMED`/`PENDING`/`UNAVAILABLE`, 동점 규칙, 이전 기간 순위 | api-spec §14 대로 통합 테스트 통과, 권한 테스트 |
| 6 | 상태별 건수 API(`status-counts`) 추가 후 프런트의 브라우저 건수 계산 제거 (예약 목록은 이미 날짜 필터 조회라 그대로 둠, 2026-10-16 결정) | 기존 화면 동작 유지, 건수는 서버 값 |
| 7 | 프런트 랭킹 섹션: 기간·지표·지역 선택, 집계 중 안내, 유의사항(확정 시각, 동점 순서, 현금주의, 한계) | 화면 확인, 동점·빈 기간·집계 중 표시 |
| 8 | 검증·문서화: 전체 테스트 직접 실행, 결정 문서 검증 결과·면접 정리 채움, api-spec·erd 최종 갱신 | 인계 보고(①–④) 작성 |

## 2-1. 묶음 구성과 검증 범위

> 2026-10-16: 단계를 묶음 A·B·C로 나눠 구현하고, 묶음마다 좁은 검증을 둔 뒤 마지막에 최종 검증을 한다. 구현이 Claude Code로 바뀌어 구현과 검증은 서로 다른 세션이며, 보고에 "자기검증"을 표시한다. 커밋은 최종 검증 통과 후 대상 파일 목록을 보여주고 한다(문서/코드 분리, push 없음).

| 묶음 | 단계 | 좁은 검증이 보는 것 | 보지 않는 것 |
| --- | --- | --- | --- |
| A | 1–3 (location enum, V22 테이블·인덱스, 집계·확정 서비스) | 새 테스트 직접 실행(현금주의 순매출, KST·월요일 경계, 동점, 0 행 제외, 멱등). 선행 확인 3개(`location` 기존 값, `RESERVATION_CHARGE` 부호, `Clock`·DB 시간대). V22 번호 충돌 여부 | API 모양, 화면 |
| B | 4–5 (스케줄러·보충, 조회 API) | 새 테스트 직접 실행(보충, 중복 실행 멱등). API가 api-spec §14와 필드·상태(`CONFIRMED`/`PENDING`/`UNAVAILABLE`)·오류 코드까지 일치하는지, 비관리자 차단 | 프런트 |
| C | 6–7 (상태별 건수 이전, 프런트) | 화면 확인, 기존 대시보드 동작 유지, 전체 다운로드 코드 제거 | |
| 최종 | 8 | 전체 테스트 직접 실행, `AGENTS.md` 규칙 1–7, 신규 코드의 Lombok·시크릿, 배포 job 변경 여부, 에이전트 코드에 상태 변경 도구 없음, 동시성·멱등성 경계 테스트, 결정 문서 검증 결과·면접 정리 채움, api-spec·erd 갱신 | |

보고 파일: `docs/lab/notes/space-ranking/step-1-3.md`, `step-4-5.md`, `step-6-7.md`, 최종 검증은 `step-8.md`.

## 3. 구현 전 확인 항목 (미확인)

- 운영 `DB_URL`의 시간대 설정과 `Clock` 빈 정의
- `RESERVATION_CHARGE`의 부호(ERD는 차감 −로 기록. `CreditServiceImpl`로 확인)
- 운영 수준의 예약 데이터 양(계산 쿼리 시간 측정에 필요)
- 최초 배포 시 보충 범위
- 응답에 `UNAVAILABLE` 상태를 두는 것(확정 전 과거 기간 구분용, 설계 합의에서 구체화하지 못한 항목이라 리뷰 필요)

## 4. 화면 유의사항 문구 초안

- "순위는 해당 기간이 끝난 뒤 24:00(다음날 00:00) 기준으로 확정된 값이며, 이후 환불 등 변경은 해당 기간의 값에 반영되지 않습니다."
- "오늘·이번 주·이번 달은 집계 중입니다. 오늘 순위는 내일 00:00 기준으로 확정됩니다."
- "순매출은 결제에서 환불을 뺀 값이며 위약금을 포함합니다. 환불·위약금은 발생한 날에 반영됩니다."
- "지표 값이 같으면 순매출 순위는 예약 건수, 예약 건수 순위는 순매출, 슬롯 수 순위는 예약 건수, 그래도 같으면 공간 ID가 작은 순서로 정해집니다."
- "취소된 예약은 예약 건수에 포함되지 않지만 위약금은 순매출에 포함됩니다."
