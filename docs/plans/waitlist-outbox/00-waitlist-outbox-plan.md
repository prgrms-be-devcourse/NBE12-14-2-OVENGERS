# 예약 대기열 + Outbox + Kafka 구현 계획 (10/21)

> 작성: 2026-10-15. 마감 2026-10-21까지 Spring + Java로 구현하는 범위와 순서의 기준 문서다. 문제와 대안의 기록은 [waitlist](../../decisions/waitlist.md), [outbox-kafka](../../decisions/outbox-kafka.md)에 두고, 자동 선점권 관련 항목은 3차로 이월했다. 세부는 [01 대기 신청 규칙](01-waitlist-rules.md), [02 Outbox·Kafka 설계](02-outbox-kafka-design.md)를 본다.

## 1. 범위

| 포함 (10/21) | 3차로 미룸 |
| --- | --- |
| 대기 신청·취소·내 목록·신청 순서 | 순번 자동 선점권(1순위에게 HOLD 제안), 연쇄 |
| 이벤트 1종(`SlotReleased`), 폴링 Outbox, Kafka 발행 | CDC, 다중 인스턴스 락, DLT |
| 컨슈머(멱등) → 대기자 전원 알림(DB 저장 + 조회 API) | SSE·메일, 예약 성사 감지(FULFILLED), 재인증(PIN) |

## 2. 방식 선택: 순번 선점(A) 대신 전원 알림 + 선착순(B)

| 기준 | A. 순번 선점 | B. 전원 알림 + 선착순 | C. 순번대로 시차 알림 |
| --- | --- | --- | --- |
| 공정성 | 높음 | 낮음 | 중간 |
| 순번의 의미 | 약속이 지켜짐 | 신청 순서(참고용) | 우선 알림일 뿐 |
| 기존 예약 경로 영향 | 큼 | 없음 | 없음 |
| 구현·테스트 비용 | 높음 | 낮음 | 중간 |
| 10/21 적합도 | 낮음 | 높음 | 중간 |

**B를 고른 이유**
1. A의 순번은 지켜지지 않는 약속이 된다. 대기자가 아닌 사람의 직접 예약 경로가 막혀 있지 않으면 1순위도 자리를 보장받지 못한다. 보장하려면 선점 구간 동안 일반 예약을 막아야 하고, 그러면 이 프로젝트의 핵심인 예약 동시성 경로를 건드린다.
2. A는 부수 상태가 늘어난다. 1순위 HOLD 생성, 만료 시 다음 순번 이월, 무응답·정지 회원·크레딧 부족자 처리가 모두 필요하다. 정처기(10/25) 직전 일주일에는 무겁다.
3. B는 "알림은 힌트, 판정은 슬롯 UNIQUE"로 정리된다. 기존 `createHold`를 고치지 않고, 테스트도 "알림 대상 선정"과 "멱등"에 집중한다.

**B의 약점과 대응**
- N명이 동시에 시도해 N-1명이 409를 받는다 → 알림 문구에 선착순이며 보장이 없다는 점을 명시한다. 3차에서 C나 A로 올린다.
- 오래 기다린 사람이 불리하다 → 순번은 "신청 순서(참고용)"로 표기해 약속처럼 보이지 않게 한다.
- "점유 중인 슬롯도 모두 예약 가능하게"는 하지 않는다. 점유 중인 슬롯에는 **대기 등록만** 허용하고, 예약은 슬롯이 비었을 때 기존 UNIQUE로 처리한다.

## 3. 구현 순서

대기 신청을 먼저 한다. 컨슈머가 `waitlist_entry`를 필요로 하고, 새 인프라 없이 끝나는 가장 안전한 단위이며, Kafka가 늦어져도 독립적으로 완성되기 때문이다.

| 단계 | 내용 | 구현 | 비고 |
| --- | --- | --- | --- |
| 0 | prep: 결정 목록 확인 + 발행 지점 3곳·에러 코드 이름을 실제 코드와 대조 | Claude Code | Codex 토큰을 쓰지 않는다. 결과는 2단계 지시문에 요약으로 넣는다 |
| 1 | 대기 테이블·신청/취소/내 목록/신청 순서 API + 본인 점유 차단 + 테스트 | Claude Code | Kafka 없음 |
| 2 | `outbox_event` + 3곳 기록 + 롤백 시 이벤트 없음 테스트 (발행 없음) | **Codex** | 기존 동시성 테스트 회귀 확인이 핵심. 토큰이 적어 지시문을 자급형으로 쓴다(아래) |
| 3 | `OutboxPublisher` 포트(Kafka·Fake) + relay + compose 프로필 + spring-kafka | Claude Code | **단계 1 직후 compose 기동 스모크 30분을 먼저** 해 인프라 위험을 일찍 드러낸다. **추가 할 일(fix-2)**: compose 스모크 때 본인 점유 조회의 인덱스를 `key_len`·`Extra`를 포함한 표로 다시 재서 `(member_id, space_id, status, start_time)` vs `(member_id, space_id, start_time)`를 비교하고 결과를 `01` 문서 "인덱스" 항목에 적는다 — 바뀐 WHERE가 `status IN (…) OR (status=HELD AND …)` 형태라 `status`가 동등 조건으로 쓰이지 못해 4번째 칸이 범위 축소에 못 쓰일 수 있고, 1단계 EXPLAIN 표에는 `key_len`이 없어 그것이 확인되지 않았다(step-1-review.md L4) |
| 4 | 컨슈머 핸들러 + `processed_event` + `notification` + 알림 API | Claude Code | |
| 5 | 로컬 E2E(취소 → 알림 → 선착순 예약), api-spec·erd 갱신, README 기술적 의사결정 정리. **`decisions/waitlist.md`·`outbox-kafka.md`를 `decisions/TEMPLATE.md` 형식으로 채운다**(기각한 대안, trade-off, 한계·재검토 조건, 면접·발표용 정리) | Claude Code | 면접·발표·위키 ingest용. 시간이 부족하면 README 정리보다 이 항목을 우선한다 |

**역할 배분 (2026-10-15 확정):** Codex 토큰이 약 10%만 남아, 코드량은 적고 위험은 큰 2단계(Outbox 기록)에만 Codex를 쓴다. 나머지는 Claude Code가 구현한다. 2단계는 Claude Code가 독립적으로 리뷰하고, Claude Code가 구현한 단계는 새 세션에서 "자기검증"으로 표시해 검증한다(AGENTS.md "작업 역할과 인계 규칙"). 2단계 지시문에는 슬롯 해제 호출 지점 3곳의 파일·메서드, 잠금 순서 주석, 지켜야 할 기존 테스트 이름, 이 계획의 해당 규칙을 그대로 넣어 Codex가 코드 탐색에 토큰을 쓰지 않게 한다. 한 단계만 하고 멈춘다.

일정 목표(마감 10/21): 1단계 10/15~16, 2단계 10/17, 3단계 10/18~19, 4단계 10/20, 5단계 10/21. 밀리면 자르는 순서는 5단계의 README 정리 → 홀드 만료 발행 지점 → 알림 읽음 API이고, 1~4단계 핵심 흐름은 유지한다. Kafka가 끝내 늦어지면 Fake 발행으로 Outbox → 컨슈머 흐름을 먼저 완성하고 Kafka 구현체만 교체한다(포트로 분리한 이유).

## 4. 검증 계획

- 신청: 전부 비어 있으면 거절, 일부 점유면 성공. 같은 공간·겹치는 시간에 본인 `HELD` 또는 `CONFIRMED` 예약이 있으면 거절, 다른 공간이나 겹치지 않는 시간이면 성공. 중복·4건째 거절, 타인 대기 취소 403, 정지 회원 신청 거절.
- 신청(2026-10-15 fix-1 추가): 본인 `HELD`가 **이미 만료**됐으면 점유가 아니므로 신청이 되고, 만료 전이면 계속 거절된다(점유 기준이 예약 경로와 같아야 한다). 취소한 뒤 **같은 구간 재신청이 되고**, 취소·재신청을 반복하면 `CANCELLED` 이력이 쌓이면서 활성은 항상 1건이다. 활성 상태의 중복 신청은 여전히 거절, 이미 취소된 건의 재취소는 멱등, 활성 3건 제한은 `WAITING` 행만 센다.
- Outbox: 취소 트랜잭션이 롤백되면 outbox 행이 없고 성공하면 PENDING이 정확히 1건(3지점 모두). 발행이 실패해도 취소는 성공하고 복구 후 relay가 이어 발행한다.
- 컨슈머: 같은 이벤트를 두 번 전달해도 알림은 한 번. 구간 일부만 비었거나, 정지·탈퇴 회원, 시작이 지난 항목, CANCELLED 항목, 신청 뒤 본인이 예약을 잡은 대기자에게는 알림이 가지 않는다. 홀드 만료 직후 재점유된 슬롯은 알림이 가지 않는다.
- 회귀: `ReservationCancelConcurrencyTest`, `ReservationCompletionSchedulerTest`, `AdminReservationControllerTest` 등 기존 테스트가 그대로 통과한다. 취소와 직접 예약이 동시에 들어와도 슬롯은 한 명만 가진다.
