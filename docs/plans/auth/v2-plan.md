| 지적 | 결과 |

**배포 영향(코드 검토로 확인, 실제 적용은 미검증)**: 기존 AT는 `sid`가 없어 거부되고 기존 RT는 V24가 삭제하므로 모든 사용자가 다시 로그인해야 한다. 구버전 서버는 `auth_session_id` 없이 RT를 저장하므로 V24 적용 DB에서 로그인할 수 없고 `sid`를 검사하지 않으므로, 구·신 서버 혼합 운영과 앱만 되돌리는 롤백은 불가하다. 개발·운영 DB 적용과 실제 환경 동작은 확인하지 않았다.

**회원 상태 차단과 영구 세션 폐기의 구분**: 보호 요청은 1번부터 회원 상태(`ACTIVE`)를 조회해 정지·탈퇴 회원의 AT를 거부한다. 2번은 여기에 더해 탈퇴·관리자 정지·인증 최종 잠금 자동 정지·비밀번호 재설정 시 회원의 모든 세션과 RT의 `revoked_at`을 기록한다. 복구는 상태만 `ACTIVE`로 되돌리고 폐기 기록을 지우지 않으므로 옛 AT·RT는 계속 거부되고 새 로그인만 성공한다.

### 2번 이슈 리뷰 (2026-10-18, 미커밋 작업 트리)

**코드로 확인한 동작**

| 사건 | 연결 위치 | 같은 트랜잭션에서 함께 처리되는 것 |
| --- | --- | --- |
| 탈퇴 | `MemberWithdrawalService.withdraw` | 회원 잠금 → `WITHDRAWN` → 세션·RT 폐기 → 출입 토큰 폐기 (이전의 RT만 폐기를 대체) |
| 관리자 정지 | `AdminMemberService.changeStatus`(대상 상태 `SUSPENDED`일 때만) | 회원 잠금 → 상태 변경 → 세션·RT 폐기 → 감사 로그. 감사 저장 실패 시 폐기도 롤백 |
| 인증 최종 잠금 자동 정지 | `VerificationCheckService.suspendMemberIfNeeded` | Guard 잠금 → 회원 잠금 → `SUSPENDED` → 세션·RT 폐기 → 감사 로그. 서비스가 결과 값을 반환해 커밋한 뒤 Controller가 403을 만들므로 오류 응답과 무관하게 커밋 |
| 비밀번호 재설정 | `PasswordResetService.reset` | Guard 잠금 → 회원 잠금 → 비밀번호 변경 → grant 소비 → 세션·RT 폐기. 어느 단계가 실패해도 함께 롤백 |
| 복구 | `AdminMemberService.restore` | 상태만 `ACTIVE`. 폐기 기록은 그대로 |

- 폐기는 `AuthSessionService.revokeAllForMember`가 `auth_session`과 `refresh_token`을 회원 ID 조건의 bulk update로 처리한다(이미 폐기된 행은 유지, 다른 회원 행은 대상 아님). 두 쿼리는 `flushAutomatically`라 앞선 회원 상태·비밀번호 변경이 먼저 반영되고, `clear`하지 않으므로 같은 트랜잭션의 관리 중인 회원 엔티티가 분리되지 않는다. 이 트랜잭션들은 세션·RT 엔티티를 미리 읽지 않아 오래된 영속 상태를 쓰는 경로가 없다.
- 회원 상태·비밀번호를 바꾸는 운영 코드 경로는 위 네 곳(+복구)뿐임을 호출부 검색으로 확인했다.
- 잠금 순서: 상태·자격 증명 변경 경로는 (Guard →) 회원 → 세션 → RT 순이고, 로그인은 회원 잠금 후 세션·RT를 만든다. 로그아웃은 회원을 잠그지 않고 세션 → RT 순으로 갱신한다. 정적 검토에서 순환 대기 경로는 찾지 못했다(부하 상태의 교착 검증은 아님).

**경합 분석**

- 재설정·정지 ↔ 로그인: 로그인도 회원을 비관적 잠금으로 읽으므로 직렬화된다. 로그인이 먼저면 새 세션도 뒤이은 폐기 대상이고, 폐기가 먼저면 새 비밀번호·변경된 상태로 판정된다.
- 정지·탈퇴 ↔ refresh: refresh는 회원 잠금 후 회원을 다시 읽으므로 정지·탈퇴 커밋 뒤에는 403/401로 거부된다.
- 재설정 ↔ refresh: refresh는 RT·세션을 잠금 없이 읽은 뒤 회원 잠금을 기다린다. 재설정이 그 사이에 커밋하면 회원은 `ACTIVE`라 refresh가 200과 새 AT를 줄 수 있지만, 그 AT의 `sid`는 이미 폐기된 세션이라 다음 보호 요청에서 401이다. RT 회전이 없어 새 RT도 생기지 않으므로 사용 가능한 토큰은 남지 않는다. 3번(RT 회전)에서는 회원 잠금 후 세션·RT 상태를 다시 확인해야 한다(아래 이월 사항).

- 카운트는 로그인 트랜잭션이 시작되기 전에 커밋되므로 로그인 실패(롤백)나 429 응답이 카운트를 되돌리지 않는다. 현재 Controller에는 바깥 트랜잭션이 없어 `REQUIRES_NEW`는 향후 바깥 트랜잭션 안에서 호출될 경우를 막는 장치다.
- 버킷 트랜잭션이 끝난 뒤에 로그인의 회원 잠금이 시작되므로 두 잠금을 동시에 쥐는 경로가 없어 교착 경로가 없다.
- 저장소 예외(`DataAccessException`·`TransactionException`)와 버킷 조회 이상은 `AUTHENTICATION_SERVICE_UNAVAILABLE`(503)로 실패 종료한다(제한 우회 없음). 로그에는 예외 클래스 이름만 남고 이메일·비밀번호는 남지 않는다. 그 밖의 런타임 예외는 기본 500이다.
- 이메일 식별: 버킷 `email`은 `VARCHAR(254)`, 컬럼 collation을 지정하지 않아 DB 기본값을 쓰며, `member.email`(V1, `VARCHAR(254)`)도 지정하지 않았다. 회원 조회(`findByEmailForUpdate`)와 버킷 비교가 모두 DB 비교라 같은 DB에서 생성됐다면 대소문자 등에서 같은 규칙을 따른다(Testcontainers의 MySQL 8.4 기본 `utf8mb4_0900_ai_ci`는 대소문자·악센트 무시, 뒤 공백 유의). 앞뒤 공백이 있는 값은 `@Email` 검증에서 먼저 거부된다고 판단했으나 테스트로 확인하지는 않았다. **운영 DB 두 테이블의 실제 collation은 확인하지 않았고, 대소문자가 다른 이메일의 버킷 공유를 검증하는 테스트도 없다.**
- V26은 새 테이블 생성뿐이라 기존 데이터에 영향이 없다. `CHECK (attempt_count BETWEEN 0 AND 10)`이 코드 상수 10과 묶여 있어, 한도를 올리면 마이그레이션도 함께 바꿔야 한다.
- 로그인 외 경로·기존 세션에는 영향이 없다(제한은 로그인 Controller에서만 호출).

**테스트로 확인한 것 (선택 실행 XML)**

- `V2SecurityRedTest`의 로그인 제한 목표 테스트가 "5회 실패 후 6번째 429"에서 "성공 1회 + 실패 9회 허용, 11번째 429, `Retry-After` 840, 성공 세션 유지"로 바뀌었고 `@Disabled`가 해제됐다. 테스트 소스 전체에 `@Disabled`는 남아 있지 않다.
- `LoginRateLimitIntegrationTest` 7개: 미가입 이메일 10회 후 429, 이메일 간 격리, 다음 구간 재허용과 `Retry-After` 올림(1초), 잘못된 JSON·DTO 미집계, 같은 이메일 최초 동시 12건 중 정확히 10건 허용·2건 429, 저장소 장애 시 503(서비스 단위 테스트로 `DataAccessException`만 확인 — HTTP 응답과 `TransactionException` 경로는 미확인), 제한 후에도 회원 정지·세션 폐기 없음.
- 로그인 실패(트랜잭션 롤백) 후에도 카운트가 유지되는 것은 반복 실패 테스트로 드러나지만, 바깥 트랜잭션 롤백에 대한 `REQUIRES_NEW` 보장 자체를 검증하는 테스트는 없다.
- 기존 `AuthControllerTest` 3개 메서드는 버킷이 테스트 간에 남는 문제(제한 트랜잭션이 테스트의 롤백과 무관하게 커밋됨)를 피하려고 이메일을 무작위로 바꿨다.

**한계**: 고정 15분 구간이라 구간 경계 앞뒤로 최대 20회까지 몰릴 수 있다. 버킷은 이메일·구간마다 한 행이 생기고 정리 작업이 없어 누적되며, 미가입 이메일도 저장하므로 임의 이메일을 대량 입력하면 행이 계속 늘어난다(IP 제한은 정책상 없음). 버킷에는 입력된 이메일 원문이 남는다. 현재 구간보다 이전 구간(`window_id < floor(now/900)`)의 행은 더 이상 판정에 쓰이지 않으므로 언제든 지워도 제한이 약해지지 않는다(정리 작업은 이번 범위가 아님).

## 1. 해결할 문제

V1은 이메일 인증과 가입·복구를 처리하지만, 발급한 AT의 즉시 폐기를 서버가 확인하지 않는다. RT는 DB에서 검증하지만 refresh 성공 시 교체하지 않는다. 범용 요청 제한도 없다.

V2는 서버가 현재 로그인 상태를 관리하여 로그아웃·복구·정지·탈퇴 사건을 기존 인증에 반영한다. 보안 동작을 먼저 정확하게 구현하고 DB 조회·잠금 비용을 측정한다.

## 2. 범위

필수 범위는 DB 세션, AT의 세션 연결·현재 상태 검증, 폐기 사건 연동, RT Rotation·재사용 대응·동시성 제어, 인증 API 요청 제한이다.

전체·기기별 로그아웃 API, 관리자 세션 종료, 권한 변경 반영, CSRF 방어와 감사 로그 확대는 상세 범위를 정한 후 포함한다. 기존 첨부 계획에 후보가 있었다는 이유로 모든 API·관리 화면을 이미 확정된 기능으로 취급하지 않는다.

Google 로그인·Redis 전환·예약 분산락은 V2 범위가 아니다.

## 3. 구현 전에 채울 결정표

| 결정 항목 | 확정된 방향 | 결정이 필요한 세부 사항 |
| --- | --- | --- |
| 세션 단위 | 로그인 단위로 AT·RT 연결 | 식별자, 저장 모델, 현재 기기 의미 |
| AT 검증 | 서버의 유효 세션과 현재 회원 상태 확인 | sid, 권한 갱신 방법, 조회 구조 |
| 만료 | 만료된 인증 거부 | AT 수명 변경, 세션 절대·유휴 만료 |
| 로그아웃 | 대상 세션 AT·RT 폐기 | 전체 로그아웃 API, 반복 호출, 쿠키만 있을 때 |
| 비밀번호 재설정 | 전체 기존 세션 폐기 | 변경 API와의 공통 처리 |
| RT 재사용 | 사용 토큰 거부 및 폐기 대응 | family/sid 또는 회원 전체 |
| 정상 중복 refresh | 같은 RT 교체 한 번만 성공 | 다중 탭 합치기, 응답 유실 재로그인/재시도 |
| 요청 제한 | 한도 초과 429 | API·키·기간·횟수·알고리즘·해제 |
| 권한 변경 | 오래된 역할로 권한 유지 방지 | 세션 폐기 또는 매 요청 최신 역할 |
| 브라우저 요청 보호 | 쿠키 사용 경로 보호 | 배포 출처, SameSite, CSRF 방식 |
| 감사 로그 | 중요 사건 추적 | 대상·보존 기간·개인정보 필드 |

추천 구현안을 아래에 제시하지만 최종 합의로 간주하지 않는다.

## 4. 데이터 모델 후보

### 4.1 AuthSession

| 필드 후보 | 목적 |
| --- | --- |
| id 또는 sid | 로그인 세션 식별 |
| memberId | 회원 연결 |
| createdAt | 생성 시각 |
| expiresAt | 세션 수명 상한 |
| revokedAt | 폐기 여부와 시각 |
| revokeReason | 로그아웃·정지·재설정 등 사유 |
| lastSeenAt | 유휴 만료를 선택한 경우 활동 기준 |

매 요청 lastSeenAt을 갱신하면 읽기 경로에 쓰기 부하가 생긴다. 유휴 만료가 꼭 필요한지 먼저 정하고, 필요하면 갱신 빈도와 허용 오차를 설계한다.

### 4.2 RefreshToken 확장

RT 해시에 세션 연결, 만료, 사용 시각, 폐기 상태, 다음 토큰 연결 또는 계열 식별을 추가하는 안을 검토한다. 사용된 토큰 기록을 즉시 삭제하면 재사용 탐지와 알 수 없는 토큰을 구분하기 어렵다.

sid가 한 토큰 계열을 충분히 나타내면 별도 familyId의 필요성을 검토한다. 개념을 설명하기 위해 불필요한 필드를 모두 추가하지 않는다.

사용 기록 보존 기간은 세션·계열의 허용 수명과 재사용 탐지 요구에 맞춘다. 정리 배치가 유효한 탐지 기록을 너무 일찍 삭제하지 않도록 테스트한다.

## 5. 보호 API의 검증 흐름

1. JWT 서명·만료와 필수 claim을 검증한다.
2. sid로 세션을 조회하고 회원 연결을 확인한다.
3. 세션 존재·만료·폐기를 확인한다.
4. 회원의 현재 존재·상태와 합의한 권한 기준을 확인한다.
5. principal을 만들고 역할·리소스 소유권 검사로 이어간다.

서명 검증 전의 claim을 신뢰하여 인증을 완료하지 않는다. 세션이 없거나 폐기되면 인증 실패로 처리한다. 인프라 장애는 유효하지 않은 토큰과 구분한다.

세션 조회와 회원 조회는 조인 등으로 줄일 수 있으나 실제 SQL과 조회 횟수로 확인한다. 모든 요청에 쓰기 잠금을 거는 방식은 초기 기본값으로 두지 않는다. 읽기와 상태 변경의 일관성 목표를 먼저 정의한다.

## 6. 폐기 사건 처리

| 사건 | 처리 목표 |
| --- | --- |
| 현재 세션 로그아웃 | 대상 세션 폐기, 관련 RT 거부, 쿠키 삭제 |
| 비밀번호 재설정 | 자격 증명 변경·grant 소비·기존 세션 전체 폐기 |
| 회원 정지 | 상태 변경·전체 세션 폐기·감사 기록 |
| 회원 복구 | ACTIVE·Guard 복구, 기존 세션 폐기는 유지 |
| 회원 탈퇴 | 탈퇴 정책 수행·세션 폐기 |
| RT 재사용 | 정책에 맞는 세션/계열 폐기·감사 기록 |

DB 내부 변경은 가능한 동일 트랜잭션으로 묶는다. 다수 세션 폐기에 bulk update를 쓰면 영속성 컨텍스트의 오래된 엔티티와 flush·clear의 영향을 확인한다.

로그아웃은 AT가 만료된 상황에서도 유효한 RT로 세션 종료가 가능한지 정해야 한다. AT와 RT를 모두 받으면 서로 다른 세션의 토큰을 조합한 요청도 검증한다.

## 7. RT Rotation과 동시성

### 7.1 처리 절차 후보

1. RT 해시로 대상과 연결 세션을 식별한다.
2. 정해진 잠금 순서로 회원·세션·토큰의 필요한 상태를 잠근다.
3. 잠금 획득 후 만료·폐기·사용 여부와 회원 상태를 다시 판단한다.
4. ACTIVE RT를 USED로 전환한다.
5. 새 RT 해시와 AT를 생성한다.
6. 트랜잭션 커밋 후 새 RT 쿠키와 AT를 응답한다.

### 7.2 구현 선택지

| 방법 | 장점 | 비용·주의 |
| --- | --- | --- |
| 비관적 잠금 | 한 세션의 상태 전이를 순서대로 이해하기 쉬움 | 대기·데드락·잠금 순서 관리 |
| 조건부 UPDATE | 미사용 조건을 만족한 한 요청만 상태 변경 가능 | 영향 행 수 검사와 후속 발급을 같은 트랜잭션으로 구성 |
| 낙관적 버전 | 충돌이 드문 경우 잠금 대기 감소 가능 | 충돌 처리·재시도·응답 의미 설계 |

어떤 방법이든 “조회 후 미사용이면 발급”을 원자성 없이 분리하지 않는다. 잠금만 추가하고 토큰을 USED로 바꾸지 않으면 두 요청이 순서대로 모두 성공할 수 있다.

정지·재설정·로그아웃·refresh가 서로 다른 순서로 회원과 세션을 잠그면 데드락 위험이 생긴다. 전체 변경 경로의 잠금 순서를 하나의 표로 기록하고 경합 테스트를 만든다.

### 7.3 재사용 탐지와 롤백

USED RT를 발견하면 단순 401 외에 합의한 범위를 폐기하고 이벤트를 기록한다. 폐기 상태를 저장한 뒤 같은 트랜잭션에서 예외를 던져 그 변경까지 롤백하지 않도록 주의한다. V1의 실패 상태 반환 패턴을 참고하되 실제 트랜잭션 경계를 검증한다.

정상적인 동시 탭과 공격자의 재사용을 서버가 항상 구분할 수는 없다. 프런트에서 갱신 요청을 합치는 방법과 응답 유실 시 사용자 경험을 함께 설계한다. 편의를 위해 옛 RT를 임의로 다시 활성화하지 않는다.

## 8. DB 요청 제한

아래 표를 API별로 채운 후 구현한다. 숫자는 아직 확정하지 않는다.

| 대상 | 키 후보 | 셀 동작 결정 |
| --- | --- | --- |
| 로그인 | 정규화 이메일·신뢰한 IP | 실패만 셀지, 모든 요청을 셀지 |
| refresh | 세션·IP | 정상 갱신·오류 요청의 기준 |
| 코드 발급 | 이메일·목적·IP | 30초 간격 외 단기·일일 제한 |
| 코드 검증 | 이메일·목적·IP | 오입력 차단과 API 빈도 제한의 관계 |
| 비밀번호 재설정 | 이메일·IP | grant 오류 요청과 전체 요청 |

고정 윈도는 단순하지만 창 경계에서 요청이 몰릴 수 있다. 이동 윈도는 경계를 완화하지만 기록과 쿼리 비용이 늘 수 있다. 토큰 버킷은 허용 burst의 의미를 정의해야 한다. V3에서 비교할 때 알고리즘까지 바꾸지 않도록 V2에서 결정한다.

DB 카운터는 조회와 증가를 원자적으로 처리하고, 같은 키의 최초 생성 경합은 유일 제약과 적절한 생성 전략으로 제어한다. 만료 기록 정리·인덱스·공격으로 인한 키 증가도 고려한다.

인증 실패와 제한 카운터 저장의 트랜잭션을 점검한다. 실패 예외 때문에 카운터가 롤백되면 제한이 작동하지 않는다.

IP만 제한하면 공유망이 함께 차단될 수 있고 이메일만 제한하면 특정 계정을 공격자가 묶어둘 수 있다. 프록시 헤더를 무조건 신뢰하지 않고 배포 구성에서 인정하는 출처를 정한다.

## 9. 개발 단위와 완료 기준

| 단위 | 결과물 | 확인 |
| --- | --- | --- |
| A | 정책·스키마·잠금 순서 | 결정표, migration 검토 |
| B | 로그인 세션·AT 조회·로그아웃 | 1번 + 정상 보호 API |
| C | 재설정·정지·복구·탈퇴 폐기 | 2·4·7·8·9·10번 |
| D | RT Rotation·경합·재사용 대응 | 3·6·11번 + 폐기 범위 |
| E | 요청 제한·출처 보호·인가 회귀 | 5번 + 경계·격리·재허용 |
| F | 전체 회귀·k6 측정·문서 | 재현 가능한 결과 |

11개만 통과하면 V2 계획 전체가 자동 완료되는 것은 아니다. 전체 세션 API나 권한 변경 등 실제로 채택한 추가 범위의 검증도 필요하다.

## 10. DB 기준선 측정

> 2026-10-21 실행 결과와 측정 조건, 한계: [V3 인증 실험 결과](../../testing/auth-v3-experiment-results.md) §5, §6. DB 쿼리와 잠금 대기 지표는 수집하지 못했다. 아래는 원래 원칙이다.

보호 API, 정상 refresh, 동시 refresh, 로그인·발급 제한 시나리오를 나눈다. 정상 성공 흐름과 공격 제한 흐름을 섞은 평균 하나만 보고하지 않는다.

측정에는 테스트 데이터, 사용자 수, 토큰 수명, 환경 사양, 커넥션 풀, 인덱스, 로그 수준을 기록한다. DB 쿼리·잠금 대기와 애플리케이션 지연을 함께 확인한다. 목표 수치는 측정 전 합의하며 임의의 성능 결과를 작성하지 않는다.
