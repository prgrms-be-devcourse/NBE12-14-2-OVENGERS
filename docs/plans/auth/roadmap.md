## 1. 개발 방향

V1에서 이메일 소유 확인과 가입·복구 기능을 완성한다. V2에서 DB 기반으로 인증 수단 폐기·RT Rotation·요청 제한을 구현한다. V3에서 동일한 보안 정책을 Redis로 전환하고 성능과 운영 비용을 비교한다.

Redis는 보안 요구사항을 처음 정의하는 단계가 아니라, V2에서 확립한 동작을 다른 저장·동시성 제어 방식으로 구현하는 단계다. 성능이 개선되더라도 보안 동작이 달라졌다면 공정한 비교가 아니다.

Google 소셜 로그인은 V1~V3 이후에 추가한다. Kotlin 마이그레이션은 별도 계획이며, 인증 단계의 필수 선행조건으로 자동 삽입하지 않는다. 병행 시 기준 커밋과 담당 범위를 조율한다.

## 4. V1 완료 기록의 의미

V1은 최종 보안 목표를 모두 달성한 상태가 아니다. “이메일 인증 기반 가입·복구 구현”과 “아직 충족하지 못한 로그인 보안 기준을 재현”한 단계다.

PR head `5c60fa4`의 백엔드 CI는 694개 중 682개 통과, 11개 실패, 1개 건너뜀이었다. 실패는 V2SecurityRedTest에 한정된다. 병합본부터는 이 11개가 `@Disabled`이므로, 이후 CI 결과를 이 수치와 같은 조건으로 비교하지 않는다. 일반 회귀 실패가 추가되면 의도적 실패 수에 섞지 않고 별도로 해결한다.

발표에서는 실패 개수보다 실패의 의미를 설명한다. 예를 들어 로그아웃 후 RT는 폐기되지만 AT는 계속 사용 가능하다는 차이를 보여준다.

## 5. V2 진행 순서

1. 세션 폐기 범위, RT 재사용 대응, 요청 제한 정책을 구체화한다.
2. 로그인 세션을 DB에 저장하고 AT를 세션에 연결한다.
3. 보호 API의 현재 세션·회원 상태 검증과 로그아웃을 연결한다.
4. 비밀번호 재설정·회원 정지·복구·탈퇴의 세션 폐기를 연결한다.
5. RT Rotation, 사용 기록, 동시 갱신 제어와 재사용 대응을 구현한다.
6. API 요청 제한과 브라우저 보안·권한 경계 검증을 추가한다.
7. 보안 및 회귀 테스트를 통과시킨 뒤 k6 기준선을 측정한다.

각 작업은 트리거, 기대 동작, 실패 시 롤백, 경합 시 결과, 테스트 근거를 묶어서 검토한다. 상세 내용은 [V2 계획](v2-plan.md)을 따른다.

## 6. V3 진행 순서

1. V2와 동일하게 유지할 보안 계약과 성능 시나리오를 고정한다.
2. 저장소 경계와 Redis 데이터 수명·키·원자적 연산을 설계한다.
3. 세션·RT를 전환하고 재사용·동시성·장애를 검증한다.
4. 요청 제한과 이메일 인증·복구 임시 상태를 전환한다.
5. DB와 Redis 간 계정 변경 동기화·재시작·유실을 검증한다.
6. 동일 환경에서 V2/V3를 측정한 후 개인 AWS 환경에서도 별도 측정한다.

인증 이외의 예약·결제 분산락, 일반 조회 캐시, 예약 상태 이전은 이 단계의 기본 범위에서 제외한다. 별도 병목 증거가 있으면 별도 작업으로 검토한다.

## 7. 측정과 발표 자료

필수 기록은 커밋 SHA, 환경 사양, 데이터량, 동시 사용자·요청률, 워밍업·측정 시간, p50/p95/p99, 처리량, 오류율과 상태 코드 분포다.

V2에서 DB 조회·잠금·커넥션 비용을, V3에서 Redis 호출·메모리·지연과 DB 잔여 비용을 함께 관찰한다. 빠르게 401·429를 반환한 결과가 높은 처리량으로 잡힌 경우 정상 서비스 처리량과 구분한다.

발표 흐름은 V1 한계 재현 → V2 DB 해결 → 비용 측정 → V3 Redis 전환 → 동일 보안 검증 → 성능·운영 비교다. Redis가 항상 더 빠를 것이라는 결론을 먼저 작성하지 않는다.
