# V3: Redis 인증 상태 전환 설계와 실험 경과

> 상태(2026-10-21 최종): **실험 구현으로 보존, dev 병합과 운영 도입 보류. 배포 환경은 V2(DB)를 유지한다.** 세션 검증(2번)과 RT 처리(3번)는 로컬 실험 브랜치 `auth/improvement/v3`에서 구현, 리뷰, 전체 백엔드 회귀(1,065개 통과)까지 마쳤고, 보호 API와 RT Rotation의 V2/V3 성능 비교도 실행했다. 로그인 요청 제한과 이메일 인증 임시 상태는 DB에 유지한다. 결과와 판단 근거는 [V3 인증 실험 결과](../../testing/auth-v3-experiment-results.md)에 있다. 이 문서의 §0은 구현 당시의 리뷰 상태, §1 이후는 설계 검토 기록이다.
> 이전 상태 줄(2026-10-21 회귀 직후): 세션 검증과 RT 처리는 구현, 관련 리뷰, 전체 회귀 완료. 코드 커밋 `cab2ad1`, `229517c`는 로컬에만 있음(미Push, 미병합, 미배포). 당시 실제 perf 앱 기동, smoke, V2/V3 성능 비교, 운영 Redis 복구 검증은 미실시. 최초 전체 회귀 46개 실패(구현 보고 기준) 뒤 테스트 6개 보완, 선택 실행 73개 통과(별도 기록).
> 선행조건: V2의 DB 기반 보안 동작과 측정 기준선  
> 기준: [V2 계획](v2-plan.md), [인증 정책](../../decisions/authentication-policy.md)  
> 기존 Redis 도입 범위·설계 문서의 논점을 V1 → V2 → V3 순서에 맞춰 재구성했다.

## 0. 진행 상태와 범위 (2026-10-20, 범위 확정 2026-10-21, 도입 보류 2026-10-21)

**최종 판단(2026-10-21)**: 보호 API 전체 응답 시간에서는 일관된 개선을 확인하지 못했고, RT Rotation에서는 p50 감소가 관찰됐다(p95 대표값도 낮았지만 반복 범위가 겹침). 세션 검증 단계만의 지연과 DB 자원 감소는 측정하지 않았다. 확인한 이득과 Redis 운영, 장애 복구의 복잡성을 고려해 V2 운영을 유지하고 V3 도입을 보류했다. 상세는 [V3 인증 실험 결과](../../testing/auth-v3-experiment-results.md). 아래 내용은 구현 당시 기록이다.

**선행 조건 상태**: V2(DB 세션, RT 회전, 로그인 요청 제한)는 PR #350으로 dev에 병합됐다(`4051bb3`, 2026-10-19). V2 k6 탐색은 보호 API, RT 회전, 로그인 제한 429 세 경로를 10, 50, 100 RPS로 실행했다고 보고됐고(리뷰어가 결과 파일을 직접 확인하지는 않음), 최종 반복 측정과 V3 비교가 남아 있다.

**V3 도입 목적(2026-10-21 확정)**: V2에서 즉시 세션 폐기와 회원 상태 반영을 위해 추가한 인증용 DB 접근 비용을 줄이는 것이다. Redis로 무상태성을 복원하는 것이 목적은 아니다.

**V3 범위(2026-10-21 확정)**: (1) 일반 보호 API의 로그인 세션 검증, (2) RT 상태 저장, Rotation, 재사용 탐지만 Redis로 처리한다. 로그인 요청 제한은 Redis 이전 범위에서 제외하고 V2의 DB 구현(`login_attempt_bucket`, 이메일별 UTC 15분 10회)과 기존 정책을 유지한다. 이메일 소문자 통일이나 가입, 로그인 식별 정책 변경도 하지 않는다. 제외 이유는 현재 확인된 병목 근거와 추가 변경 비용을 고려해 핵심 인증 경로에 집중하기 위해서다. Redis로 정확한 제한을 구현할 수 없어서 제외한 것이 아니다.

**성능 비교(2026-10-21 확정)**: V2/V3 성능 비교 대상은 보호 API `GET /api/v1/members/me`와 RT Rotation 두 경로뿐이다. 기존 로그인 제한 429 측정 기록은 역사적 결과로 보존하되 Redis 개선 효과 비교에서는 제외한다. V3에서도 refresh에는 DB 회원, 세션 잠금 조회가 남으므로 RT Rotation 비교는 DB 비용이 없어진 경로가 아니다. 기존 V2 탐색 결과는 보존한다. 최종 비교 반복 측정은 같은 날 V2, V3 각 3회씩 실행했다([V3 인증 실험 결과](../../testing/auth-v3-experiment-results.md) §5).

**이전 범위 기록(2026-10-20)**: 당시에는 로그인 세션, RT 상태, 사용 기록, 로그인 요청 제한을 Redis로 옮기기로 했다. 로그인 요청 제한은 2026-10-21에 제외됐다. 이메일 인증 임시 상태(Guard, Challenge, Grant)의 이전은 이번 V3 범위에서 **제외**하고 DB에 둔다(§2, §7은 참고 기록으로 남긴다). 단, 인증번호 최종 잠금에 따른 자동 정지 시 회원 전체 세션을 폐기하는 V2 연결은 V3의 세션 저장소에서도 그대로 유지한다.

**1번에서 확인한 것 (코드, XML)**

- `spring-boot-starter-data-redis`를 버전 지정 없이 추가해 Spring Boot 3.3.4 BOM이 Spring Data Redis, Lettuce 버전을 관리한다.
- `docker-compose.yml`의 `redis` 서비스: `redis:7.4.11-alpine`, 포트 `127.0.0.1:6379`(루프백만), `redis-cli ping` 헬스체크, `redis-data` 볼륨. 인증 없이 실행된다. MySQL, Kafka 서비스 정의는 바뀌지 않았다.
- `application.yml`: `spring.data.redis.host`, `port`, `connect-timeout`, `timeout`을 환경변수 자리표시자로 두고 기본값은 `localhost`, `6379`, `2s`, `2s`.
- 저장소 오인 등록 없음: 기존 저장소는 모두 `JpaRepository`를 상속하거나(`CreditBalanceRepository`는 `Repository<Member, Long>`이며 `Member`는 `@Entity`) JPA 엔티티를 다루므로, Spring Data 다중 모듈 판정에서 Redis 저장소로 배정되지 않는다(`@RedisHash` 없음). 기동 시 Redis 쪽 "저장소 배정 불가" 안내 로그가 날 수 있다.
- Lettuce는 첫 사용 때 연결하고, Actuator가 없어 Redis 헬스 체크도 없다. (1번 시점 기준) 인증 코드는 Redis를 쓰지 않으므로 Redis가 꺼져 있어도 기존 동작에는 영향이 없는 구조다(실행으로 확인하지는 않음).
- `RedisConnectionIntegrationTest`: 테스트 전용 Redis 컨테이너(`redis:7.4.11-alpine`)에 직접 연결해 저장, 조회, 만료(500ms TTL 후 키 소멸)를 확인한다. Spring Boot 자동 설정과 `application.yml` 값의 바인딩은 검증하지 않는다.

**한계, 주의**

- `redis-data` 볼륨은 컨테이너를 다시 만들 때 데이터 디렉터리를 유지할 뿐이다. 영속화 방식(RDB/AOF), 백업, 복구 절차는 정하지 않았고, 이를 데이터 복구 정책으로 보지 않는다(§9 장애, 유실 정책에서 결정).
- `SPRING_DATA_REDIS_USERNAME`, `PASSWORD`는 `application.yml`에 자리표시자가 없다. 운영체제 환경변수로 주면(예: EC2 서비스 환경 파일) Spring Boot의 환경변수 바인딩으로 적용되지만, `local` 프로필이 읽는 `backend/.env`에 적으면 일반 속성 이름으로만 들어가 적용되지 않는다. host, port, 타임아웃은 자리표시자가 있어 `.env`에서도 적용된다.

**2번 리뷰 상태 (2026-10-20 최종 리뷰 — 구현, 관련 검증, 리뷰 완료, 코드 커밋 `cab2ad1`)**

- 구조: 보호 요청은 JWT 서명, 만료 검증 후 Redis Lua 한 번(세션 해시의 회원 ID, generation, 만료 대조, 키 누락 시 거부)으로 인증하며 인증용 DB 조회가 없다. 키는 `slotkey:auth:v3:{namespace}:{member:id}:...` 형식이다. RT는 아직 DB에 있고 refresh 때 Redis 세션 유효성을 함께 확인한다.
- 관리자 직접 정지, 탈퇴, 비밀번호 재설정: 회원 행 잠금 아래 Redis generation을 먼저 교체한 뒤 DB 세션, RT를 폐기한다. Redis 실패는 503으로 그 트랜잭션을 롤백하고, Redis 교체 뒤 DB가 실패하면 세션은 무효인 채로 남는다(fail-closed).
- 인증 최종 잠금에 따른 자동 정지(확정 정책):
  1. 인증번호 확인 트랜잭션이 실패 누적, Guard 최종 잠금, challenge 무효화를 먼저 커밋한다. 잠긴 뒤에는 올바른 코드도 `ADMIN_LOCKED`로 거절된다.
  2. 별도 정지 트랜잭션이 Guard(전 목적) → 회원 순서로 잠그고, 최종 잠금이 남아 있고 회원이 `ACTIVE`일 때만 진행한다. 관리자 복구도 같은 순서로 잠그므로 복구와 겹쳐도 오래된 판단으로 다시 정지하지 않는다(C1 보완).
  3. 그 트랜잭션에서 회원 행 잠금 아래 DB의 활성 세션 ID를 모으고, DB 세션, RT 폐기, `SUSPENDED` 변경, 감사 로그, 세션별 Redis 차단 대기 행(`auth_session_revocation_retry`, V27)을 함께 커밋한다. 로그인도 회원 행을 잠그므로 정지 직전에 만들어진 세션도 목록에 포함되고, 정지 뒤 로그인은 거절된다.
  4. 커밋 뒤 같은 요청에서 기록된 namespace의 해당 세션 키만 Redis에서 삭제한다. 회원 generation은 바꾸지 않는다. 실패하면 대기 행이 남고, 스케줄러(기본 5초 간격, 1회 100건)가 계속 재시도한다. Redis 차단이 끝나기 전까지 기존 AT가 보호 요청에 쓰일 수 있는 지연은 정책상 허용한다. refresh와 로그인은 DB 상태로 거절된다.
  5. 같은 행을 여러 인스턴스가 동시에 처리하거나, Redis 삭제 뒤 완료 기록이 실패해도 같은 키 삭제를 반복할 뿐이라 안전하다. 완료, 재예약은 `PENDING`일 때만 갱신한다.
- 출입 거절 감사 로그: Redis가 `INVALID`로 거절한 `POST /api/v1/door-access/verify` 요청에서만 JWT의 회원 ID, sid로 DB 회원 상태를 조회해 비활성일 때 `MEMBER_INACTIVE` 로그를 남긴다(`REQUIRES_NEW`). 응답은 항상 401이고, Redis 장애 503 요청과 다른 경로는 조회하지 않으며, 로그 저장 실패도 401을 유지한다.
- namespace: `local` 기본값 `local`, `perf` 기본값 `perf`, `prod`는 `AUTH_REDIS_NAMESPACE` 필수. perf 실행기는 값을 검증해 전달하고 `APP_AUTH_REDIS_NAMESPACE`를 지운다. 재시도 스케줄러는 `test` 프로필에서만 꺼져 있다.
- **알려진 한계**
  - (2026-10-21 회귀 보완에서 확인) 보호 요청이 DB 회원 상태를 읽지 않으므로, 서비스(`AdminMemberService.suspend`, 탈퇴, 비밀번호 재설정, 인증 최종 잠금)를 거치지 않고 DB의 `member.status`만 직접 바꾸면 기존 AT는 차단되지 않는다. refresh와 로그인은 DB 상태로 거절된다. 운영에서 상태를 바꿀 때는 서비스 경로를 써야 한다. 관리자 계정은 정지, 탈퇴 대상이 아니므로 "비활성 ADMIN의 기존 AT" 시나리오는 서비스 경로로 만들 수 없다.
  - 완료된 재시도 행을 정리하는 작업이 없어 행이 계속 쌓인다.
  - Guard 최종 잠금은 커밋됐지만 이어지는 정지 DB 트랜잭션 자체가 실패하면, 정지와 대기 행이 남지 않아 스케줄러가 복구하지 않는다. 같은 이메일로 인증 확인 요청이 다시 오면 정지를 다시 시도한다. 이번 Redis 차단 재시도는 "정지가 DB에 커밋된 뒤의 Redis 실패"를 다루는 범위이므로 이 한계가 그 완료 판단을 바꾸지는 않는다.
  - 정지 트랜잭션의 커밋 응답 자체가 실패하면 실제 커밋 여부를 응답만으로 알 수 없다. 오류 응답을 롤백으로 간주하지 않는다.
- **3번(RT 이전) 이월 사항** (3번 리뷰에서 충족 확인 — 아래 "3번 리뷰 상태"): 자동 정지 대상 세션 ID를 DB `auth_session`의 활성 행에서 모은다. 3번에서 세션, RT 기록 방식이 바뀌어 DB에 활성 세션이 남지 않거나 만료, 폐기 값이 Redis와 달라지면 차단 대상을 놓칠 수 있다. 3번에서 같은 회원 잠금 아래 세션 ID를 빠짐없이 얻는 방법을 유지하거나 다시 설계해야 한다.
- 배포 영향(도입했다면 필요했던 준비, 2026-10-21 도입 보류로 진행하지 않음): 운영 Redis, `AUTH_REDIS_NAMESPACE`, V27 적용. 전환 시 기존 DB 세션에는 Redis 키가 없으므로 모든 사용자가 다시 로그인해야 한다.
- 검증 범위: 관련 9개 클래스 63개 통과([테스트 결과](../../testing/test-results.md)). 2번 변경 뒤 전체 백엔드 회귀, 실제 `local`, `perf`, `prod` 프로필 앱 기동, 운영 Redis 장애, 복구 검증은 하지 않았다.
**3번 리뷰 상태 (2026-10-20 — 구현, 관련 검증, 리뷰 완료, 코드 커밋 `229517c` 로컬)**

- RT 형식: `v3.<memberId>.<sid>.<난수 32바이트 Base64URL>`. 회원 ID, sid는 조회 힌트일 뿐이며, 서버는 원문 SHA-256 해시가 그 세션의 Redis RT 이력에 있는지 확인한 뒤에만 갱신, 로그아웃을 처리한다. 형식이 맞지 않으면 refresh는 401, logout은 구형 DB RT 경로로만 조회하며 원문은 로그에 남기지 않는다.
- 남는 데이터:
  - Redis: 세션 해시(`...:session:{sid}`)와 RT 이력 해시(`...:session:{sid}:refresh` — `currentHash`, `rt:{해시}` = `ACTIVE`/`CONSUMED`). 두 키 모두 세션 절대 만료 시각에 `PEXPIREAT`로 만료되고 회전해도 연장되지 않는다.
  - DB: 로그인마다 `auth_session` 행은 계속 만든다(자동 정지 sid 수집, 로그아웃, 재사용 폐기 기록용). 새 RT는 `refresh_token` 행을 만들지 않는다. 기존 `refresh_token` 행은 구형 RT 로그아웃 식별에만 쓰인다.
- refresh: 회원 → 세션 순서로 DB 행을 잠그고, 세션 소유, DB 세션 유효, 회원 상태를 확인한 뒤 Redis Lua 한 번으로 세션, generation, 회원 ID, 만료와 RT 이력을 대조하고 회전한다. **정상 refresh에도 DB 회원, 세션 잠금 조회는 남는다.** 성공 시 쓰기는 마지막 `HSET` 한 명령(구 RT `CONSUMED`, 새 RT `ACTIVE`, `currentHash`)이라 부분 회전이 남지 않는다.
- 재사용: `CONSUMED`(또는 현재 해시가 아닌) RT가 오면 Lua가 그 세션 키를 삭제하고, DB 세션 폐기를 커밋한 뒤 401을 반환한다. 그 세션의 기존 AT와 최신 RT가 함께 거부되고 다른 세션은 유지된다. 이력에 없는 해시는 세션을 건드리지 않고 401만 반환한다(타인 세션 삭제 불가).
- logout: 쿠키 RT 해시가 그 세션 이력에 있을 때만 세션 키를 삭제하고 DB 세션을 폐기한다. 구형 RT는 refresh가 거부되고, logout은 DB 해시 조회로만 기존 세션을 폐기한다.
- 계정 사건: 정지, 탈퇴, 재설정은 generation 교체로, 자동 정지는 DB 활성 `auth_session`에서 모은 sid 삭제로 차단한다. 로그인이 DB 세션 행을 계속 만들고 Redis 쪽 삭제가 DB 폐기보다 먼저이므로, Redis에서 살아 있는 세션은 DB에서도 활성으로 남아 수집 대상에서 빠지지 않는다.
- 전환: 기존 DB RT는 갱신할 수 없으므로 V3 배포 시 모든 사용자가 다시 로그인해야 한다(2번 세션 전환과 같은 시점).
- **알려진 한계**
  - 회전이 Redis에 반영된 뒤 응답이 유실되면 클라이언트는 옛 RT로 다시 시도하고, 이것이 재사용으로 판정돼 세션이 폐기된다(재로그인 필요). DB 커밋 실패도 같은 결과다.
  - RT 이력 키만 사라지면 그 세션의 RT는 401이 되고 재사용 탐지도 할 수 없다. 이력을 다시 만들지 않으며, 세션 키는 절대 만료까지 남아 기존 AT(최대 5분)만 쓸 수 있다.
  - 과거 Redis 스냅샷을 복원하면 그 뒤 소비된 RT가 다시 `ACTIVE`로 보일 수 있다. 복원 시에는 트래픽을 멈추고 새 namespace로 전환해야 한다(전원 재로그인).
  - 로그인 등록 Lua가 중간 명령에서 런타임 오류를 내면 앞선 쓰기가 남을 수 있다(TTL 없는 키 등). 로그인 트랜잭션은 롤백되고 토큰은 발급되지 않아 인증 우회는 아니지만 고아 키가 남을 수 있다.
- 검증 범위: 관련 7개 클래스 최신 선택 실행 63개 통과(단일 전체 실행 아님, [테스트 결과](../../testing/test-results.md)). 전체 백엔드 회귀와 운영 Redis 장애, 복구 검증은 하지 않았다.

- 유지하는 한계: RT 쿠키 없이 로그아웃하면 기존처럼 204만 반환하고 서버 세션은 폐기되지 않는다(AT는 만료까지 유효). V2와 같은 동작이며 V3에서도 바꾸지 않았다. **사용자 재검토 항목**으로 남긴다(V3 도입 보류와 무관하게 V2 운영에도 해당).

**팀원 로컬 실행 (V3 실험 브랜치 기준, dev에는 Redis 서비스가 없다)**

```bash
cd backend
docker compose up -d redis      # 127.0.0.1:6379, 인증 없음
docker compose ps redis         # health 상태 확인
```

추가 설정 없이 `application.yml` 기본값(`localhost:6379`)으로 연결된다. 다른 Redis를 쓸 때만 `SPRING_DATA_REDIS_HOST`, `PORT`(필요하면 타임아웃)를 지정한다. 자동 테스트는 이 컨테이너가 아니라 Testcontainers로 별도 Redis를 띄운다(Docker 필요).

## 1. 목적

V3의 목적은 V2에서 즉시 세션 폐기와 회원 상태 반영을 위해 추가한 인증용 DB 접근 비용을 줄이는 것이다. Redis로 무상태성을 복원하는 것이 목적은 아니다. V2와 같은 보안 요구사항을 유지하면서 (1) 일반 보호 API의 로그인 세션 검증, (2) RT 상태 저장, Rotation, 재사용 탐지를 Redis로 처리하고, V2의 DB 조회, 잠금 비용과 V3의 Redis 호출, 메모리, 동기화 비용을 비교한다(2026-10-21 확정). 실제 측정은 API 전체 응답 시간만 비교했고 DB와 Redis 자원 지표는 수집하지 않았다([V3 인증 실험 결과](../../testing/auth-v3-experiment-results.md) §6).

> 2026-10-15 초안 당시 문구: “수명이 제한된 인증 상태의 저장과 동시 처리를 Redis로 전환하는 것이다.” 아래 §3~§10의 키 구조와 알고리즘은 초안 단계의 후보이며, 실제 구현은 §0의 2번, 3번 리뷰 상태를 따른다. 성능 비교 결과는 [V3 인증 실험 결과](../../testing/auth-v3-experiment-results.md)에 있다.

## 2. 이전 범위와 유지 범위

| 데이터 | V3 방향 | 주의점 |
| --- | --- | --- |
| 활성 로그인 세션 | Redis 이전 대상 | 세션 누락을 인증 성공으로 해석하지 않음 |
| RT 현재 상태·사용 기록 | Redis 이전 대상 | 재사용 탐지 기록 보존 |
| API 제한 상태(로그인 요청 제한) | **이번 V3 범위 제외(V2 DB 구현 유지, 2026-10-21 결정)** | 아래 §6은 참고 기록 |
| 인증 Challenge, Grant | **이번 V3 범위 제외(DB 유지, 2026-10-20 결정)** | 아래 §7은 향후 검토용 기록 |
| 인증 Guard | **이번 V3 범위 제외(DB 유지, 2026-10-20 결정)** | 최종 잠금 시 세션 전체 폐기 연결은 V3 세션 저장소에서도 유지 |
| Member·LocalCredential | DB 유지 | 회원·자격 증명 원본 |
| 감사·업무 기록 | DB 등 영속 저장 유지 | 보존 및 조회 정책 |
| 예약·결제·크레딧 | 기존 DB 중심 유지 | 인증 개선과 별도 범위 |

Redis를 사용한다는 이유로 모든 상태에 짧은 TTL을 설정하지 않는다. 최종 관리자 잠금은 단순한 3분 코드와 다르며, TTL 만료나 데이터 유실로 해제되면 정책 위반이다.

예약·결제 분산락, 일반 조회 캐시, 예약 상태 전이는 기본 범위에서 제외한다. 기존 DB 동시성 장치를 대체할 근거가 필요하다.

## 3. 저장소 경계

인증 정책과 저장 기술이 강하게 결합되지 않도록 세션 조회·폐기, RT 교체, 요청 제한 판정을 명시적인 작업 단위로 분리하는 방안을 검토한다.

DB의 엔티티 CRUD를 그대로 Redis 명령으로 치환하는 것만으로는 충분하지 않다. “유효성 검사와 RT 교체”, “횟수 검사와 증가”처럼 함께 원자적으로 수행되어야 하는 경계를 인터페이스 수준에서 표현한다.

V2와 V3에 같은 외부 시나리오를 적용하되 DB 내부 조회에 결합된 테스트는 저장소 구현 테스트와 분리한다. 공개 API의 보안 의미를 유지하는 것이 기준이다.

## 4. 로그인 세션과 AT

V2에서 sid 기반 세션을 선택했다면 V3에서도 같은 식별 의미를 유지한다. 보호 API는 JWT 검증 후 Redis의 활성 세션과 필요한 회원 보안 정보를 확인한다.

### 키 후보

| 키 후보 | 값 | 수명 기준 |
| --- | --- | --- |
| auth:session:{sid} | 회원 연결·생성·만료·폐기 상태 | 세션 절대 수명과 정리 정책 |
| auth:member-sessions:{memberId} | 회원의 세션 식별자 목록 | 세션 정리와 일관성 유지 |
| auth:refresh:{hash} | sid·상태·만료·사용 기록 | 계열 유효 기간·탐지 보존 |
| auth:member:{memberId} | 상태·역할·보안 버전 후보 | 누락·동기화 정책 별도 |
| auth:limit:{scope}:{key} | 요청 제한 상태 — 이번 V3 범위 제외(2026-10-21) | 윈도, 버킷 정책 |

위 표는 개념적 후보다. Redis Cluster에서 여러 키를 한 원자 연산에 묶으려면 실제 hash tag와 슬롯 배치를 별도로 설계한다. 원문 토큰·이메일을 그대로 키에 넣는 방식은 피하고 식별자 또는 키용 보호값을 검토한다.

### sid와 jti 선택

과거 설계에는 jti별 AT denylist가 있었다. 하지만 토큰 하나를 차단하는 것과 한 로그인 세션에서 발급한 모든 AT를 차단하는 것은 다르다.

V2가 sid 기반으로 완성되면 이를 V3로 옮기는 것을 우선 검토한다. 별도 jti denylist는 개별 AT만 폐기해야 하는 요구가 있을 때 도입한다. 두 방법을 이유 없이 중첩하지 않는다.

## 5. RT Rotation의 원자성

유효한 현재 RT인지 검사하고, USED로 전환하고, 새 토큰 기록과 현재 포인터를 등록하는 절차는 하나의 원자적 작업으로 묶는다. Lua 등의 방식은 선택 후보이며 실제 키 구조와 함께 검토한다.

원자적 Redis 연산이 DB 회원 상태 변경까지 자동으로 포함하지는 않는다. 회원 정지와 refresh가 경합할 때, 정지 완료 후에도 새 토큰이 유효하게 남지 않는 조건을 별도로 설계해야 한다.

재사용 토큰의 기록은 바로 삭제하지 않는다. 현재 토큰만 남기면 알 수 없는 값과 이미 쓴 값을 구분하기 어려워진다. 보존 수명은 계열 수명과 탐지 요구에 맞춘다.

같은 RT 동시 제출 시 한 번만 갱신 성공한다는 V2 기준을 유지한다. 재사용 탐지 후 family/sid 폐기 범위, 응답 유실·다중 탭 처리도 V2와 같은 정책을 사용한다.

## 6. 요청 제한 (이번 V3 범위 제외 — 참고 기록)

> 2026-10-21: 로그인 요청 제한은 Redis로 옮기지 않고 V2 DB 구현과 정책을 유지한다(§0). 아래는 초안 단계의 검토 기록이다.

V2와 동일한 정책을 Redis의 원자적 처리로 구현한다. 예를 들어 이동 윈도 로그를 선택했다면 오래된 기록 제거·현재 개수 확인·새 요청 기록·TTL 설정을 하나의 작업으로 처리한다.

정책을 유지하려면 다음 항목이 같아야 한다.

- 어떤 요청을 세는가: 전체 요청인지, 실패 요청인지.
- 키: IP·정규화 이메일·세션 등 어떤 범위인가.
- 허용 횟수, 시간 창, burst, 재허용 시점.
- 응답 상태와 재시도 안내.
- 서버 간 시간 기준과 창 경계 처리.

V2 고정 윈도와 V3 이동 윈도를 비교하면 저장소와 알고리즘 변화가 섞인다. 알고리즘 개선을 하려면 별도 실험으로 구분한다.

키 개수와 메모리 사용량, 정리 비용을 관찰한다. 랜덤 이메일 요청으로 제한 키가 과도하게 늘어나는 경우도 검토한다.

## 7. 이메일 인증 임시 상태의 이전 (이번 V3 범위 제외 — 참고 기록)

Challenge의 번호 수명, Grant의 수명·단일 사용, Guard의 누적 실패·차단을 V1 정책 그대로 유지한다. 기존 DB 잠금이 보호하던 발급·검증·소비의 경계를 Redis 원자 연산으로 다시 표현한다.

### 7.1 Guard의 수명

일시 차단이 끝났다고 blockStage까지 사라지면 사용자가 반복해서 1차 차단만 받게 된다. 최종 adminLocked가 키 삭제로 해제되어서도 안 된다.

장기 보안 상태를 DB에 영속 유지할지, Redis 영속성 및 복구 절차로 관리할지 결정한다. 이전 대상이라는 방향과 모든 Guard 데이터를 휘발 상태로 둔다는 결정은 다르다.

### 7.2 Grant 소비와 DB 업무의 원자성

V1·V2에서는 DB 트랜잭션 하나로 가입·비밀번호 변경과 grant 소비를 묶을 수 있다. grant를 Redis로 옮기면 이 보장이 그대로 유지되지 않는다.

| 순서 | 발생 가능한 문제 |
| --- | --- |
| Redis에서 먼저 소비 → DB 변경 | DB 실패 시 유효 grant가 사라져 재시도 불가 |
| DB 변경 → Redis 소비 | 소비 실패·경합으로 동일 grant 재사용 가능 |
| Redis 사용 예약 → DB 변경 → 확정 | 예약 유실·타임아웃·복구·중복 재시도 정책 필요 |

후보는 DB에 최종 소비·멱등 처리 영수증을 남기는 방식, 사용 예약과 복구 상태를 두는 방식, 최종 grant 소비만 DB에 유지하는 방식이다. 마지막 후보를 택하면 Redis 이전 범위의 변경을 명시해야 한다.

어떤 방식을 선택해도 “업무 실패 시 재시도 가능, 성공 후 재사용 불가”라는 외부 의미를 검증한다. Redis TTL만으로 이 문제를 해결했다고 설명하지 않는다.

## 8. DB 회원 상태와 Redis의 일관성

DB의 회원 상태 변경과 Redis의 세션 폐기는 하나의 로컬 트랜잭션이 아니다. DB 정지는 성공했지만 Redis의 기존 세션이 활성인 경우, Redis만 읽는 인증 경로가 잘못 허용할 수 있다.

결정해야 할 사항은 다음과 같다.

1. 정지·재설정 API가 언제 폐기 완료를 응답하는가.
2. Redis 반영 실패 시 요청을 실패·대기·복구 중 무엇으로 처리하는가.
3. 오래된 인증 상태가 남은 구간의 보호 요청을 어떻게 거부하는가.
4. 재시도 기록과 중복 처리·보상 절차는 어디에 보관하는가.

outbox나 재시도는 변경 전달을 복구하는 후보다. 재시도가 있다는 사실만으로 반영 전 구간의 즉시 차단이 보장되지는 않는다. Kafka 도입을 이 문제의 필수 조건으로 삼지 않는다.

DB authVersion과 Redis의 현재 버전을 사용하는 안도 후보다. 복구 때 버전을 되돌리지 않으며, Redis의 버전이 오래됐을 때 감지·차단하는 경로가 필요하다.

## 9. 장애·유실 정책

확정 방향은 “인증 판정이 불가능한 보호 요청은 허용하지 않는다”이다. 최종 HTTP 오류 계약은 구현 시 정한다.

| 상황 | 처리 방향 |
| --- | --- |
| 서명 오류·만료·폐기 인증 | 인증 거부 |
| Redis 접속 불가·타임아웃 | 인증 조회 우회 금지, 503 등 장애 응답 구분 |
| 활성 세션 키 부재 | 성공으로 해석하지 않음 |
| 재시작 후 저장 데이터 유실 | 재로그인 또는 명시적 복구 경로 |
| 폐기 기록만 유실 | 이전 토큰이 다시 유효해지지 않도록 세대·활성 세션 정책 |
| 메모리 부족·쓰기 실패 | 폐기·교체 성공으로 응답하지 않음 |
| DB에는 있으나 Redis에는 폐기된 RT | 무조건 DB fallback으로 재허용하지 않음 |

denylist만 쓰면 키 부재가 “폐기되지 않음”인지 “폐기 기록 유실”인지 구분되지 않는다. 활성 세션 존재를 요구하는 방식은 유실 시 거부하도록 설계할 수 있지만 가용성 비용을 갖는다.

접속 실패에 대한 fail-closed만으로 정상 접속되는 Redis의 오래된 데이터까지 감지할 수 있는 것은 아니다. 동기화 검증과 장애 처리를 구분한다.

## 10. 전환 전략

간단한 프로젝트 전환 후보는 배포 시 기존 세션·RT·미완료 인증을 무효화하고 재로그인·재인증을 요구하는 방식이다. 사용자 영향은 있지만 두 저장소 간 이중 검증의 복잡도가 줄어든다.

무중단 이전을 선택하면 토큰 버전별 검증 원본, 전환 기간, 폐기 이벤트 전달, 전환 종료와 롤백을 설계한다. DB 또는 Redis 중 어느 한쪽에서 유효하면 통과시키는 정책은 사용하지 않는다.

전환 방식은 확정하지 않았다. 2026-10-21에 운영 도입을 보류했으므로 전환 절차는 다시 도입을 검토할 때 결정한다.

## 11. 성능 비교 실험 설계

| 통제 항목 | 기록 내용 |
| --- | --- |
| 코드 | V2·V3 정확한 SHA |
| 정책 | 토큰 수명·제한 알고리즘·폐기 의미 |
| 환경 | 앱 인스턴스 수·CPU·메모리, DB·Redis 사양, 네트워크 |
| 부하 | 동일 스크립트, 사용자·세션 수, 요청률, 데이터 규모 |
| 실행 | 워밍업·측정 시간, 반복 횟수, 실행 순서 |
| 관측 | p50/p95/p99, 처리량, 오류율, 2xx/401/429/5xx |
| 저장소 | DB 쿼리·연결·잠금 대기, Redis 호출 지연·메모리 |

**2026-10-21 확정**: V2/V3 성능 비교 대상은 보호 API `GET /api/v1/members/me`와 RT Rotation 두 경로뿐이다. 기존 로그인 제한 429 측정 기록은 역사적 결과로 보존하되 Redis 개선 효과 비교에서는 제외한다. V3에서도 refresh에는 DB 회원, 세션 잠금 조회가 남으므로 RT Rotation 비교는 DB 비용이 없어진 경로가 아니다. 같은 RT 경합, 재사용 거부는 보안 동작 확인용이며 성능 비교 수치에 넣지 않는다.

> 초안 당시 문구: 시나리오는 보호 API 반복, 정상 RT 갱신, 같은 RT 경합, 로그인, 인증 요청 제한, 이메일 인증 작업으로 나눈다. 메일 외부 전송 비용은 포함 여부를 명확히 하여 저장소 비교를 왜곡하지 않도록 한다.

성능은 기대값을 결과처럼 적지 않는다. 같은 보안을 유지했는지 먼저 확인하고, 개선 폭·변동 폭·병목 이동·운영 복잡도를 함께 보고한다.

**실행 결과(2026-10-21)**: 위 통제 항목 중 저장소 지표(DB 쿼리, 연결, 잠금 대기, Redis 호출 지연, 메모리)와 실행 순서 통제는 충족하지 못했다. V2 6회 뒤 V3 6회(추가 protect 1회 별도)를 같은 로컬 Mac에서 실행했다. 결과와 한계는 [V3 인증 실험 결과](../../testing/auth-v3-experiment-results.md) §5, §6.

## 12. AWS 검증

개인 AWS 환경에서 앱, MySQL, Redis 연결과 네트워크, 보안 설정을 직접 구성하고 측정하는 것이 후속 목표였다. 2026-10-21 V3 도입 보류로 현재 계획에 없다. 구체적인 서비스, 사양, 비용은 배포 시점에 확인한다.

로컬 Docker Redis 테스트와 관리형 Redis 운영은 별도 경험이다. 재시작·장애·백업·연결 풀·비밀값·관측 지표를 검증한다. 현재 팀 배포 상태와 개인 실습 계획을 혼동하지 않는다.
