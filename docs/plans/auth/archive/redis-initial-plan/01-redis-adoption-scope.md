## 1. 배경: 기술 적용에서 해결할 문제 중심으로

초기 목표는 SlotKey에 Redis를 도입하는 것이었다. 예약·결제의 동시 요청 제어, 예약 상태 전이, 조회 캐시 등 여러 활용처를 검토했다.

그러나 Redis를 추가할 수 있다는 사실만으로 도입 필요성이 생기지는 않는다. 기존 DB 설계가 이미 담당하는 책임을 중복 구현하면 네트워크 왕복, 장애 처리, 데이터 동기화 및 운영 비용이 증가할 수 있다. 성능 향상 여부도 측정 없이 단정할 수 없다.

따라서 작업의 목표를 **Redis 도입 계획에서 인증·인가 고도화 계획으로 변경한다.** Redis는 목표를 달성하는 수단으로 사용한다. 토큰 폐기, 재발급 상태 관리, 인증 API 요청 제한처럼 필요한 곳에 우선 적용하고, 소셜 로그인과 객체 수준 인가 점검은 Redis와 별개로 함께 진행한다.

## 2. 현재 코드에서 확인한 사실

확인 기준은 업로드된 `backend.zip`의 Java 소스 및 DB 마이그레이션이다. 최신 Kotlin 브랜치와 운영 DB를 실행·검증한 결과는 아니므로 착수 시 차이를 확인한다. 아래 경로는 `src/main/java/com/ovengers/slotkey/` 기준이다.

| 영역 | 확인한 동작 | 근거 |
| --- | --- | --- |
| 일반 요청 인증 | JWT 검증 후 SecurityContext 구성, 회원 DB 조회 없음 | `global/security/CustomAuthenticationFilter.java` |
| Access Token | 회원 id·email·role을 담아 발급, 발급 코드에 jti 없음 | `global/security/jwt/JwtProvider.java` |
| Refresh Token | UUID 원문 발급, SHA-256 해시를 DB에 저장, 만료·폐기·회원 상태 검사 | `auth/service/RefreshTokenService.java` |
| 재발급 | Refresh Token 검증 후 새 Access Token만 발급, Refresh 회전 없음 | `auth/service/AuthService.java` |
| 로그아웃 | Refresh Token 폐기와 쿠키 삭제, 기존 Access Token 즉시 무효화 미지원 | `auth/controller/AuthController.java` |
| 객체 수준 인가 | 예약 상세·취소·결제 확정·연장에 예약 소유자 비교 존재 | `reservation/service/ReservationQueryService.java` 등 |
| 쿠키 및 CSRF | Refresh는 HttpOnly 쿠키, Secure·SameSite는 설정값 사용. SecurityConfig는 CSRF 비활성화 | `auth/controller/AuthController.java`, `global/config/SecurityConfig.java` |

**객체 수준 인가가 전혀 없다는 전제는 사실과 다르다.** 기존 검사를 유지하고 다른 경로의 누락 여부와 테스트를 보강한다.

## 3. Redis 활용 후보와 현재 판단

### 3.1 예약·결제의 분산 락: 이번 범위에서는 보류

원래 의도는 같은 예약·결제에 동시 요청이 들어올 때 Redis 락으로 진입을 직렬화해 정합성을 유지하는 것이었다.

현재는 다음 DB 중심 방어 장치가 있다.

| 보호 대상 | 현재 확인한 방어 장치 |
| --- | --- |
| 동일 공간·시간 슬롯의 중복 점유 | `V3__create_reservation_tables.sql`의 `UNIQUE(space_id, slot_start)` |
| 잔액 부족 상태의 차감 | `CreditBalanceRepository.decreaseIfEnough()`의 잔액 조건부 UPDATE |
| 결제 확정 가능 여부 | `ReservationPaymentConfirmService.confirm()`의 조건부 상태 변경 |
| 관련 변경의 함께 성공·실패 | 트랜잭션, 필요한 DB 잠금, 실패 시 롤백 |
| 동일 결제 요청 재시도 | 결제 확정 경로의 멱등 기록 조회·저장 |

**UNIQUE 하나가 결제 정합성 전체를 보장하는 것은 아니다.** 서로 다른 보호 장치를 조합한 구조이다. 마이그레이션에 제약이 있더라도 실제 운영 스키마에 적용됐는지는 별도로 확인한다.

현재 DB 경합이 병목이라는 측정 근거 없이 Redis 락을 추가하면 추가 왕복과 락 만료·소유권·장애 처리만 늘어날 수 있다. Redis 락을 사용하더라도 DB 제약과 최종 상태 검사는 유지해야 한다. 분산 락은 모든 요청의 성공이나 공정한 순서도 자동 보장하지 않는다.

재검토 조건은 DB 락 대기·커넥션 대기·충돌률·p95/p99 지연이 실제 문제로 측정되고, 기존 트랜잭션 개선으로 해결하기 어려운 경우다.

### 3.2 예약 상태 전이·HOLD 만료 보조: 보류

현재 상태 전이는 DB의 예약·잔액·슬롯·이력과 연결되어 있다. 상태만 Redis로 옮기면 DB와 Redis 사이의 부분 성공을 복구해야 한다.

Redis Sorted Set으로 만료 예정 예약을 관리하고 DB에서 최종 판정하는 보조 방식은 가능하다. 그러나 등록 실패, 작업자 중단, 재시도, 처리 누락 보정까지 추가된다. Redis 키 만료만으로 DB 상태가 자동 변경되는 것도 아니다.

현재는 만료 처리 지연이나 대상 검색 비용이 문제라는 증거가 부족하므로 보류한다. 기존 스케줄러의 조회 주기·쿼리·인덱스를 먼저 점검한다. 단순히 조회 주기를 줄여 얻은 개선을 Redis의 효과로 설명하지 않는다.

### 3.3 공간 목록·상세 캐시: 측정 전 보류

공간 정보의 반복 조회 결과를 여러 사용자가 재사용한다면 효과가 있을 수 있다. 다만 검색 조건·페이지·정렬별 키 증가, 가격·이미지·상태 수정 시 무효화, 캐시 미스와 장애 시 DB 집중 부하를 관리해야 한다.

먼저 JPA가 실행한 SQL과 호출 횟수, 실행 계획을 확인한다. SQL·인덱스 개선 후에도 반복 조회 비용이 높고 적중률을 확보할 수 있을 때 도입을 재검토한다. 날짜·시간별 슬롯 가용성은 예약 변경 및 시간 경과로 달라지므로 특히 신중히 다룬다.

### 3.4 추가로 검토했으나 우선 도입하지 않는 기능

아래는 추가 검토 후보이며, 모두 기존 구현의 문제를 확인했다는 뜻은 아니다.

| 후보 | 현재 보류 이유 | 재검토 조건 |
| --- | --- | --- |
| 잔액·결제 상태의 Redis 저장 | DB 원장·예약·이력과 정합성을 맞추는 비용이 큼 | 별도 원장 구조와 복구 설계가 필요한 명확한 규모·요구 |
| 결제 멱등 응답 캐시 | DB 멱등 기록이 있고 반복 재시도 비중·조회 비용을 측정하지 않음 | 재시도 부하가 유의미하며 DB 기록을 유지하는 보조 캐시의 효과 확인 |
| 모든 API에 공통 캐시 | 사용자별 데이터 격리와 무효화 정책이 다름 | 안전한 응답과 키 범위를 API별로 정의한 경우 |
| Pub/Sub 예약 상태 알림 | 실시간 알림 요구가 미확정이며 단순 Pub/Sub는 유실 복구용 큐가 아님 | 실시간 UX 요구 및 재연결·재조회 설계 확정 |
| 인기 공간 순위·방문 집계 | 현재 인증 보완 목표와 직접 관련 없고 제품 요구가 미확정 | 순위 기준·사용 목적·보관 정책 합의 |

## 4. 인증·인가에 우선 도입하는 이유

해결할 요구가 구체적이다.

- 로그아웃 후 유효기간이 남은 Access Token의 재사용을 차단한다.
- 계정 정지·탈퇴·전체 로그아웃 시 기존 인증을 무효화한다.
- Refresh Token 회전과 재사용 탐지에 필요한 단기 상태를 관리한다.
- 여러 서버가 로그인·재발급 요청 횟수 제한을 공유한다.

Redis의 키 조회, TTL, 원자적 연산은 이 요구에 적합하다. 일반 보호 요청마다 관계형 DB를 추가 조회하지 않으면서 보안 상태를 검사할 수 있다. 다만 기존 JWT 단독 검증보다 Redis 조회 비용과 의존성은 증가한다.

이 기능은 DB나 다른 저장소로도 구현할 수 있다. Redis를 유일한 해결책이라고 주장하지 않으며, 현재 목표와 만료성 데이터의 특성을 고려한 선택으로 설명한다. Refresh 회전도 저장소를 Redis로 옮기는 것만으로 완성되지 않는다.

## 5. 결과를 설명하는 기준

- **보안 성과:** 기존 토큰 차단, 재사용 탐지, 권한 검사, 요청 제한의 성공 여부
- **비용:** 인증 p50/p95/p99, 오류율, Redis 메모리·지연, 장애 복구 동작
- **별도 성능 과제:** Kotlin 기준선에서 JPA·SQL 개선 전후 비교, 필요 시 캐시 효과 추가 비교

“Redis를 도입해서 빨라졌다”를 미리 결론 내리지 않는다. 기존보다 어떤 공격·오용 시나리오에 대응할 수 있게 됐으며 그 비용이 얼마인지 제시한다.

## 6. REST 무상태성 관련 설명

REST의 무상태성은 DB나 캐시의 존재를 금지하는 규칙이 아니다. 각 요청은 처리에 필요한 정보를 포함하고, 서버가 이전 대화의 진행 맥락에 의존하지 않아야 한다.

본 제안은 요청마다 JWT를 전달하고 폐기 정책을 검사한다. 서버에 인증 상태를 저장하므로 “완전히 서버 상태가 없는 JWT 인증”이라고 부르지는 않는다. 즉시 폐기 능력과 저장소 의존성 사이의 선택을 명시한다. `SessionCreationPolicy.STATELESS`만으로 시스템 전체의 REST 준수를 증명할 수도 없다.
