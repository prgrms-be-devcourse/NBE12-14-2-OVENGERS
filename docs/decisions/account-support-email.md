# 이용 제한 안내에 고객지원 이메일 제공

## 한 줄 요약

계정·이메일 인증 정지 안내에 공개 고객지원 이메일을 표시해, 로그인 권한을 완화하지 않고 문의 경로를 제공한다.

## 1. 문제와 배경

- 정지 회원은 로그인할 수 없지만 기존 문의 작성 API는 로그인이 필요하다. 안내 문구의 “관리자에게 문의”를 실행할 연락처가 없다.
- 사용자는 별도 문의창 없이 `anton061311@gmail.com`을 공개 고객지원 연락처로 사용하고 프론트 수정 PR을 만들도록 요청했다.
- 공통 인증 검사와 출입 차단 동작은 이번 변경 범위가 아니다.

## 2. 선택과 이유

- 기존 `ErrorMessage`에서 `ACCOUNT_INACTIVE`, `MEMBER_SUSPENDED`, `MEMBER_NOT_ACTIVE`, `VERIFICATION_ADMIN_LOCKED`에만 이메일 주소와 `mailto:` 링크를 표시한다.
- 서버가 명시한 제한 사유에 대응한다. 일반 401이나 `INVALID_ACCESS_TOKEN`만으로 회원이 정지됐다고 판단하지 않는다.
- 주소를 그대로 표시해 메일 앱이 설정되지 않은 환경에서도 복사할 수 있게 한다. 클릭은 메일 작성만 열며 자동 발송하지 않는다.
- 기존 메시지·오류 접근성(`role="alert"`)·재시도 버튼과 스타일을 유지한다.

## 3. 기각한 대안과 이유

| 대안 | 장점 | 기각한 이유 |
| --- | --- | --- |
| 정지 회원의 일반 로그인 허용 | 기존 문의 기능 사용 가능 | 문의를 위해 기존 인증 차단 정책과 서버 권한 경계를 바꿔야 한다 |
| 문의 전용 제한 세션·별도 문의창 | 서비스 안에서 본인 문의·답변 관리 | 현재 연락처 제공 요청보다 구현·검증 범위가 크다 |
| 모든 인증 오류에 정지 안내 표시 | 처리 단순 | 토큰 만료·로그아웃을 정지로 오인하게 한다 |

## 4. Trade-off

| 얻는 것 | 잃는 것(비용·위험) | 완화책 |
| --- | --- | --- |
| 인증 정책 변경 없는 문의 경로 | 개인 주소가 공개돼 스팸·피싱 대상이 될 수 있음 | 사용자 공개 승인에 따라 제공하며 필요 시 전용 주소로 교체 |
| 별도 서버·폼 없이 연락 가능 | 외부 메일 앱에 의존하고 서비스 내 문의 이력은 없음 | 링크와 함께 복사 가능한 주소 표시 |

## 5. 검증

### 검증 계획

- 실제 공통 오류 컴포넌트 렌더링 테스트: 명시적 제한 코드에는 올바른 메일 링크, 일반 만료·인증 실패에는 메일 링크 없음.
- 변경 전 테스트 실패 확인 후 구현한다.
- 프론트 전체 Node 테스트, ESLint, TypeScript 검사, 정적 배포 빌드를 실행한다.
- 로그인 제한 오류를 데스크톱·모바일에서 확인한다. 실제 메일 발송은 하지 않는다.

### 검증 결과

- 자기검증: 변경 전 기존 프론트 테스트 78건 통과. 새 렌더링 테스트를 먼저 추가한 뒤 메일 링크 부재로 1건 실패(관련 파일 14건 중 13건 통과)를 확인했다.
- 구현 후 전체 프론트 테스트 80건 통과, 실패·건너뜀 0. 제한 코드 4종의 실제 렌더링과 일반 인증 실패·401·네트워크 오류·오류 없음의 비노출을 확인했다.
- TypeScript 검사와 정적 배포 빌드(36페이지) 통과.
- 기본 `npm run lint`는 기존 로컬 중첩 산출물 `frontend/frontend/.next`까지 검사해 213개 오류·4,093개 경고로 실패했다. 해당 산출물만 제외한 `npm run lint -- --ignore-pattern 'frontend/**' --format json`은 오류 0·기존 경고 7개다. 이번 변경 파일의 경고·오류는 없다. 산출물·lint 설정은 수정하지 않았다.
- 정적 배포 결과와 로컬 가짜 `ACCOUNT_INACTIVE` 응답을 사용해 Chrome에서 실제 로그인 오류 안내와 `mailto:` 주소를 확인했다. 데스크톱 및 390×844 모바일에서 표시·줄바꿈을 확인했다. 실제 이메일 발송은 하지 않았다.
- 별도 세션의 독립 검증은 수행하지 않았다. 백엔드·API·DB 변경이 없어 백엔드 테스트는 재실행하지 않았다.

## 6. 한계와 재검토 조건

- 출입 거절 로그 저장, 정지 원인을 구분하는 백엔드 응답 변경, 제한 회원의 문의 API 접근은 추가하지 않는다.
- 공통 401 응답 뒤 로그아웃되는 경우에는 이 변경만으로 정지 전용 안내를 표시하지 못한다. 명시적 제한 코드가 전달되는 화면에 적용된다.
- 문의량이 늘거나 운영 주체가 바뀌면 전용 이메일 또는 본인 확인을 포함한 지원 기능을 재검토한다.

## 면접·발표용 정리 (구현 후)

- **30초 설명:** 정지 회원에게 일반 로그인 권한을 주는 대신 오류 안내에 이메일 문의 경로를 제공한다. 기존 인증·출입 차단을 유지하면서 사용자가 다음 행동을 선택할 수 있게 한다.
- **예상 질문과 답:**
  - Q. 왜 문의창을 만들지 않았나요? 현재 요구는 연락 경로 제공이며, 기존 문의 API를 열려면 별도 권한 설계가 필요하기 때문이다.
  - Q. 단점은 무엇인가요? 공개 주소의 스팸 노출과 외부 메일 앱 의존이다. 주소를 표시해 복사도 가능하게 한다.
  - Q. 규모가 커지면 어떻게 바꾸나요? 전용 지원 주소나 범위가 제한된 지원 기능을 도입한다.
- **숫자·근거 한 줄:** 프론트 테스트 80건 통과, 정적 페이지 36개 빌드, 명시적 제한 코드 4종에만 연락처 표시.
