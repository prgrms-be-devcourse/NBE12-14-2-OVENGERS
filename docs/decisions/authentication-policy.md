# SlotKey 인증 정책

> 기준일: 2026-10-15 (KST)  
> 구현 기준: PR #302, `5c60fa444dfc427016954fdacc44d3dfd293c004`  
> 문서 성격: V1 적용 정책 + V2·V3 확정 방향 + 미결정 정책의 목록  
> 관련 문서: [구현 해설](../architecture/auth-v1-implementation.md), [로드맵](../plans/auth/roadmap.md)

## 1. 목적과 적용 범위

이 문서는 이메일 인증, 로컬 회원가입, 로그인, 비밀번호 재설정과 로그인 인증 수단의 생명주기를 다룬다. 예약 소유권, 관리자 전용 기능 등 업무별 접근 권한은 별도의 [인가 정책](authorization-policy.md)에서 관리한다.

인증 성공만으로 다른 회원의 예약을 조회·취소할 권한이 생기지 않는다. 인증 처리와 리소스 소유권 검증은 모두 필요하다.

## 2. 용어

| 용어 | 의미 |
| --- | --- |
| Member | 회원의 프로필·역할·서비스 이용 상태 |
| LocalCredential | 로컬 비밀번호 해시와 변경 시각 |
| Guard | 이메일·목적별 실패 횟수와 차단 상태 |
| Challenge | 한 번 발급한 인증번호의 검증 상태 |
| Grant | 이메일 인증 성공 후 가입·복구에 사용하는 일회성 증표 |
| AT | 보호 API에 전달하는 Access Token |
| RT | 새 AT 발급에 사용하는 Refresh Token |
| 로그인 세션 | 한 번의 로그인으로 생성되는 서버 측 인증 기록. V2 도입 대상 |

Grant는 로그인 토큰이 아니다. 가입용 grant로 보호 API에 접근하거나 RT처럼 AT를 재발급받을 수 없다.

## 3. 계정과 로컬 자격 증명

**V1 적용 정책**

- 이메일을 로컬 로그인 식별자로 사용한다.
- 회원 프로필과 비밀번호 저장 책임을 분리한다.
- 비밀번호 원문을 저장하지 않고 PasswordEncoder로 처리한 해시를 저장한다.
- 신규 가입은 이메일 인증이 완료된 SIGNUP grant를 요구한다.
- 가입이 완료되면 Member.emailVerifiedAt에 인증 완료 시각을 기록한다.
- V1 이전 회원은 서비스 연속성을 위해 마이그레이션에서 인증 완료 상태로 인정한다. 이는 과거에 실제 메일 인증을 수행했다는 증거가 아니다.

이 분리는 향후 외부 로그인 확장을 쉽게 하지만, 소셜 로그인 기능 자체가 구현되었다는 의미는 아니다.

## 4. 인증번호 발급·재발송

| 항목 | V1 기준 |
| --- | --- |
| 목적 | SIGNUP / PASSWORD_RESET |
| 형식 | 8자리 숫자 문자열 |
| 수명 | 발급 후 3분 |
| 재발송 최소 간격 | 마지막 발송 후 30초 |
| 저장 | 원문 대신 HMAC 기반 검증값 |
| 검증 대상 | 요청 이메일·목적에 해당하는 최신 유효 challenge |
| 재발송 | 이전 미인증 challenge 무효화 후 새 challenge 발급 |

번호는 숫자로 변환하지 않고 문자열로 취급하여 앞자리 0을 보존한다. 클라이언트의 타이머는 안내 기능이며, 허용 여부는 서버가 판단한다.

서버는 차단 여부와 재발송 간격을 검사한 후 발급한다. PASSWORD_RESET은 로컬 자격 증명이 있는 계정에만 실제 메일을 보내는 처리가 있다. 응답 본문을 유사하게 만드는 것만으로 응답 시간이나 외부 관측을 통한 계정 존재 추론까지 방어했다고 주장하지 않는다.

재발송이 이미 발급된 grant까지 모두 폐기한다는 정책은 현재 코드로 보장하지 않는다. challenge와 grant의 수명을 혼동하지 않는다. 이 범위 변경은 별도 정책·테스트가 필요하다.

## 5. 인증번호 실패·차단·회원 정지

**실패 누적 기준은 이메일과 목적의 조합이다.** 새로운 challenge를 발급받았다는 이유로 누적 차단 단계가 초기화되지 않는다.

| 단계 | 조건 | 인증 상태 | 기존 ACTIVE 회원 | 정지 감사 로그 |
| --- | --- | --- | --- | --- |
| 1차 | 유효 challenge에서 오입력 5회 | 5분 임시 차단 | ACTIVE 유지 | 없음 |
| 2차 | 차단 해제 후 다시 오입력 5회 | 1시간 임시 차단 | ACTIVE 유지 | 없음 |
| 3차 | 다음 차단 해제 후 다시 오입력 5회 | 관리자 해제 전까지 최종 잠금 | SUSPENDED 전환 | 1건 |

“3회 실패”는 인증번호를 총 세 번 잘못 입력한다는 뜻이 아니다. 각 단계에서 5회 오입력이 누적되어 세 번째 차단 단계에 도달한다는 뜻이다. 중간 인증 성공으로 실패 상태가 초기화될 수 있으므로 단순한 평생 누적 15회 규칙도 아니다.

- 차단을 시작하는 오입력에서 해당 challenge를 무효화한다.
- 차단 중에는 인증 및 재발급을 제한한다.
- 임시 차단이 만료되면 현재 단계의 시도 횟수는 초기화하되 blockStage는 유지한다.
- 올바른 인증번호로 인증이 성공하면 실패 횟수·차단 단계·차단 상태를 초기화한다.
- 잘못된 challenge ID, 만료되거나 이미 사용한 challenge는 INVALID_CHALLENGE로 처리한다. 모든 잘못된 요청이 오입력 횟수 증가로 연결되는 것은 아니다.
- 가입 전 이메일은 Member가 없으므로 Guard만 잠근다.
- 이미 SUSPENDED 또는 WITHDRAWN인 회원은 자동 정지 과정에서 상태를 덮어쓰지 않는다.

### 5.1 수정된 V1 결함

이전 구현은 recordFailure의 true를 최종 잠금으로 취급하여 1차 임시 차단에서도 회원을 정지시킬 수 있었다. 현재 기준에서는 adminLocked를 추가로 확인한 경우에만 회원 정지를 수행한다.

회귀 테스트는 3차 최종 결과만 검사하지 않는다. 1차·2차 직후 ACTIVE와 로그 0건, 3차 직후 SUSPENDED와 로그 1건을 각각 검사한다.

### 5.2 남은 정책 결정

현재 자동 정지 분기는 회원 역할에 따른 ADMIN 예외를 두지 않는다. 기존 관리자 복구 정책과 함께 관리자 계정의 자동 잠금·복구 절차를 검토해야 한다. 또한 가입 전 이메일의 최종 잠금 해제 경로는 회원 복구 API와 구분하여 정해야 한다. 본 문서는 임의로 예외 동작을 확정하지 않는다.

## 6. Grant 정책

인증번호 검증 성공 시 grant 원문을 한 번 반환하고 DB에는 해시만 저장한다. 이메일·목적 귀속은 Grant → Challenge → Guard 관계로 확인한다. Grant 테이블에 이메일과 목적이 직접 중복 저장된다고 설명하지 않는다.

| 검증 조건 | 요구사항 |
| --- | --- |
| 입력 | 원문이 비어 있지 않음 |
| 존재 | 해시와 일치하는 grant가 존재 |
| 귀속 | 요청 이메일·목적의 Guard와 연결 |
| 시간 | 현재 시각이 expiresAt 이전 |
| 상태 | consumedAt과 invalidatedAt이 없음 |
| 수명 | 발급 후 5분 |
| 사용 | 최종 작업에 한 번만 사용 |

가입이나 재설정과 grant 소비는 같은 트랜잭션에서 완료한다. 입력 오류와 저장 실패로 최종 작업이 롤백되면 grant 소비도 롤백되어야 한다.

“성공 후 소비”는 트랜잭션의 최종 결과를 뜻한다. 코드에서 consume 호출이 반드시 마지막 줄이어야 한다는 뜻은 아니다. flush·clear를 수행하는 후속 작업 전에 소비 상태를 반영해야 할 수 있다.

## 7. 회원가입

1. 이메일, 비밀번호, 비밀번호 확인, 닉네임, 가입용 grant를 받는다.
2. 비밀번호 확인과 grant 유효성·목적·이메일 귀속을 검증한다.
3. 중복 가입을 거부한다.
4. Member와 LocalCredential을 저장하고 이메일 인증 시각을 기록한다.
5. grant 소비와 가입 보너스 처리를 같은 트랜잭션에서 수행한다.
6. 성공 응답 후 로그인은 별도로 수행한다.

PASSWORD_RESET grant, 다른 이메일의 grant, 만료·소비된 grant로 가입할 수 없다. 비밀번호 확인 불일치만으로 유효한 grant를 소모하지 않는다.

## 8. 비밀번호 재설정

로그인하지 않은 사용자도 이메일 인증을 거쳐 PASSWORD_RESET grant를 얻으면 재설정할 수 있다. 이메일, grant, 새 비밀번호와 확인값을 검증하고 LocalCredential을 변경한다.

**V1 구현:** 비밀번호 변경과 grant 소비는 처리하지만 기존 AT·RT 전체 폐기는 수행하지 않는다. 새 비밀번호로 새 로그인하는 정상 흐름은 PasswordResetIntegrationTest에서 확인한다.

**V2 확정 방향:** 변경 성공 시 기존 모든 로그인 세션의 AT·RT를 폐기한다. 변경 전 토큰은 사용할 수 없으며, 새 비밀번호로 다시 로그인하여 새 세션을 생성한다. V1의 정상 재설정 기능은 유지한다.

## 9. 로그인과 토큰

| 항목 | V1 구현 | V2 목표 |
| --- | --- | --- |
| 로그인 계정 상태 | ACTIVE 확인 | 유지 |
| AT 형식 | 서명된 JWT, 회원 식별·이메일·역할·만료 | 세션 연결 정보와 검증 추가 |
| AT 수명 | 현재 설정 기준 5분 | 변경 여부 결정 필요 |
| RT | 난수 토큰 원문은 쿠키, SHA-256 해시는 DB | 서버 세션과 연결(1번 구현), Rotation(3번 로컬 커밋 `a29dfc9`) |
| RT 수명 | 현재 구현 기준 1일 | 절대·유휴 만료 정책 결정 필요 |
| refresh | DB RT 상태·회원 상태 확인 후 새 AT | 기존 RT 소비와 새 AT·RT 발급 — 3번 로컬 커밋 `a29dfc9` |
| 보호 API | JWT 검증 후 principal 구성 | 현재 회원·세션 유효성 추가 확인 |
| logout | 해당 RT 폐기와 쿠키 삭제 | 해당 로그인 세션 폐기로 AT도 거부 |

V1에도 RT의 DB 만료·폐기 검증은 존재한다. “V1 RT에는 서버 검증이 없다”는 설명은 잘못이다. 현재의 핵심 한계는 AT의 즉시 폐기와 RT 단일 사용 보장이 없다는 점이다.

## 10. 회원 상태 변경과 인증 수단

| 사건 | V2 확정 방향 | 추가 결정 |
| --- | --- | --- |
| 현재 세션 로그아웃 | 해당 세션의 기존 AT·RT 폐기 | 토큰 전달 방식·반복 호출 응답 |
| 비밀번호 재설정 | 회원 전체 기존 세션 폐기 — V2 2번 커밋 `02c3557` | 경합 처리 순서 |
| 회원 정지 | 전체 기존 세션 폐기, 신규 인증 제한 — 관리자 정지·인증 최종 잠금 자동 정지 모두 V2 2번 커밋 `02c3557` | 관리자 예외·복구 경로 |
| 회원 복구 | 새 로그인 허용, 옛 세션은 계속 폐기 — V2 2번 커밋 `02c3557` | 복구와 Guard 해제 범위 |
| 회원 탈퇴 | 기존 세션 폐기 — V2 2번 커밋 `02c3557` | 기존 탈퇴 정책과 정합성 |
| 역할 변경 | 오래된 권한만 신뢰하지 않음 | 전체 폐기 또는 최신 권한 조회 |
| RT 재사용 탐지 | 재사용 거부 및 해당 로그인 세션(sid)과 그 RT 폐기, 다른 세션 유지 — 3번 로컬 커밋 `a29dfc9` | 확정: 세션 단위, grace 없음 |

정지 상태 확인만 추가하면 복구 후 과거 토큰이 다시 통과할 수 있다. 폐기는 회원 상태와 별도로 지속되어야 한다.

“즉시”의 기본 해석은 폐기 변경이 확정된 뒤 시작한 인증 검사가 거부된다는 뜻이다. 이미 인증을 통과해 실행 중인 요청의 소급 취소까지 보장하는 것은 아니다.

## 11. 요청 제한

V1의 30초 재발송 간격과 인증번호 실패 차단은 이미 구현된 개별 방어다. V2의 범용 요청 제한과 동일하지 않다.

V2에서는 로그인·refresh·인증번호 발급·검증·비밀번호 재설정 요청에 대해 필요한 제한을 정의한다. 현재 레드 테스트는 반복 로그인 실패 후 429만 검사한다. API별 횟수·기간·IP/이메일 기준·성공 시 초기화 여부·재허용 시각은 아직 상세 결정이 필요하다.

테스트에 있는 “5회 실패 후 6번째 429”를 모든 API의 운영 정책으로 확대하지 않는다. 제한 알고리즘과 수치는 V2·V3 성능 비교에서도 동일하게 유지한다.

## 12. 쿠키·출처·비밀값

V1 RT 쿠키는 HttpOnly, 경로 /api/v1/auth를 사용하고 Secure와 SameSite는 설정값에 따른다. 환경별 실제 값과 배포 도메인은 별도로 점검한다.

현재 CSRF 비활성 설정을 완성된 브라우저 보안 정책으로 해석하지 않는다. 쿠키 자동 전송이 사용되는 요청에 대해 허용 출처와 CSRF 방어 방식을 V2에서 결정한다. CORS 설정만으로 모든 요청 위조가 차단된다고 판단하지 않는다.

비밀번호·코드·grant·AT·RT 원문은 감사 로그나 일반 애플리케이션 로그에 남기지 않는다. HMAC 비밀키의 배포·회전 시 기존 인증 수단에 미치는 영향도 운영 정책에 포함한다.

## 13. 감사 로그와 운영

V1은 관리자 정지·복구 및 인증 실패로 인한 자동 회원 정지를 기록한다. 자동 정지의 행위자 ID가 null인 것은 시스템 작업을 뜻한다.

V2 확대 후보는 로그인 실패, RT 재사용, 세션 강제 종료, 비밀번호 재설정, 요청 제한 초과다. 수집 범위·보존 기간·IP 및 User-Agent 취급은 결정 후 구현한다. 모든 요청을 무제한 기록하는 정책을 기본값으로 삼지 않는다.

## 14. V3 및 후속 범위

V3는 V2의 보안 의미를 유지하면서 세션·RT·요청 제한·이메일 인증 임시 상태의 저장·동시성 제어를 Redis로 전환한다. 인증 판정이 불가능하면 보호 API를 우회 허용하지 않는다.

Google 소셜 로그인은 V1~V3 이후에 수행한다. 외부 계정 연결, 동일 이메일 충돌 처리, Google 검증 이메일 인정 여부는 후속 설계에서 결정한다.
