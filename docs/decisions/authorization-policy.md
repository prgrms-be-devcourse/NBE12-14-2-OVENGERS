# 기술적 의사결정 — 인가 정책

## 문제 상황

로그인 성공 여부만 확인하는 인증으로는 "관리자만 공간을 등록할 수 있다", "본인 예약만 취소할 수 있다", "취소된 예약으로는 출입할 수 없다" 같은 규칙을 표현할 수 없다. 이 프로젝트는 인증·인가를 다음 다섯 축으로 확장하는 것을 핵심 목표로 삼는다(기획서 2-2).

## 인증·인가의 다섯 축

| 축 | 질문 | 예 |
| --- | --- | --- |
| 인증 | 이 요청은 어떤 회원의 인증 정보로 들어왔는가? | Access JWT 서명·만료 검증 (회원 상태는 로그인·refresh 경계에서 검증) |
| 역할 기반 인가 | 공간 등록·수정, 전체 예약 조회를 요청한 회원이 관리자인가? | ADMIN 전용 API |
| 소유권 기반 인가 | 조회·취소하려는 예약이 본인 것인가? | 예약 취소, 도어 토큰 발급 |
| 상태 기반 인가 | 예약·토큰 등 대상 리소스가 해당 작업을 허용하는 상태인가? | 취소는 CONFIRMED만, 도어 토큰은 CONFIRMED 또는 IN_USE |
| 시간 기반 인가 | 지금 출입 토큰을 발급/사용할 수 있는가? | 체크인 허용 구간, 종료 시각 전 |

## 선택 및 근거

- Access JWT 페이로드에는 `id`, `email`, `role`, `sid`, 만료 시각(`exp`)을 담는다. 현재 운영 기준인 V2의 `CustomAuthenticationFilter`는 서명·만료를 검증한 뒤 `sid`와 회원 ID로 DB 로그인 세션 및 현재 회원 상태를 확인하고 `AuthPrincipal`을 생성한다. 따라서 보호 요청 인증은 매 요청 DB 세션 검증을 포함한다. V3에서는 이 인증 상태 검증을 Redis로 옮긴 실험을 했지만 운영 도입은 보류했다 — [V3 실험 결과](../testing/auth-v3-experiment-results.md).
  - **경로별 정지 계정 동작**:
    - 로그인(`POST /api/v1/auth/login`)과 토큰 재발급(`POST /api/v1/auth/refresh`)은 DB에서 회원 상태를 조회하므로 정지(`SUSPENDED`) 회원을 `ACCOUNT_INACTIVE`(403), 탈퇴(`WITHDRAWN`) 회원을 `ACCOUNT_WITHDRAWN`(401)으로 즉시 차단한다.
    - 반면 예약(HOLD·결제·연장·취소), 출입 키 발급·검증, 문의 등록 등 비즈니스 API는 `AuthPrincipal`의 ID/Role과 리소스 소유권만 확인할 뿐 회원 DB의 `status`를 매번 재조회하지 않는다. 따라서 이미 발급된 Access Token은 만료 전까지(최대 5분) API 호출이 통과된다.
  - **기존 인증 수단 즉시 차단 — V2에서 구현되어 현재 운영 기준으로 유지**:
    - V2는 로그인마다 DB 세션을 만들고 Access Token의 `sid`와 연결한다. 보호 요청은 세션의 소유 회원·만료·폐기 여부와 현재 회원 상태를 확인한다. 로그아웃은 해당 세션을, 탈퇴·정지·비밀번호 재설정 및 인증 최종 잠금에 따른 자동 정지는 기존 세션들을 폐기한다. 회원 복구는 폐기된 세션을 되살리지 않는다. RT Rotation과 재사용 탐지도 DB 기반으로 동작한다. 세부 정책은 [인증 정책](authentication-policy.md) §9~§10 및 [V2 계획](../plans/auth/v2-plan.md)을 따른다.
    - **V3는 실험 구현으로 보존하고 도입을 보류했다(2026-10-21).** Redis 세션 및 RT 이전은 dev·운영 기준이 아니며, 현재 정책과 적용 기준은 V2(DB)다 — [V3 실험 결과](../testing/auth-v3-experiment-results.md).
    - 이 문서의 역할·소유권·상태·시간 기반 인가는 계속 적용되며, 공통 인증 검증은 도메인 권한 판단을 대신하지 않는다.
- 역할은 `USER` / `ADMIN` 두 가지만 둔다(`MemberRole` enum). 팀별 역할, 공간 운영자 소유권 같은 추가 개념은 도입하지 않는다(예약은 항상 개인 명의).
- **관리자 권한은 소유권 검사를 대체하지 않는다** — 관리자도 본인 예약이 아니면 취소·출입 토큰 발급을 할 수 없고, 강제 취소는 별도의 `force-cancel` 경로로만 허용한다. 이것이 기획서가 명시한 핵심 차별점이다.
- 화면에서 버튼을 숨기는 것과 별개로, 모든 보호 API에서 서버가 권한을 검사한다(클라이언트 신뢰 금지).
- 일반 회원의 타인 예약 접근은 `FORBIDDEN_NOT_OWNER`(403)로 차단하고, 존재하지 않는 예약 접근은 `RESERVATION_NOT_FOUND`(404)로 처리한다.
- 회원가입 요청으로 `role`을 지정할 수 없다 — 서버가 항상 `USER`로 생성.

## 담당 간 협업

공통 인증(AUTHN/AUTHZ 필터)은 천종원이 제공하고, 각 도메인 담당자(space: 김재철, reservation: 이태호, credit_transaction/history: 백한비, door_access: 박창현)가 자신의 `AuthorizationService`와 관련 테스트를 구현한다(기획서 13장, 리스크 4). *(2026-09-15: `payment` → `credit_transaction`, `core-domain-decisions.md` §1/§11)*

## 검증 방법

- 일반 회원의 관리자 API 접근, 타인 예약 접근이 거절되는지 테스트.
- 관리자도 타인 예약 취소·출입 토큰 발급을 할 수 없는지 별도 테스트.
- 로그아웃·계정 정지·탈퇴·비밀번호 재설정 등 사건 이후 기존 AT와 RT가 거부되고, 다른 회원 및 다른 로그인 세션은 영향을 받지 않는지 확인한다. 현재 V2 기준의 보안 회귀 테스트는 [인증 보안 테스트](../testing/auth-security-tests.md)에 기록한다.
- 회원 상태와 역할·소유권 검사는 구분한다. 세션 검증이 성공해도 각 업무 API는 기존 역할·객체 소유권 검사를 별도로 수행해야 한다.
