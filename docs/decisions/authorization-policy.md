# 기술적 의사결정 — 인가 정책

## 문제 상황

로그인 성공 여부만 확인하는 인증으로는 "관리자만 공간을 등록할 수 있다", "본인 예약만 취소할 수 있다", "취소된 예약으로는 출입할 수 없다" 같은 규칙을 표현할 수 없다. 이 프로젝트는 인증·인가를 다음 네 축으로 확장하는 것을 핵심 목표로 삼는다(기획서 2-2).

## 인가의 네 축

| 축 | 질문 | 예 |
| --- | --- | --- |
| 인증 | 이 요청은 어떤 회원의 인증 정보로 들어왔는가? | JWT 검증 |
| 역할 기반 인가 | 공간 등록·수정, 전체 예약 조회를 요청한 회원이 관리자인가? | PLATFORM_ADMIN 전용 API |
| 소유권 기반 인가 | 조회·취소하려는 예약이 본인 것인가? | 예약 취소, 도어 토큰 발급 |
| 상태 기반 인가 | 회원과 예약이 현재 이용 가능한 상태인가? | ACTIVE 회원, CONFIRMED 예약만 |
| 시간 기반 인가 | 지금 출입 토큰을 발급/사용할 수 있는가? | 체크인 허용 구간 |

## 선택 및 근거

- JWT 클레임에는 `id`(회원 식별자), `email`, `role`, `exp`를 담는다. `CustomAuthenticationFilter`는 이 클레임만으로 인증하며 **매 요청마다 회원 DB를 재조회하지 않는다** *(2026-09-22 정정, PR #208 — 기존에는 역할·상태를 요청마다 DB에서 재조회했음)*. 그 결과 계정 정지는 즉시 반영되지 않는다 — 이미 발급된 Access Token은 만료 전까지(현재 5분) 그대로 통한다. 정지는 리프레시 시점에만 강제된다: `RefreshTokenService.validateRefreshToken`이 리프레시 토큰마다 회원 상태를 확인해서, 정지된 계정은 `POST /api/v1/auth/refresh`로 새 Access Token을 받을 수 없다. 로그인(`POST /api/v1/auth/login`)도 같은 방식으로 막힌다. 즉 "정지되면 곧 키를 못 쓰게 된다"는 맞지만, 그 시점은 정지 즉시가 아니라 **가지고 있던 Access Token이 만료되는 시점(최대 5분 이내)**이다.
- 역할은 MEMBER / PLATFORM_ADMIN 두 가지만 둔다. 팀별 역할, 공간 운영자 소유권 같은 추가 개념은 도입하지 않는다(예약은 항상 개인 명의).
- **관리자 권한은 소유권 검사를 대체하지 않는다** — 관리자도 본인 예약이 아니면 취소·출입 토큰 발급을 할 수 없고, 강제 취소는 별도의 `force-cancel` 경로로만 허용한다. 이것이 기획서가 명시한 핵심 차별점이다.
- 화면에서 버튼을 숨기는 것과 별개로, 모든 보호 API에서 서버가 권한을 검사한다(클라이언트 신뢰 금지).
- 일반 회원의 타인 예약 접근은 자원 존재 여부를 노출하지 않기 위해 404로 처리(설계 원칙 — 최종 코드값은 API 명세서 확정본 기준).
- 회원가입 요청으로 `role`을 지정할 수 없다 — 서버가 항상 MEMBER로 생성.

## 담당 간 협업

공통 인증(AUTHN/AUTHZ 필터)은 천종원이 제공하고, 각 도메인 담당자(space: 김재철, reservation: 이태호, credit_transaction/history: 백한비, door_access: 박창현)가 자신의 `AuthorizationService`와 관련 테스트를 구현한다(기획서 13장, 리스크 4). *(2026-09-15: `payment` → `credit_transaction`, `core-domain-decisions.md` §1/§11)*

## 검증 방법

- 일반 회원의 관리자 API 접근, 타인 예약 접근이 거절되는지 테스트.
- 관리자도 타인 예약 취소·출입 토큰 발급을 할 수 없는지 별도 테스트.
- 계정 정지 후에도 만료 전 Access Token으로는 보호 API 호출이 계속 성공하는지 테스트(`AuthControllerTest#t15`).
- 계정 정지 후 리프레시 토큰으로 재발급을 시도하면 `ACCOUNT_INACTIVE`(403)로 거절되는지 테스트.
