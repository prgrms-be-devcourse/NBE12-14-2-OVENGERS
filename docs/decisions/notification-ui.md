# 알림 목록과 일괄 읽음 처리

## 한 줄 요약

기존 알림 조회에 목록 화면과 본인 알림 일괄 읽음만 추가한다.

## 1. 문제와 배경

DB에 저장된 알림을 사용자가 볼 화면이 없고 읽음 API가 없어 배지가 줄지 않는다. 기존 예약·인증·이벤트 전달 흐름은 유지한다.

## 2. 선택과 이유

토큰 회원 id, `read_at IS NULL`, `id <= upToId`를 조건으로 단일 UPDATE하고 `{ updatedCount }`를 반환한다. `upToId`는 필수 Long 쿼리 파라미터이며 요청 본문은 없다. 프런트는 목록을 렌더링한 뒤 그 목록의 최대 id를 보관하고 자동 읽음과 실패 재시도에 같은 상한을 넘긴다. 빈 목록은 호출하지 않는다. 읽음 응답으로 목록 스냅샷을 덮어쓰지 않는다.

상한 방식을 채택한 이유는 조회 이후 도착한 더 큰 id의 알림을 미읽음으로 보존하면서 단일 UPDATE와 반복 요청의 안전성을 유지하기 위해서다. 화면은 기존 Pagination·상태 컴포넌트·날짜 유틸을 재사용하며, 배지는 로그인·알림 경로 출입·읽음 성공 이벤트에서 서버 개수를 재조회한다.

## 3. 기각한 대안과 이유

| 대안 | 장점 | 기각한 이유 |
| --- | --- | --- |
| 상한 없이 전부 읽음 처리 | 요청이 단순함 | 조회 이후 도착해 화면에 표시되지 않은 새 알림까지 읽음 처리하므로 기각 |
| 항목마다 읽음 API | 개별 제어 | 최소 읽음 요구보다 복잡하고 요청 수 증가 |
| 목록 조회 전에 읽음 처리 | 구현 간단 | 처음부터 안 읽은 표시가 사라짐 |
| 주기적 폴링 | 새 알림 반영 빠름 | 명시된 범위 밖, 불필요한 주기 요청 |

## 4. Trade-off

| 얻는 것 | 잃는 것(비용·위험) | 완화책 |
| --- | --- | --- |
| 단일 UPDATE와 새 알림 보호 | 상한 이하의 이전 페이지 알림도 읽음 처리됨 | 화면 안내에 상한까지 읽음을 명시하고 배지는 서버 개수 재조회 |
| 최초 안 읽음 표시 유지 | 읽음 후 현재 화면은 스냅샷 | 다음 목록 조회부터 반영 |

## 5. 검증

### 검증 계획

상한 초과 알림 미변경·본인만 읽음·기존 읽음 시각 유지·재요청 0건·무토큰 401 통합 테스트. 프런트 API 상한 전달, 렌더 후 최대 id 전달·빈 목록 미호출 테스트. API 경로·파라미터·매핑·배지 조건 프런트 테스트. 전체 테스트, lint, build와 가능한 로컬 브라우저 검증.

### 검증 결과

M1 자기검증: `./gradlew test --rerun-tasks` 성공, {'tests': 816, 'failures': 0, 'errors': 0, 'skipped': 11}. 프런트 `node --test tests/*.test.cjs` 55/55 통과, `npm run lint` 오류 0·기존 경고 7, `npm run build` 성공. 브라우저 수동 검증과 CI는 미실행.

테스트 우선: 변경 전 백엔드 2개 중 1개가 상한 뒤 알림까지 읽어 실패했다. 프런트는 upToId 전달 누락으로 API·렌더 후 호출 테스트 2개가 실패했다. 수정 후 전체 검증에서 통과했다. 페이지 테스트는 실제 컴포넌트를 서버 렌더하고 effect를 실행하며 API 호출과 hooks 경계는 대체하므로 실제 브라우저·배지 수명주기 검증은 포함하지 않는다.

## 6. 한계와 재검토 조건

실시간 전달 및 개별 읽음은 제외한다. 요구가 생기면 별도 설계한다. `upToId` 이하의 이전 페이지 알림은 포함하므로 표시된 항목만 정확히 읽는 요구가 생기면 id 집합 방식을 재검토한다. ID는 커밋 순서를 보장하지 않으므로 상한 이하 id의 지연 커밋까지 보호하지는 않는다.

- Low: 읽음 실패 시 배지를 재조회하지 않는 동작은 이번 수정에서 유지한다.
- Low: 관리자에게도 알림 링크를 노출하는 동작은 이번 수정에서 유지한다.

## 면접·발표용 정리 (구현 후)

회원 id와 미읽음 조건을 단일 UPDATE에 포함해 타인 알림과 기존 읽음 시각을 보존했다. UI는 목록 스냅샷을 유지하고 서버의 안 읽은 개수를 재조회한다. 상한으로 새 알림을 보호하되 상한 이하의 이전 페이지 알림은 포함되는 trade-off가 있다.
