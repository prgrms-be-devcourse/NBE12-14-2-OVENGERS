# 기술적 의사결정 — 출입 키(door_access_token) 정책

> **2026-09-15 갱신**: `docs/core-domain-decisions.md` §8 반영 — 발급 시간 제한 삭제, 최초 체크인 허용 구간을 "시작 전후 30분"에서 "`[start, start+15분]`"로 변경. 체크아웃이 별도 API로 분리됨.

## 문제 상황

"예약당 사용 가능한 토큰은 최대 1개"라는 규칙이 서비스 로직에만 의존하면 이 프로젝트의 동시성 원칙(기저 데이터는 스냅샷, DB 제약으로 동시성을 막는다)과 어긋난다.

## 요구 조건

- 예약 하나당 현재 유효한(폐기되지 않은) 출입 토큰은 최대 1개여야 한다.
- 재발급(재입장 등) 시나리오에서 기존 토큰과 새 토큰이 동시에 유효한 상태가 되어서는 안 된다.
- 폐기된 토큰의 이력은 감사/디버깅을 위해 계속 쌓여야 한다.

## 선택 및 근거

- `door_access_token`에 생성 컬럼 `active_reservation_id`를 추가한다.
  - `revoked_at IS NULL`일 때만 `reservation_id` 값을 갖고, 폐기된 토큰은 `NULL`.
  - `UNIQUE(active_reservation_id)` 인덱스를 적용한다.
- MySQL 유니크 인덱스는 NULL을 여러 개 허용하므로, 폐기된 토큰(`active_reservation_id = NULL`)은 여러 건 존재할 수 있고, "현재 유효한 토큰은 예약당 1개"만 DB가 강제한다.
- 재발급 시나리오: 새 토큰 발급 전, 기존 활성 토큰을 먼저 폐기(`revoked_at` 세팅)하는 것을 하나의 트랜잭션으로 처리한다.
- 이 규칙은 `core-domain-decisions.md` §11에서도 **"유지"** 항목으로 재확인되었다 — 변경 없음.

## 발급/검증/체크아웃 규칙 (API 명세서 §7, §5-6)

- **발급**: 예약자 본인만. **시간 제한 없음** — 예약이 `CONFIRMED`이고 종료 시각 전이면 확정 직후부터 언제든 발급 가능. 발급은 입장 권한이 아니라 신분증을 받는 것일 뿐이며, `start_time` 전엔 문이 열리지 않는다. *(2026-09-15 정정 — 기존에는 "예약 시작 30분 전부터"였음. 시간 제한을 없애면 `TOKEN_ISSUE_TOO_EARLY` 검사가 통째로 사라지고, 예약 완료 화면에서 바로 키를 보여줄 수 있다.)*
- **검증**: 토큰 해시 → 활성 토큰 조회(폐기 토큰 즉시 거절) → 예약 상태(`CONFIRMED` 또는 `IN_USE`)/공간 일치 → 시간대 확인 → 성공/실패 모두 `door_access_log`에 기록.
  - **최초 체크인**: `[start_time, start_time + 15분]` — 앞 여유 0분(시작 시각 정각 허용), 뒤 15분. 성공 시 `CONFIRMED → IN_USE` 전이가 부수 효과로 일어난다.
  - **재입장**: `(checked_in_at, end_time)` — 열린 구간이라 종료 시각 정각은 거절.
  - 앞 여유를 0으로 두는 이유: 연속된 두 슬롯(예: 14:00~15:00 다음 15:00~16:00)의 이용 구간이 겹치지 않으려면 다음 예약자의 입장 가능 구간이 정확히 15:00부터 시작해야 하기 때문. "직전 슬롯이 비었으면 일찍 허용" 같은 동적 규칙은 체크인 판정이 남의 예약 상태에 의존하게 만들므로 채택하지 않는다.
  - *(2026-09-15 정정 — 기존에는 "최초 체크인: 시작 30분 전~30분 후"였음)*
- **체크아웃**: 별도 API(`POST /reservations/{id}/check-out`)로 분리되어 있으며 예약 도메인에 속한다. Mock Door는 입장/퇴장을 구분하지 못하고 재입장을 허용하는 이상 어떤 검증이 "마지막 퇴장"인지 알 수 없기 때문이다. 체크아웃 시 활성 토큰을 폐기하고, 슬롯 반환·환불은 없으며 되돌릴 수 없다.
- 원문 토큰은 발급 응답에만 담고 DB에는 해시만 저장한다.
- 토큰 자체에는 시간 정보를 담지 않는다 — 검증 시점에 예약에서 시간을 읽는다. 연장해도 토큰을 재발급할 필요가 없고, 취소 시 토큰 폐기가 늦어도 예약 상태 검사가 이중 방어가 된다.

## 담당 간 협업

`door_access_token`/`door_access_log`는 박창현이 소유하지만, 인증·인가 담당(천종원)의 회원 상태 확인 로직, 예약 담당(이태호)의 예약 상태·취소/체크아웃 시 토큰 무효화 로직과 인터페이스를 맞춰야 한다.

## 검증 방법

- 재발급을 연속으로 여러 번 호출해도 활성 토큰이 항상 1개로 수렴하는지 통합 테스트로 확인.
- 예약 취소 직후 기존 토큰 검증이 즉시 실패하는지 확인(DoD).
- 체크인 시간 경계(`start-1s`/`start`/`start+15m`/`start+15m+1s`)와 재입장 경계(`checked_in_at`/`end-1s`/`end`)를 `Clock` 주입으로 검증.
