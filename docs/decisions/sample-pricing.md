# 샘플 공간 가격과 기본 크레딧을 현실적인 값으로 조정

## 한 줄 요약

샘플 공간 30분 요금을 수용인원과 지역으로 정한 5,500~26,400원으로 올리고, 기존 샘플 공간에도 `spaces.version`을 올려 적용하며, 기본 크레딧은 회원가입 300,000원·샘플 회원 1,000,000원으로 맞춘다.

## 1. 문제와 배경

- 샘플 공간(운영 39개, 로컬 39개)의 30분 요금이 2,000~6,500원(시간당 4,000~13,000원)이었다. 회의실·공유오피스 요금으로는 비현실적이라 시연·발표에서 서비스가 장난감처럼 보인다.
- 요금이 수용인원과 무관하게 순번으로 정해져(`2000 + MOD(n-1,10)*500`) 2인실이 12인실보다 비싼 경우가 있었다.
- 요금을 올리면 기본 크레딧도 함께 올려야 한다. 회원가입 지급액(`app.credit.signup-grant`) 50,000원으로는 새 요금에서 4인실 2시간 정도만 예약할 수 있다. 운영 샘플 회원은 100,000원, 로컬 샘플 회원은 1,000,000원으로 서로 달랐다.
- 제약
  - 요금은 30분당 정액이고 100원 단위다(AGENTS.md 절대 규칙 1).
  - 결제는 HOLD 때 받은 `spaces.version`과 비교한다(core-domain-decisions.md). 요금을 바꾸면 version을 올려야 결제 대기 중인 예약이 옛 요금으로 결제되지 않는다.
  - 크레딧 잔액은 원장(`credit_transaction`)과 함께 움직여야 한다.

## 2. 선택과 이유

- 선택한 방법:
  - **요금 = 수용인원 기준가 × 지역 가중치.** 30분 기준가는 2인 5,000 / 4인 8,000 / 6인 12,000 / 8인 15,000 / 12인 22,000원이다. 지역 가중치는 강남 1.2, 판교 1.1, 하남 1.0이다. 결과는 5,500~26,400원(시간당 1만~5.3만 원)이고 모두 100원 단위로 떨어진다.
  - **기존 샘플 공간에도 적용한다.** 운영 `aws-setup.sh update`·`setup`과 로컬 `setup.sh setup`이 등록된 샘플 공간 요금을 새 기준으로 맞춘다. 요금이 실제로 바뀐 경우에만 `spaces.version`을 1 올린다.
  - **기본 크레딧.** 회원가입 지급 50,000 → 300,000원(`application.yml`). 운영 샘플 회원 100,000 → 1,000,000원으로 로컬과 맞춘다. 이미 있는 회원 잔액은 바꾸지 않고, 새로 만들어지는 회원부터 적용한다.
- 이유:
  1. 수용인원이 클수록 비싼 것이 실제 공유오피스 요금 구조와 맞고, 화면에서 설명하기 쉽다. 지역 가중치는 랭킹의 지역 비교에도 의미를 준다.
  2. version을 올리는 것은 이미 설계된 가격 변경 경로와 같다(관리자가 요금을 바꿀 때와 동일). 결제 대기 중인 예약은 409로 거절되고 새 요금으로 다시 예약하게 된다.
  3. 회원가입 300,000원은 새 요금으로 4인실 약 4~5시간, 12인 강남 회의실 약 1시간 분량이라 충전 없이도 기능을 둘러볼 수 있다. 1회 충전 한도(100,000원)는 그대로 둔다.
  4. 기존 잔액을 원장 없이 바꾸면 `balance_after` 연속성이 깨진다. 보충이 필요하면 관리자 크레딧 지급(ADMIN_GRANT)을 쓰면 된다.

## 3. 기각한 대안과 이유

| 대안 | 장점 | 기각한 이유 |
| --- | --- | --- |
| 수용인원만으로 요금 결정 | 규칙이 더 단순하다 | 지역 차이가 없어 강남·하남 공간의 차이를 설명할 수 없다 |
| 기존 요금 × 3 | 기존 규칙을 유지한다 | 수용인원과 요금이 무관한 문제가 그대로 남는다 |
| 새로 만드는 공간에만 새 요금 | 기존 데이터와 진행 중 결제를 건드리지 않는다 | 운영 샘플이 계속 몇천 원으로 남고, 로컬은 reset해야만 적용된다 |
| 요금 변경 때 version을 올리지 않음 | 결제 대기 예약이 거절되지 않는다 | HOLD 때의 옛 요금으로 결제될 수 있어 가격 버전 비교 규칙을 깬다 |
| 기존 샘플 회원 잔액을 ADMIN_GRANT로 보충 | 기존 계정도 바로 넉넉해진다 | 운영 데이터에 금액 변경과 원장 행이 생긴다. 필요하면 관리자 화면에서 개별 지급할 수 있다 |

## 4. Trade-off

| 얻는 것 | 잃는 것(비용·위험) | 완화책 |
| --- | --- | --- |
| 현실적인 요금과 수용인원·지역에 비례한 요금 구조 | 스크립트 실행 순간 결제 대기 중인 샘플 예약이 409로 거절된다 | 운영 실행은 서비스를 잠시 멈춘 상태에서 한다(AWS.md 절차). HOLD는 10분이면 만료된다 |
| 스크립트가 요금 기준을 계속 보장한다 | 관리자가 샘플 공간 요금을 바꿔도 다음 스크립트 실행 때 기준값으로 돌아간다 | 이름·사진과 같은 기존 정책이다. 샘플이 아닌 공간은 건드리지 않는다 |
| 가입 크레딧으로 충분히 체험 가능 | 기존 회원과 새 회원의 초기 잔액이 다르다 | 필요한 계정은 관리자 크레딧 지급으로 보충한다 |

## 5. 검증

검증 결과 (2026-10-18, 테스트를 먼저 바꿔 실패를 확인한 뒤 구현):

- `data-setting/tests/test_aws_setup.py` 18개 통과(임시 MySQL 8.4): 39개 공간의 (지역, 수용인원, 요금)이 기준표와 모두 같다. 관리자가 9,000원·version 7로 바꾼 판교 2인 공간이 `update` 후 5,500원·version 8이 되고, `setup`을 다시 돌려도 version은 8로 유지된다. 수용인원·영업시간·상태는 보존된다. 샘플 회원 100명의 잔액과 `SIGNUP_GRANT` 원장 합계는 100,000,000원이다.
- `data-setting/tests/test_local_setup.py` 5개 통과: 로컬 요금 기준표, 2,000원·version 3 공간이 `setup` 두 번 후 5,500원·version 4.
- 백엔드 `./gradlew test` 988개 통과(가입 지급액 300,000원 변경 후). 가입 지급액을 직접 단언하는 테스트는 없다.

## 6. 한계와 재검토 조건

- 요금표는 실제 시장 조사가 아니라 시연용 추정값이다. 실제 운영 요금이 생기면 그 값으로 바꾼다.
- 기존 샘플 회원 잔액은 바뀌지 않는다. 운영 샘플 회원 잔액이 부족하다는 피드백이 오면 ADMIN_GRANT 일괄 지급을 별도로 검토한다.
- 1회 충전 한도 100,000원은 26,400원 공간의 2시간 예약(105,600원)보다 작다. 충전을 여러 번 해야 하는 불편이 관측되면 한도를 다시 본다.

## 면접·발표용 정리 (구현 후)

- **30초 설명:** 샘플 요금이 비현실적이라 수용인원 기준가에 지역 가중치를 곱하는 규칙으로 바꿨다. 기존 공간에도 적용하되, 요금이 바뀐 공간만 가격 버전을 올려 결제 대기 중인 예약이 옛 요금으로 결제되지 않게 했다.
- **예상 질문과 답:**
  - Q. 가격을 바꿀 때 진행 중인 결제는 어떻게 되나요? A. HOLD 때 받은 `spaces.version`과 결제 때 값을 비교하므로, 버전이 오른 공간의 결제는 409로 거절되고 새 요금으로 다시 예약한다.
  - Q. 기존 회원 잔액은 왜 안 올렸나요? A. 잔액은 원장과 같이 움직여야 해서 직접 바꾸지 않았다. 필요하면 관리자 지급으로 원장을 남기며 보충한다.
- **숫자·근거 한 줄:** 30분 요금 5,500~26,400원(기존 2,000~6,500원), 요금이 바뀐 공간만 version +1(재실행 시 추가 증가 없음), 회원가입 지급 300,000원.
