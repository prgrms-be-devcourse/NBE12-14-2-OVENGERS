# 고위험 행위 재인증 (2차 비밀번호, step-up auth)

> 2026-10-14 작성. **3차 프로젝트 범위**다. 2026-10-21 마감 목록에는 넣지 않는다. 천종원의 V2(DB 세션) 위에 올라가므로 V2 완료 후 구현한다.

## 목적

세션(AT)이 탈취되더라도 크레딧 사용과 계정 정보 변경 같은 고위험 행위는 할 수 없게 한다.

## 적용 범위

| 대상 | 재인증 | 이유 |
| --- | --- | --- |
| 크레딧으로 예약 결제 확정 | 필요 | 이미 충전된 크레딧이 빠져나가는 순간이 실제 피해 지점이다 |
| 이메일·비밀번호 변경 | 필요 | 계정 탈취로 이어진다 |
| PG 크레딧 충전 | **불필요** | 토스 결제창에서 카드사 인증을 따로 거친다. 탈취된 세션으로 충전해도 공격자 카드로 피해자 계정에 돈을 넣는 셈이다 |

## 설계

"결제 API에 PIN을 같이 보내는 방식"은 쓰지 않는다. PIN 확인과 결제를 분리하고, PIN 확인 결과로 **용도·대상·금액에 묶인 1회용 승인 토큰**을 발급한다.

```
① POST /auth/step-up
   요청: { pin, purpose: RESERVATION_PAYMENT, reservationId }
   서버: PIN 확인 (5회 실패 시 잠금, 이메일 인증으로 해제)
         → 결제 승인 토큰 발급
           (회원 ID, 예약 ID, 금액에 묶임 / 5분 만료 / 1회용 / DB에는 해시로 저장)
   응답: { stepUpToken }

② POST /reservations/{id}/payment-confirm
   헤더: Step-Up-Token, Idempotency-Key
   서버: 한 트랜잭션 안에서
         토큰의 소유자·예약·금액 일치, 만료·사용 여부 확인
         → 토큰을 "사용됨"으로 조건부 UPDATE
         → 크레딧 차감 → 예약 확정
```

## 이렇게 나누는 이유

- PIN이 오가는 경로가 한 곳뿐이다. 결제 API는 PIN을 다루지 않는다.
- 토큰을 가로채도 다른 예약이나 금액에는 쓸 수 없다.
- 같은 승인으로 두 번 결제할 수 없다. 1회용이며 "사용됨" 처리가 크레딧 차감과 같은 트랜잭션에서 일어난다.

## 규칙

- PIN은 BCrypt로 저장한다. 숫자 6자리는 경우의 수가 적으므로 **시도 횟수 제한이 핵심**이다.
- PIN만으로는 비밀번호와 같은 "아는 것" 요소이므로 진짜 2단계 인증이 아니다. 이 기능의 가치는 "고위험 행위 직전 재확인 + 범위가 묶인 1회용 토큰"에 있다.

## 함께 필요한 작업

- PIN 설정, 변경, 분실 시 재설정(이메일 인증) API와 화면

## 검증할 테스트

- 세션만 있고 승인 토큰이 없으면 결제 거절
- 다른 예약·다른 금액의 토큰으로 결제 거절
- 같은 토큰으로 두 번 결제 시 1번만 성공
- 만료된 토큰 거절
- PIN 5회 실패 시 잠금, 잠금 중에는 올바른 PIN도 거절
