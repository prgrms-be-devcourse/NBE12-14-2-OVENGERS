# 의사결정 초안 — 회원탈퇴 정책

> 작성일: 2026-09-29
> 상태: **제안 / 확정 전**. 회원탈퇴 구현을 위한 논의 초안이며, 아래 정책은 아직 구현되거나 최종 승인되지 않았다.
> 적용 범위: 본인 회원탈퇴. 닉네임 중복 방지는 이번 작업에 포함하지 않으며 기존 중복 허용 정책을 유지한다.

## 문제 상황

회원은 예약, 크레딧 원장, 출입 기록과 연결되어 있다. 회원 행을 바로 삭제하면 기존 이력의 참조와 운영상 조회에 영향을 준다.

또한 현재 인증 필터는 JWT의 ID와 역할을 사용하고 매 요청마다 회원 상태를 조회하지 않는다. 브라우저에서 로그아웃하거나 리프레시 토큰만 폐기하면 이미 발급된 액세스 토큰은 만료 전까지 사용될 수 있다.

## 제안 정책

### 1. 탈퇴 방식과 대상

- 회원 행을 물리적으로 삭제하지 않고 `MemberStatus`에 `WITHDRAWN`을 추가하여 탈퇴 상태로 전환한다.
- 탈퇴 시각을 기록한다. 탈퇴 상태는 관리자 정지 해제 기능으로 복구할 수 없다.
- 본인만 탈퇴할 수 있다. 대상 회원 ID는 요청 본문이나 URL에서 받지 않고 인증 정보에서 가져온다.
- 관리자 본인 탈퇴와 정지 회원의 탈퇴 허용 여부는 별도 확정이 필요하다. 기존 관리자 정지·복구 API를 탈퇴 기능으로 재사용하지 않는다.

### 2. 진행 중인 예약

다음 예약이 하나라도 있으면 탈퇴를 차단하는 것을 제안한다.

| 상태 | 탈퇴 전 처리 |
| --- | --- |
| `HELD` | 결제 대기 예약의 만료·정리 후 다시 시도 |
| `CONFIRMED` | 취소 가능한 예약은 사용자가 직접 취소. 취소 불가 시 이용 완료 또는 노쇼 처리 후 다시 시도 |
| `IN_USE` | 체크아웃 또는 자동 완료 처리 후 다시 시도 |
| `COMPLETED`, `CANCELLED`, `EXPIRED`, `NO_SHOW` | 탈퇴를 차단하지 않음 |

- 탈퇴 요청이 예약을 자동 취소하거나 환불하지 않는다. 기존 취소·환불 정책을 사용한다.
- 현재 일반 예약 취소는 `CONFIRMED`에 대한 기능이므로 `HELD`를 취소하라고 안내하지 않는다.
- 만료 시각이 지난 `HELD`나 종료 시각이 지난 예약이 배치 지연으로 남아 있는 경우의 처리 기준은 구현 전에 확정한다. 상태만 조회하면 정리 전까지 탈퇴가 차단될 수 있다.

### 3. 잔여 크레딧

- 잔여 크레딧은 탈퇴 시 소멸하며 환급하지 않는 것을 제안한다.
- 최종 확인 화면에 현재 잔액과 소멸 내용을 표시하고 명시적인 동의를 받는다.
- 소멸 금액은 기존 결제·취소 위약금과 구분되는 원장 항목으로 기록하고 잔액을 0으로 변경한다. 원장 유형의 명칭과 잔액이 0인 경우의 기록 여부는 구현 시 확정한다.
- 기존 크레딧 원장은 삭제하지 않는다. 소멸 처리 후에도 원장 합계와 회원 잔액이 일치해야 한다.

### 4. 인증과 출입 권한

- 탈퇴 시 해당 회원의 모든 유효한 리프레시 토큰과 활성 출입 키를 폐기한다.
- 탈퇴 회원은 로그인과 토큰 재발급을 할 수 없다.
- 기존 액세스 토큰이 남아 있어도 탈퇴 완료 이후 보호 API 요청을 거절한다. JWT에서 닉네임을 제거하거나 프론트 토큰을 삭제하는 것만으로는 충족되지 않는다.
- 출입 검증도 탈퇴 상태 또는 폐기된 출입 키를 근거로 거절해야 한다.
- 프론트는 성공 응답을 받은 뒤 인증 상태와 저장된 토큰, 해당 회원의 출입 키 캐시를 정리하고 홈 또는 로그인 화면으로 이동한다.

현재 [인가 정책](authorization-policy.md)은 정지 회원의 액세스 토큰을 만료 전까지 허용하는 구현을 설명한다. 탈퇴 즉시 차단은 추가 요구사항이며, 모든 비활성 회원을 일괄 차단하도록 변경하면 정지 정책도 달라진다. 탈퇴 검증 방식과 정지 정책의 변경 여부를 구분해 확정하고 관련 문서·테스트를 갱신해야 한다.

### 5. 재가입과 이력 보존

- 우선 탈퇴한 이메일의 재가입을 허용하지 않는 것을 제안한다. 회원 행과 이메일 유니크 제약을 유지하는 방식이다.
- 탈퇴 전 예약, 상태 변경, 크레딧, 출입 및 문의 이력은 참조 관계를 유지한다.
- 논리적 탈퇴는 개인정보 삭제와 동일하지 않다. 이메일·닉네임 등 개인정보의 보관 기간, 익명화·삭제 범위는 별도 확정 사항이다. 이 초안은 무기한 보관을 확정하지 않는다.
- 추후 이메일 익명화나 재가입을 허용한다면 이메일 재사용 제한과의 일관성도 함께 재설계한다.

## 처리 일관성과 동시성

- 예약 확인, 회원 상태 전환, 크레딧 소멸·원장 기록, 리프레시 토큰·출입 키 폐기는 하나의 DB 트랜잭션으로 처리한다. 일부 실패 시 전체를 롤백한다.
- 단순히 진행 중인 예약을 조회한 뒤 상태를 변경하는 것만으로는 충분하지 않다. 조회 직후 다른 요청이 예약을 생성할 수 있다.
- 예약 생성·결제·출입 키 발급·토큰 재발급·크레딧 지급 등과 탈퇴가 경합해도 탈퇴 후 신규 활성 데이터나 잔액이 생기지 않도록 공통 상태 확인 및 잠금 방식을 설계한다.
- 인증 필터의 상태 확인만으로 이미 인증을 통과한 진행 중 요청까지 차단할 수는 없다. 쓰기 트랜잭션에서도 탈퇴와의 경합을 제어해야 한다.
- 기존 공간·예약·회원 잠금 순서와 충돌하지 않도록 검토한다. 탈퇴 로직에만 회원 잠금을 추가해서 동시성 문제가 해결되었다고 가정하지 않는다.
- 중복 요청이나 응답 유실 후 재시도로 크레딧 소멸이 중복 기록되어서는 안 된다. 이미 탈퇴한 계정의 재요청 응답은 인증 차단 방식과 함께 확정한다.

## 화면 및 API 설계 방향

- 마이페이지 하단에 회원탈퇴 진입점을 둔다.
- 최종 확인 화면에 복구 불가, 예약 제한, 잔여 크레딧 소멸, 동일 이메일 재가입 제한을 안내한다.
- 확인 전에는 탈퇴 요청을 보내지 않는다. 처리 중 중복 제출을 막고, 실패하면 서버 사유를 표시한다.
- 진행 중인 예약으로 차단되면 내 예약 화면으로 이동할 수 있게 한다.
- API 경로·요청 DTO·성공 응답·오류 코드·본인 재확인 방식(현재 비밀번호 등)은 구현 전에 확정한다.
- API는 허용된 필드만 받고 회원 상태나 차감할 잔액을 클라이언트 입력으로 신뢰하지 않는다.

## 검증 항목

- 정상 탈퇴 시 상태·탈퇴 시각·잔액·원장·토큰 폐기가 함께 반영된다.
- 차단 대상 예약이 있으면 회원·크레딧·토큰 상태가 변경되지 않는다.
- 완료·취소·만료·노쇼 이력만 있는 회원은 탈퇴할 수 있다.
- 기존 액세스 토큰·리프레시 토큰·출입 키로 탈퇴 후 접근할 수 없다.
- 관리자 정지 해제로 탈퇴 회원이 복구되지 않는다.
- 중복 탈퇴 요청으로 소멸 원장이 중복 생성되지 않는다.
- 예약 생성·결제·토큰 발급·크레딧 지급과 탈퇴의 동시 요청에서도 정책이 유지된다.
- 처리 중 실패하면 전체 변경이 롤백된다.
- 탈퇴 후 기존 이력의 참조가 유지되며 동일 이메일 재가입은 거절된다.

## 구현 전 확정할 사항

1. 위 제안 정책의 채택 여부: 논리적 탈퇴, 예약 제한, 잔액 소멸, 동일 이메일 재가입 불가.
2. 관리자·정지 회원의 탈퇴 허용 여부 및 본인 재확인 방식.
3. 배치 지연으로 상태가 정리되지 않은 예약의 처리 기준.
4. 개인정보 보관·익명화·삭제 범위와 기간.
5. API 계약, 원장 유형, 동시성 제어 및 액세스 토큰 즉시 차단 방식.

정책 확정 후 API 명세, ERD, 인가 정책 및 테스트 문서에 반영한다. 이 문서 작성만으로 애플리케이션 동작은 변경되지 않는다.
