# 기술적 의사결정 — 예약 동시성 제어

## 문제 상황

같은 공간·시간대에 대한 예약 요청이 거의 동시에 들어오면, 조회 시점엔 "예약 가능"으로 보이던 슬롯에 두 예약이 확정될 수 있다(기획서 2-1). 화면의 가용 여부 표시와 실제 확정 사이에는 항상 시간차가 있으므로, 화면 표시가 아니라 **예약 생성 트랜잭션 자체**에서 중복을 막아야 한다.

## 요구 조건

- 동일 공간의 동일 30분 슬롯에 대해 동시 요청이 20건 들어와도 정확히 1건만 성공한다(DoD).
- 실패한 요청은 예약·슬롯 데이터를 전혀 남기지 않는다.
- 새 인프라(분산 락, 별도 락 서버 등)를 추가하지 않는다(기획서 5-3).

## 검토한 대안

- 애플리케이션 레벨 락(synchronized, 분산 락) — 인프라가 늘고 다중 인스턴스 환경에서 신뢰하기 어려움. 이번 MVP 범위 밖.
- 비관적 락(`SELECT ... FOR UPDATE`) — 후보였으나, 슬롯 단위 유니크 제약으로 더 단순하게 동일 효과를 낼 수 있음.
- **DB 유니크 제약 + 트랜잭션 롤백** (채택)

## 선택 및 근거

- 슬롯 단위를 30분으로 통일하고, `reservation_slot`에 `UNIQUE(space_id, slot_start)`를 적용한다.
- 예약 생성 트랜잭션 순서: 회원/공간/시간 검증 → 가격 계산 → **슬롯 확보(유니크 제약 위반 시 예외)** → Mock 결제 승인 → 모두 성공한 경우에만 CONFIRMED 예약 + 가격 스냅샷 + 슬롯 + 최초 상태 이력 저장.
- 슬롯 유니크 제약 위반은 409(`RESERVATION_SLOT_CONFLICT`), 결제 승인 실패는 422(`PAYMENT_DECLINED`)로 응답하고, 두 경우 모두 트랜잭션 전체를 롤백한다.
- 분산 락 등 새 인프라 없이 MySQL 제약과 트랜잭션 범위 안에서 구현한다.

## 검증 방법

- Testcontainers로 실제 MySQL을 띄우고, 동일 공간·슬롯에 대해 다중 스레드/커넥션으로 동시 예약 생성 요청을 재현.
- 정확히 1건만 CONFIRMED로 남고, 나머지는 예외로 롤백되어 예약·슬롯 레코드가 남지 않는지 확인.
- 결과와 측정 조건(동시 요청 수, 커넥션 풀 크기 등)은 구현 완료 후 이 문서에 추가한다.

## 남은 한계

- 대기 없이 즉시 실패하는 구조라, 실패한 사용자에게 다른 시간대를 안내하는 UX는 프론트엔드 책임으로 남는다.
- 슬롯 단위가 30분보다 세분화되면(예: 15분) 유니크 제약과 가격 계산 로직을 함께 재검토해야 한다.
