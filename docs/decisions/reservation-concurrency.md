# 기술적 의사결정 — 예약 동시성 제어

> **2026-09-15 갱신**: `docs/core-domain-decisions.md` §2·§4 반영 — 예약 생성이 2단계(HOLD → 결제)로 바뀌면서 동시성 시나리오가 "슬롯 확보"와 "연장"까지 넓어짐.

## 문제 상황

같은 공간·시간대에 대한 예약 요청이 거의 동시에 들어오면, 조회 시점엔 "예약 가능"으로 보이던 슬롯에 두 예약이 확정될 수 있다(기획서 2-1). 화면의 가용 여부 표시와 실제 확정 사이에는 항상 시간차가 있으므로, 화면 표시가 아니라 **슬롯 INSERT 자체**에서 중복을 막아야 한다.

## 요구 조건

- 동일 공간의 동일 30분 슬롯에 대해 동시 요청이 20건 들어와도 정확히 1건만 성공한다(DoD).
- 실패한 요청은 예약·슬롯 데이터를 전혀 남기지 않는다.
- 연장 요청도 신규 요청과 동일하게 같은 슬롯을 두고 경합할 수 있다 — 먼저 커밋한 쪽이 이긴다.
- 새 인프라(분산 락, 별도 락 서버 등)를 추가하지 않는다(기획서 5-3).

## 검토한 대안

- 애플리케이션 레벨 락(synchronized, 분산 락) — 인프라가 늘고 다중 인스턴스 환경에서 신뢰하기 어려움. 이번 MVP 범위 밖.
- 비관적 락(`SELECT ... FOR UPDATE`) — 후보였으나, 슬롯 단위 유니크 제약으로 더 단순하게 동일 효과를 낼 수 있음.
- **DB 유니크 제약 + 트랜잭션 롤백** (채택)

## 선택 및 근거

### 점유 vs 락

**점유를 슬롯 행(row)으로 표현한다.** 락으로 자원을 잡으면 "잡고 있는 동안 아무도 못 쓴다"는 뜻이 되어, 사용자가 결제 확인 페이지를 보는 몇 분 동안 DB 커넥션/락을 물고 있게 된다. 대신 슬롯 단위를 30분으로 통일하고, `reservation_slot`에 `UNIQUE(space_id, slot_start)`를 적용해 "행이 존재하면 점유"로 표현한다. 만료 시각(`hold_expires_at`)을 함께 두어 "데이터로 표현한 락"을 만든다.

### 예약 생성(HOLD) 트랜잭션

1. 회원/공간/시간 검증 → 가격 계산
2. 대상 슬롯의 만료된 `HELD`를 조건부 UPDATE로 `EXPIRED` 전이 + 슬롯 삭제 — **배치를 기다리지 않는다.** 만료 배치는 별도로 돌지만 정합성의 유일한 보장선은 아니다("배치는 청소부지 심판이 아니다").
3. **슬롯 확보(유니크 제약 위반 시 예외)** → `HOLD` 생성

슬롯 유니크 제약 위반은 409(`RESERVATION_SLOT_CONFLICT`)로 응답하고 전체 롤백한다. 결제(크레딧 차감)는 별도 트랜잭션(`POST /reservations/{id}/pay`)에서 처리하며, 슬롯 INSERT와 결제 승인을 더는 하나의 트랜잭션으로 묶지 않는다 — 슬롯을 잡아두는 동안 결제 확인 페이지에 머무를 시간을 주기 위함이다. *(2026-09-15 정정 — 기존에는 "슬롯 확보 → Mock 결제 승인"이 한 트랜잭션이었음)*

### 사전 검사는 규칙이 아니다 (TOCTOU)

확인 시점(`GET /spaces/{id}/slots`)과 사용 시점(슬롯 INSERT) 사이에 타 사용자가 점유할 수 있으므로, 사전 검사는 화면 표시용 참고값일 뿐이다. 슬롯 INSERT의 UNIQUE 위반이 충돌 판정의 유일한 진실이며, 같은 에러를 두 곳(사전 검사 + INSERT 예외)에서 처리하지 않는다.

### 연장 ↔ 신규 예약 동시 요청 — 선착순

연장도 신규도 같은 `reservation_slot`에 같은 `(space_id, slot_start)`를 INSERT하는 행위이므로, 먼저 커밋한 쪽이 이긴다. 현재 이용 중인 사용자에게 우선권을 주지 않는다 — 우선권을 주면 판정이 상대방 상태에 의존하는 경합 지점이 하나 더 생기고, "예약 가능"을 보고 요청한 신규 예약자에게 거절 사유를 설명할 수 없기 때문이다.

| 경합 | 처리 |
| --- | --- |
| 연장 ↔ 신규 (같은 슬롯) | UNIQUE 위반 → 진 쪽 409 |
| 연장 ↔ 연장 (중복 제출) | `WHERE id=:id AND end_time=:expectedEnd` 낙관적 검사 |
| 연장 ↔ 취소/체크아웃 | 조건부 UPDATE에 `AND status IN ('CONFIRMED','IN_USE')` |

## 검증 방법

- Testcontainers로 실제 MySQL을 띄우고, 동일 공간·슬롯에 대해 다중 스레드/커넥션으로 동시 예약 생성 요청을 재현.
- 정확히 1건만 `HOLD`로 남고, 나머지는 예외로 롤백되어 예약·슬롯 레코드가 남지 않는지 확인.
- 연장 ↔ 신규, 연장 ↔ 연장 동시 요청도 동일한 방식으로 재현해 하나만 성공하는지 확인.
- 결과와 측정 조건(동시 요청 수, 커넥션 풀 크기 등)은 구현 완료 후 이 문서에 추가한다.

## 남은 한계

- 대기 없이 즉시 실패하는 구조라, 실패한 사용자에게 다른 시간대를 안내하는 UX는 프론트엔드 책임으로 남는다.
- 슬롯 단위가 30분보다 세분화되면(예: 15분) 유니크 제약과 가격 계산 로직을 함께 재검토해야 한다.
