# 기술적 의사결정 — 예약 요청 멱등성

## 문제 상황

예약 생성은 Mock 결제를 동반한다. 네트워크 재시도나 사용자의 중복 클릭으로 동일한 예약 생성 요청이 여러 번 전송되면, 결제와 예약이 중복 처리될 위험이 있다.

## 요구 조건

- 동일한 예약 생성 요청을 같은 Idempotency-Key로 3회 중복 제출해도 결제·예약 확정은 한 번만 처리된다(DoD).
- 같은 키로 다른 내용의 요청이 오면 충돌로 처리한다.
- 서로 다른 키로 같은 시간을 요청하는 것은 멱등성이 아니라 예약 동시성 규칙(`reservation-concurrency.md`)이 처리한다 — 두 개념을 혼동하지 않는다.

## 선택 및 근거

- 예약 생성처럼 결제가 결부된 POST 요청은 `Idempotency-Key`(UUID) 헤더를 필수로 받는다(API 명세서 1-7).
- 동일 키로 재요청 시 서버는 새로 처리하지 않고 **최초 처리 결과를 그대로 반환**한다(성공이든 실패든).
- 키·요청 내용의 매핑은 예약 담당(이태호) 트랜잭션 안에서 처리하며, 결제 담당(백한비)의 Mock 결제 승인 호출도 같은 키로 idempotent하게 동작해야 한다.

## 검증 방법

- 같은 Idempotency-Key로 동일 요청을 3회 연속 전송해 응답이 동일하고, `payment`/`reservation` 레코드가 1건만 생성되는지 확인.
- 같은 키로 내용이 다른 요청을 보냈을 때의 충돌 처리 정책은 구현 시 확정하고 이 문서에 추가한다.

## 남은 한계

- Idempotency-Key의 서버 측 보관 기간(TTL)은 아직 정하지 않음 — 구현 시 결정하고 문서화한다.
