## 서비스 개요

- 서비스명: Slot Key — "시간을 Slot으로 나누고, 예약한 Slot이 하나의 Key가 된다."
- 회의실·공유오피스를 30분 단위로 예약하고, 예약 상태·이용 시간에 맞춰 출입 권한(Mock Door)을 제공하는 서비스.
- 예약은 2단계로 처리한다: ① 슬롯 확보 시 `HOLD` 상태로 생성(결제 대기, 10분 후 자동 만료) → ② 결제 확인 페이지에서 크레딧 차감에 성공하면 `CONFIRMED`로 확정. *(2026-09-15 정정 — 기존에는 "하나의 트랜잭션으로 즉시 처리, 별도 결제 대기 상태 없음"이었으나, 결제 확인 단계를 두기로 하면서 `HOLD`가 그 대기 상태가 되었다.)*

## 서비스 대상과 가치 가설

- **주요 도입 고객**: 다수의 오피스 계열 건물을 보유한 건물주. 보유 공간의 예약·이용을 서비스로 제공하려는 주체를 대상으로 한다.
- **최종 이용자**: 건물에 있는 회의실·공유오피스를 필요한 시간에 찾아 예약하고 이용하는 회원. 웹 앱의 관리자 계정은 공간을 운영하는 역할이며, 현재 시스템에 건물주라는 별도 계정 유형이 있는 것은 아니다.

이 서비스가 두 대상에게 유용해질 수 있는 이유는 다음과 같다. 기대 효과는 기능에서 도출한 **가설**이며, 실제 이용률·운영 시간 절감·수익 증가는 아직 측정된 성과가 아니다.

| 제공 방식 (현재 MVP 범위) | 기대되는 효용 |
| --- | --- |
| 관리자가 공간의 위치·수용 인원·운영시간·요금·사진을 등록하고, 이용자가 공간과 날짜별 예약 가능 시간을 조회한다. | 건물주는 예약 가능한 공간과 시간을 이용자에게 제시할 수 있고, 이용자는 문의 없이 조건을 비교해 공간을 찾을 수 있다. |
| 이용자가 30분 슬롯을 확보·확정하고, 서버가 겹치는 예약과 상태 변경을 검사한다. | 건물주는 같은 시간대의 중복 예약을 줄일 수 있고, 이용자는 선택한 시간의 예약 결과를 명확히 확인할 수 있다. |
| 예약자 본인의 확정된 예약에 도어 토큰을 발급하고, 모의 출입 시 예약자 일치·예약 상태·토큰 유효성 및 이용 시간을 검증하며 시도를 기록한다. (회원 상태는 출입 검증 시점에 재검사하지 않음) | 예약 정보와 이용 권한을 연결해 운영자가 이용 이력을 확인하고, 이용자는 예약에 따른 출입 절차를 거칠 수 있다. 현재 출입 검증은 Mock Door다. |
| 관리자가 공간 정보를 수정하고 전체 예약·회원 목록 및 감사 로그 API를 조회한다. | 운영자는 공간 운영 규칙과 변경 이력을 확인하며 예약 관련 문제를 추적할 수 있다. 감사 로그 조회 화면은 아직 없다. |

현재 MVP는 공간 단위의 예약·운영 기능을 제공한다. `Space`에 건물 또는 건물주 소속 정보가 없고 권한도 공통 `ADMIN` 역할을 사용하므로, **건물주별 데이터 분리, 여러 건물의 포트폴리오 관리, 이용률 분석·정산**을 제공한다고 해석해서는 안 된다. 실제 출입 하드웨어와 결제도 연동하지 않는다. 건물주 대상의 효용을 검증하려면 이후 해당 운영 기능과 실사용 지표를 별도로 확인해야 한다.

## 해결하려는 문제 (기획서 2장)

1. **동시 예약**: 같은 공간·시간대를 두 사용자가 거의 동시에 예약하면 서버가 확실히 하나만 확정해야 한다. 화면의 예약 가능 여부는 참고용 스냅샷일 뿐, 실제 차단은 예약 생성 시점의 DB 제약으로 한다.
2. **예약 상태와 출입 권한의 불일치**: 예약 취소·이용 종료 이후에는 기존 출입 토큰이 남아 있어도 출입을 거절해야 한다. 출입 요청마다 예약자 본인 일치·예약 상태·토큰 폐기 여부·허용 시간을 함께 확인한다. (단, 계정 정지 회원의 경우 현재 구현은 무상태 JWT 특성상 기발급 Access Token이 만료 전까지 인증을 통과하고 출입 검증 서비스도 회원 행의 상태를 재검사하지 않아, 정지 즉시 기존 출입 토큰이 차단되지 않는다. 정지 즉시 출입/API 차단은 별도 코드 과제로 다룬다.)

이 프로젝트는 인증·인가를 "로그인 성공 여부"에서 역할 기반 인가 + 소유권 기반 인가 + 상태 기반 인가 + 시간 기반 인가로 확장하는 것을 핵심 목표로 삼는다.

## Out of Scope (4-2, 의도적 제외)

- 소셜 로그인, 모바일 앱, 다국어 지원
- 실제 도어 하드웨어 연동 (Mock Door API로 대체), 실제 PG 결제 (크레딧 잔액 차감으로 대체 — 셀프 충전도 범위 밖)
- **예약 변경(시간대 이동)** 및 자동 재예약 보장 (취소 후 재생성만 허용). **연장(기존 슬롯 유지, 종료 시각만 늘리는 것)은 별개이며 MVP에 포함한다** — 기존 슬롯을 해제하지 않으므로 변경과 달리 실패해도 원 예약이 무손상이다. *(2026-09-15 명확화)*
- 예약 대기(대기번호)·승격, 관리자 점검 시간 블록, 셀프 크레딧 충전, 크레딧 회수, 출입 키 공유·동행자 초대, HOLD 시간의 사용자 연장(만료 시각 자체를 늘리는 것 — 예약의 "연장"과는 다른 개념) *(2026-09-15 추가, `core-domain-decisions.md` §10)*
- Refresh Token Family 전체 폐기/재사용 공격 추적, Access Token 블랙리스트 (로그아웃은 Refresh Token만 폐기, Access Token은 만료로 처리)
- 여러 요금 구간을 가로지르는 예약 (하나의 예약은 단일 요금 구간)
- 동적/피크타임 요금, 회원 등급별 차등 요금
- 공간 소유자의 개별 예약 강제 취소 (강제 취소는 ADMIN 경로에서만)
- 팀 관리자의 대리 체크인·대리 취소 (예약자 본인만)
- 권한·회원 상태 조회용 분산/로컬 캐시 (매 요청 DB 재조회 없이 Access JWT 클레임으로 검증하며, 회원 상태 확인은 로그인·refresh 시점에만 수행)

## 성공 기준 (11장 DoD 발췌 — 전체는 README 참고)

- 동일 공간·시간에 20개 동시 예약 요청 중 정확히 1건만 성공, 실패 요청의 예약·슬롯 데이터는 남지 않는다.
- 같은 Idempotency-Key로 결제 요청을 3회 순차 제출해도 크레딧 차감 1회, CONFIRMED 확정, 매번 동일한 응답(상태 CONFIRMED 및 예약 ID 일치)을 반환한다.
- 예약 취소 직후 기존 도어 토큰 검증은 실패한다.
- 체크아웃(`COMPLETED`) 후에는 활성 출입 토큰이 폐기되며 새 토큰 재발급이 불가하다.
- 계정 정지(`SUSPENDED`) 후 로그인 및 토큰 재발급(refresh) 요청 시 `ACCOUNT_INACTIVE`(403)로 차단된다. (무상태 JWT 특성상 기발급 유효 Access Token은 만료 전까지 일반 보호 API를 통과하며, 출입 검증 서비스도 회원 상태를 재확인하지 않으므로 정지 직후 출입 및 API 즉시 차단은 별도 코드 과제다.)
- 잔액 부족 등으로 결제 실패 시 예약 및 슬롯은 `HELD`로 유지되고 멱등 키가 소진되지 않아 관리자 지급 등으로 잔액 확보 후 HOLD 만료 전 재결제가 가능하다.
- 공간 요금이 변경돼도 기존 예약 금액은 유지되고, 새 예약에만 변경된 요금이 적용된다.
- 임의 시점에 `SUM(credit_transaction.amount) == member.balance`가 항상 성립한다. *(2026-09-15 추가)*
- 시작+15분까지 미체크인이면 노쇼로 전이되고 슬롯은 반환되지만 환불은 없다. *(2026-09-15 추가)*
- `HOLD` 상태에서 결제 확인 페이지에 머무는 동안 관리자가 가격을 바꿔도, 결제 시 `space.version` 불일치로 거절된다(가격이 아니라 버전으로 비교). *(2026-09-15 추가)*
