# 핵심 비즈니스 로직 확정본 — 예약 / 체크인

> 리팩토링 논의 결과 확정본. `docs/` 하위 문서(ERD, API 명세, 상태 전이, 테스트 전략)와 README, 기획서는 **이 문서를 기준**으로 갱신한다.
> 충돌 시 이 문서가 우선한다.

---

## 0. 설계 원칙

이 프로젝트의 모든 결정은 아래 네 가지에서 파생된다.

1. **핵심은 예약이다.** 체크인·체크아웃은 예약의 생명주기 일부이며 별도 도메인이 아니다. 결제는 예약의 한 단계이지 자기 상태 기계를 갖는 도메인이 아니다.
2. **flow는 길게, 폭은 좁게.** 예약의 단계는 늘리되 외부 연동(PG, 스마트락, 알림)은 늘리지 않는다.
3. **사람이 기다리는 시간은 락이 아니라 데이터로 표현한다.** 락은 기계가 잡고 기계가 놓는다.
4. **되돌릴 수 없는 작업은 시스템이 암묵적으로 수행하지 않는다.** 사용자가 명시적으로 선택하게 한다.

## 1. 결제 — Mock 결제 + 크레딧 단위

### 1-1. 확정

- **선불**. 후불은 채택하지 않는다. 후불이면 취소·노쇼 환불 정책이 전부 무의미해진다.
- **Mock 결제 서비스가 크레딧 잔액을 차감**하는 구조. 외부 PG 연동 없음.
- **실패 조건은 잔액 부족 하나뿐.** 랜덤 실패는 만들지 않는다 — 같은 입력에 다른 결과가 나오면 테스트가 불가능하다. 잔액 부족은 입력만 맞추면 100% 재현된다.
- `payment` 테이블은 **삭제**하고 `credit_transaction` 원장으로 단일화한다.

### 1-2. 크레딧 정의

- **단위: 1 크레딧 = 1원, `int`**. 별도 환율을 두지 않는다. `space.price_per_slot`(원)과 같은 단위여야 변환 코드가 필요 없다.
- 크레딧은 **결제 수단이 아니라 이용 한도**다. 현금 → 크레딧 전환(셀프 충전)은 범위 밖이며, 도입하면 PG 문제가 그대로 돌아온다.

### 1-3. 지급 경로 (2개)

| 경로 | 트리거 | type |
| --- | --- | --- |
| 가입 지급 | 회원가입과 **동일 트랜잭션**에서 자동 | `SIGNUP_GRANT` |
| 관리자 지급 | `POST /admin/members/{id}/credits` | `ADMIN_GRANT` |

- 가입 지급액은 **설정값**(`app.credit.signup-grant`)으로 관리한다. 하드코딩하지 않는 이유: 테스트 프로파일에서 값을 낮춰 잔액 부족 시나리오를 검증하기 위함.
- 관리자 지급: 사유 1~500자 필수, **자기 자신에게는 지급 불가**(`actor_id != member_id`), **지급만 가능**(회수 없음 — 회수는 정산·분쟁 처리를 열기 때문에 범위 밖).
- 관리자 지급은 원장과 `audit_log` **양쪽**에 기록한다. 원장은 "얼마가 들어왔나", 감사 로그는 "누가 왜 줬나"로 역할이 다르다.

### 1-4. 원장 (`credit_transaction`)

```
credit_transaction (
  id, member_id,
  amount,          -- 부호 있음: 지급/환급 +, 차감/위약금 -
  type,            -- SIGNUP_GRANT, ADMIN_GRANT, RESERVATION_CHARGE, REFUND, PENALTY
  reservation_id,  -- NULL 허용 (지급 건은 예약과 무관)
  balance_after,
  reason,          -- NULL 허용 (ADMIN_GRANT만 필수)
  created_at
)
INDEX (member_id, created_at)
```

- **부호를 `amount`에 담는다.** `SUM(amount)`가 곧 잔액이 되어야 검증이 쉽다.
- `balance_after`를 남기는 이유: 잔액이 안 맞을 때 어느 시점부터 틀어졌는지 추적할 수 있다.
- **차등 환불은 두 줄로 분리 기록한다.**
  ```
  REFUND  +10000  (전액 환급)
  PENALTY  -5000  (취소 위약금 50%)
  ```
  한 줄로 `REFUND +5000`을 쓰면 원금과 차감을 구분할 수 없고, 위약금 총액 집계도 불가능하다.

### 1-5. 차감과 지급

차감은 **조건부 UPDATE**로 처리한다. 엔티티 필드를 수정하고 dirty checking에 맡기면 갱신 유실(lost update)이 발생한다.

```sql
UPDATE member SET balance = balance - :amount
WHERE id = :id AND balance >= :amount
-- 영향 행 0 → INSUFFICIENT_BALANCE
```

지급(증가)은 실패 조건이 없으므로 조건부 UPDATE가 필요 없다.

```sql
UPDATE member SET balance = balance + :amount WHERE id = :id
```

## 2. 예약 flow — 2단계 (HOLD → 결제)

### 2-1. 결제 확인 페이지를 둔다

클릭 한 번에 크레딧이 빠지는 것은 UX상 거칠고, 실제 서비스는 금액 확인 단계를 둔다. 이 단계가 있으므로 **사용자가 화면에 머무는 동안 슬롯을 유지해야 한다.**

```
① POST /reservations
   규칙 검사 → 만료 HELD 정리 → 슬롯 INSERT(UNIQUE) → HELD 생성
   (hold_expires_at = now + 10분)
        ↓
   [결제 확인 페이지]  금액 / 잔액 / 예약 정보 표시
        ↓
② POST /reservations/{id}/pay
   space.version 비교 → 크레딧 차감 → CONFIRMED
```

- ②의 조건부 UPDATE: `WHERE id=:id AND status='HELD' AND :now < hold_expires_at`
- **`Idempotency-Key`는 ②에 붙인다.** 돈이 움직이는 지점이 ②이기 때문.
- 만료 후 결제 시도 → 409.

### 2-2. HOLD의 역할을 정확히 할 것

> **동시 예약 차단은 `UNIQUE(space_id, slot_start)`가 담당한다. HELD는 결제 대기 구간을 위한 장치다.**

이 둘을 혼동하면 안 된다. 두 요청이 같은 슬롯에 INSERT하면 DB가 하나만 통과시키며, 이는 HELD 유무와 무관하게 작동한다. HELD는 그 슬롯 행에 붙는 "만료되는 점유"라는 성격일 뿐이다.

### 2-3. 만료 홀드 정리 — 배치에 의존하지 않는다

`UNIQUE` 제약은 "만료된 홀드는 점유가 아니다"를 표현하지 못한다. 만료된 행이 남아 있으면 새 예약이 UNIQUE 위반으로 실패한다.

```
예약(HOLD) 생성 시:
  1. 대상 슬롯의 만료된 HELD를 조건부 UPDATE로 EXPIRED 전이 + 슬롯 행 삭제
  2. 슬롯 INSERT 시도
  3. UNIQUE 위반 → 409 (살아있는 점유가 있는 것)
```

**배치는 청소부지 심판이 아니다.** 만료 배치는 별도로 돌리되, 정합성은 위 1번이 보장한다. 배치가 1분 늦어도 사용자는 예약할 수 있어야 한다.

## 3. 상태 전이 — 7개

### 3-1. 현재 상태와 과거 상태 둘 다 저장

```
reservation.status          ← 현재 상태 (컬럼)
reservation_status_history  ← 전이 로그 (테이블)
```

이력만 두고 현재 상태를 계산하는 방식(이벤트 소싱)은 채택하지 않는다. 예약 목록을 상태로 필터링·정렬할 때 매번 이력을 전부 읽어야 하고 인덱스를 걸 수 없다. **현재 상태는 의도적으로 중복 저장한다.**

```
reservation_status_history (
  id, reservation_id,
  from_status,   -- 최초 생성은 NULL
  to_status,
  changed_by,    -- member_id, 시스템 작업은 NULL
  reason,        -- 관리자 강제 취소 등
  changed_at
)
```

**성공한 전이만 기록한다.** 조건부 UPDATE의 영향 행이 1일 때만 INSERT하며, 같은 트랜잭션에서 처리한다.

### 3-2. 상태 기계

```
HELD ─(결제 성공)──→ CONFIRMED ─(최초 체크인)→ IN_USE ─(체크아웃/종료시각)→ COMPLETED
  │                      │
  └─(10분 경과)→ EXPIRED ├─(취소: now < start_time)→ CANCELLED
                         └─(start + 15분 미체크인)→ NO_SHOW
```

| 상태 | 진입 조건 | 슬롯 | 환불 | 토큰 |
| --- | --- | --- | --- | --- |
| `HELD` | 슬롯 확보, 미결제 | 점유 | — | **발급 불가** |
| `EXPIRED` | 10분 내 미결제 | **삭제** | — | — |
| `CONFIRMED` | Mock 결제 성공(크레딧 차감) | 점유 | — | 발급 가능 |
| `IN_USE` | 최초 체크인 성공 | 점유 | — | 재입장 허용 |
| `COMPLETED` | 체크아웃 또는 종료 시각 경과 | 유지 | 없음 | 폐기 |
| `CANCELLED` | 시작 전 취소 | **삭제** | 100% / 50% | 폐기 |
| `NO_SHOW` | 시작 + 15분까지 미체크인 | **삭제** | 없음 | 폐기 |

`NO_SHOW`를 `CANCELLED`와 합치지 않는 이유: 환불 정책이 다르고, 운영상 "취소한 사람"과 "안 온 사람"은 완전히 다르다.

### 3-3. 허용되지 않는 전이

- `EXPIRED → 무엇이든`
- `CANCELLED → 무엇이든`
- `COMPLETED → 무엇이든` — 체크아웃은 되돌릴 수 없다
- `HELD → IN_USE` — 결제 없이 입장 불가
- `NO_SHOW → IN_USE` — 15분 지나면 늦음
- `IN_USE → CANCELLED` — 시작 후에는 취소가 아니라 체크아웃

### 3-4. 전이 주체

| 전이 | 주체 |
| --- | --- |
| `HELD → EXPIRED` | 배치 + 예약 생성 시점 정리 |
| `CONFIRMED → IN_USE` | 출입 검증의 부수 효과 |
| `CONFIRMED → NO_SHOW` | 배치 |
| `IN_USE → COMPLETED` (자동 퇴실) | 배치 |
| `HELD/CONFIRMED/IN_USE → CANCELLED` (강제 취소) | 관리자 (6-4) |
| 나머지 | 사용자 요청 |

**자동 퇴실 시 `checked_out_at`은 배치 실행 시각이 아니라 `end_time`을 넣는다.** 배치가 15:00:03에 돌았다고 퇴실 시각이 15:00:03이면 이용 시간 집계가 예약 구간을 삐져나간다. 배치 실행 시각은 시스템의 사정이지 도메인 사실이 아니다.

## 4. 동시성

### 4-1. 점유 vs 락 — 점유로 처리한다

락으로 자원을 잡는 것은 "잡고 있는 동안 아무도 못 쓴다"는 뜻이다. 사용자가 결제 확인 페이지를 보는 몇 분 동안 DB 커넥션과 락을 물고 있으면 동시 접속자 수만큼 커넥션이 고갈된다.

**점유를 슬롯 행(row)으로 표현한다.** 행이 존재하면 점유이고, `UNIQUE(space_id, slot_start)`가 중복을 막는다. 만료 시각을 함께 두어 "데이터로 표현한 락"을 만든다.

### 4-2. 슬롯 가용성은 사전 검사 대상이 아니다 (TOCTOU)

```
14:00:00.000  "9/17 14:00 비었어?"  → "네"     (검사 통과)
14:00:00.050  남이 그 슬롯 INSERT 성공
14:00:00.100  내가 INSERT 시도       → UNIQUE 위반
```

확인 시점(Time Of Check)과 사용 시점(Time Of Use) 사이에 타 사용자가 점유할 수 있으므로, **사전 검사는 화면 표시용 참고값일 뿐이다.**

| | 역할 |
| --- | --- |
| `GET /spaces/{id}/slots` | 화면에 회색 표시. 규칙 아님 |
| 슬롯 INSERT의 UNIQUE 위반 | **유일한 진실** |

사전 검사를 규칙에 넣으면 같은 에러를 두 곳(검사 + INSERT 예외)에서 처리하게 되고, 검사를 믿고 예외 처리를 생략하면 500이 튀어나간다. **충돌 판정 지점을 한 곳에 모은다.**

```java
ruleEngine.validate(ctx);        // 슬롯 검사 없음
try {
    slotRepository.saveAll(slots);
    slotRepository.flush();
} catch (DataIntegrityViolationException e) {
    throw new SlotConflictException();   // 409 — 여기 한 곳
}
```

> 4-1과 4-2는 같은 논지의 두 얼굴이다. 발표에서는 하나로 묶는다.

### 4-3. 연장 ↔ 신규 예약 동시 요청 — 선착순

연장도 신규도 같은 `reservation_slot`에 같은 `(space_id, slot_start)`를 INSERT하는 행위이므로, **먼저 커밋한 쪽이 이긴다.**

현재 이용 중인 사용자에게 우선권을 주지 않는다. 우선권을 주면 ① 판정이 상대방 상태에 의존하게 되어 경합 지점이 하나 더 생기고, ② 조회에서 "예약 가능"을 보고 요청한 신규 예약자에게 거절 사유를 설명할 수 없다.

부수 경합 처리:

| 경합 | 처리 |
| --- | --- |
| 연장 ↔ 신규 (같은 슬롯) | UNIQUE 위반 → 진 쪽 409 |
| 연장 ↔ 연장 (중복 제출) | `WHERE id=:id AND end_time=:expectedEnd` 낙관적 검사 |
| 연장 ↔ 취소/체크아웃 | 조건부 UPDATE에 `AND status IN ('CONFIRMED','IN_USE')` |

## 5. 가격 — 서로 다른 두 장치

혼동하지 말 것. 이름을 나눠서 쓴다.

### 5-1. 가격 스냅샷 (저장한다)

예약 확정 시 **서버가 직접 읽은** `space.price_per_slot`을 `reservation.price_per_slot_snapshot`에 복사한다. 이후 관리자가 공간 가격을 변경해도 기존 예약의 금액은 불변이다.

`total_amount = price_per_slot_snapshot × 점유 슬롯 수`

### 5-2. 가격 확인 (저장하지 않는다, 낙관적 검증)

사용자가 결제 확인 페이지에 머무는 동안 관리자가 가격을 바꿀 수 있다. HOLD 생성 시 `space.version`을 응답에 실어 보내고, 결제 요청에 되돌려받아 비교한다. 다르면 거절하고 초기 페이지로 돌아간다.

- **비교 기준은 가격 값이 아니라 `space.version`이다.** 5000 → 6000 → 5000으로 돌아오면 가격 비교는 통과해버린다(ABA 문제).
- **클라이언트가 보낸 금액은 "사용자가 동의한 가격"일 뿐 청구액이 아니다.** 서버는 비교만 하고, 차감과 스냅샷은 서버가 직접 읽은 현재 값으로 한다. 이를 지키지 않으면 클라이언트에서 금액을 1원으로 바꿔 보내는 공격이 통한다.

## 6. 취소 · 노쇼 · 환불

### 6-1. 취소 가능 시점과 환불률

| 시점 | 가능 | 환불 |
| --- | --- | --- |
| 시작 1시간 전까지 | 가능 | 100% |
| 시작 1시간 전 ~ 시작 시각 | 가능 | 50% (`PENALTY` 50% 기록) |
| 시작 이후 | **불가** | — |

시작 이후에는 취소가 아니라 **체크아웃**으로 종료한다.

| | 상태 조건 | 슬롯 | 환불 |
| --- | --- | --- | --- |
| 취소 | `CONFIRMED` && `now < start_time` | 삭제 | 100% / 50% |
| 체크아웃 | `IN_USE` | 유지 | 없음 |

### 6-2. 취소 처리 순서

```
1) 조건부 UPDATE로 상태 전이  ← 문지기
   UPDATE reservation SET status='CANCELLED', cancelled_at=:now
   WHERE id=:id AND status='CONFIRMED' AND :now < start_time
   → 영향 행 0이면 즉시 중단, 409

── 이하 같은 트랜잭션 ──
2) 슬롯 행 삭제
3) 활성 토큰 revoke
4) 크레딧 환급 + 원장 기록 (REFUND 전액 + PENALTY 차감)
5) 상태 이력 저장
6) COMMIT
```

- **1번이 문지기 역할을 한다.** 동시에 취소 요청이 10개 와도 조건부 UPDATE에서 하나만 통과하므로 2~5번이 중복 실행되지 않는다. 별도의 락이 필요 없다.
- 크레딧이 같은 DB에 있으므로 2~4번이 하나의 트랜잭션이다. **"취소는 성공했는데 환불은 실패한" 중간 상태가 구조적으로 존재할 수 없다.** 외부 PG였다면 커밋 후 환불 호출 + 재처리 큐가 필요했을 자리다.

### 6-3. 노쇼

- **판정: 시작 시각 + 15분까지 `IN_USE`로 전이되지 않으면 `NO_SHOW`.**
  이 값은 **최초 체크인 마감 시각과 동일한 하나의 값**이다. 두 개의 규칙이 아니다.
- 처리: **슬롯 행 전부 삭제** + 토큰 폐기 + **환불 없음**.
- 이미 지난 첫 슬롯은 재예약 시 `NotPastRule`이 자동으로 걸러주므로 별도 처리가 필요 없다.
- 슬롯을 반환하는 이유: 2시간 예약의 노쇼면 1시간 45분이 통째로 죽는다. **벌은 돈으로, 자원은 회수한다.**

### 6-4. 관리자 강제 취소와 환불

관리자 강제 취소(`POST /admin/reservations/{id}/force-cancel`)는 사용자 취소(6-1)와 달리 **시작 시각과 무관하게** 가능하다. 취소 사유가 사용자가 아니라 운영 쪽 결정이므로 **위약금은 없고**, 결제한 금액은 전액 돌려준다.

| 취소 직전 상태 | 슬롯 | 환불 |
| --- | --- | --- |
| `HELD` | 삭제 | 없음 (결제한 적이 없다) |
| `CONFIRMED` | 삭제 | **100%** (연장분 포함 `total_amount` 전액, `REFUND` 1줄) |
| `IN_USE` | 삭제 | **100%** (이미 이용한 시간도 차감하지 않는다) |
| `COMPLETED` / `EXPIRED` / `NO_SHOW` / `CANCELLED` | — | 취소 불가 (409) |

처리 순서는 6-2와 같은 골격이다.

```
1) 조건부 UPDATE로 상태 전이  ← 문지기
   UPDATE reservation SET status='CANCELLED', cancelled_at=:now
   WHERE id=:id AND status=:조회 시점의 상태
   → 영향 행 0이면 즉시 중단, 409

── 이하 같은 트랜잭션 ──
2) 상태 이력 저장 (사유 포함)
3) 슬롯 행 삭제
4) 활성 토큰 revoke
5) 크레딧 환급 + 원장 기록 (REFUND 전액, HELD는 생략)
6) audit_log 기록
7) COMMIT
```

- 상태를 `status='CONFIRMED'`로 고정하지 않고 **조회한 상태 그대로**로 두는 이유: 조회와 UPDATE 사이에 다른 요청이 상태를 바꿨다면(본인 취소, 체크인 등) 0행이 되어 **환불이 두 번 나가지 않는다.**
- 본인 취소와 강제 취소가 같은 순간에 와도 한쪽만 통과하므로 환불은 정확히 1회다(12장 동시성 테스트).

## 7. 연장 — 제공함

### 7-1. 판정

| 상황 | 결과 |
| --- | --- |
| 연장 슬롯 전부 비어있음 | 성공 |
| 일부라도 점유됨 | **409.** 응답에 "가능한 최대 종료 시각" 힌트 |
| 전부 점유됨 | 409 |

**남의 점유가 `HELD`인지 `CONFIRMED`인지 구분하지 않는다.** "저건 결제 안 한 홀드니까 밀어내도 되지 않나"는 유혹이지만, ① 확인한 순간엔 미결제였는데 밀어내려는 순간 결제 완료되는 경합이 생기고, ② "슬롯 행이 존재한다 = 점유다"라는 단일 규칙이어야 버그가 숨을 곳이 없다.

유일한 예외는 **만료된 HELD**이며, 이는 "남의 점유를 밀어내는 것"이 아니라 "이미 죽은 점유를 정리하는 것"이다(2-3 참조).

### 7-2. 처리

```
[단일 트랜잭션]
end_time 낙관적 검사(WHERE id=:id AND end_time=:expectedEnd)
→ 추가 슬롯 INSERT (UNIQUE)
→ 추가 금액 크레딧 차감
→ reservation.end_time UPDATE
→ 상태 이력 저장 → COMMIT
```

- **금액**: 추가 슬롯 × **원 예약의 `price_per_slot_snapshot`**. 같은 이용 건인데 후반부만 비싸지면 사용자가 납득하지 못한다.
- **연장 가능 시점**: `now < end_time`. 끝난 예약을 되살리는 것은 연장이 아니라 새 예약이다.
- **실패해도 원 예약은 무손상**이다. 기존 슬롯을 건드리지 않기 때문.
- **연장 종료 시각 규칙**: 신규 예약과 같은 시간 규칙을 따른다 — ① 30분 단위(분·초 모두), ② 기존 예약과 같은 날짜 안(자정을 넘기는 연장 불가), ③ 공간 운영 종료 시각 이내(정각까지는 허용, +30분은 거절). 위반은 `INVALID_RESERVATION_TIME`(400). 새 종료 시각이 기존보다 늦지 않으면 `VALIDATION_FAILED`(400).

## 8. 체크인 / 체크아웃 / 출입 키

### 8-1. 시간 규칙

| 항목 | 규칙 |
| --- | --- |
| **키 발급** | 예약 확정 직후 ~ 종료 시각 전. **시간 제한 없음** |
| **최초 체크인** | `[start, start + 15분]` — **앞 여유 0분** |
| **재입장** | `(checked_in_at, end_time)` — 종료 시각 정각 거절 |
| **NO_SHOW 판정** | `start + 15분` (= 최초 체크인 마감) |

**앞 여유를 0으로 두는 이유**: 14:00~15:00(A) 다음에 15:00~16:00(B)가 연속될 때, B의 입장 가능 구간이 15:00부터 시작해야 A의 이용 구간과 겹치지 않는다. `[시작, 종료)` 반개구간으로 딱 맞아떨어진다. "직전 슬롯이 비었으면 10분 전부터 허용" 같은 동적 규칙은 체크인 판정이 남의 예약 상태에 의존하게 만들므로 채택하지 않는다.

**키 발급에 시간 제한을 두지 않는 이유**: 발급은 입장 권한이 아니다. 일찍 받아도 `start` 전엔 문이 열리지 않는다. 제한을 없애면 `TOKEN_ISSUE_TOO_EARLY` 검사가 통째로 사라지고, 예약 완료 화면에서 바로 키를 보여줄 수 있다.

> 발급은 신분증을 받는 것, 체크인은 문을 통과하는 것. 신분증이 지갑에 있다고 아무 때나 들어갈 수 있는 게 아니다.

### 8-2. 경계값 규약

```
발급     : CONFIRMED && now < end_time
최초입장 : start_time <= now <= start_time + 15m
재입장   : checked_in_at < now < end_time
```

- **시작 시각 정각은 허용** (14:00:00 체크인 성공)
- **종료 시각 정각은 거절** (15:00:00에 다음 예약자가 들어와야 함)
- 즉 `start`는 닫힌 구간, `end`는 열린 구간.

### 8-3. 토큰에 시간 정보를 박지 않는다

```
토큰은 예약을 가리키기만 한다 → 검증 시점에 예약에서 시간을 읽는다
```

이렇게 하면 ① 연장해도 토큰 재발급이 불필요하고, ② 취소 시 토큰 폐기가 늦어도 예약 상태 검사에서 걸리는 이중 방어가 된다.

### 8-4. 체크아웃

퇴실은 출입 검증으로 잡을 수 없다. Mock Door는 입장/퇴장을 구분하지 못하며, 재입장을 허용하는 이상 어떤 검증이 마지막 퇴장인지 알 수 없다. **체크아웃은 별도 API이며 예약 도메인에 속한다.**

```
POST /reservations/{id}/check-out

1) UPDATE reservation SET status='COMPLETED', checked_out_at=:now
   WHERE id=:id AND status='IN_USE'
   → 영향 행 0이면 409
── 같은 트랜잭션 ──
2) 활성 토큰 revoke
3) 상태 이력 저장
4) COMMIT
```

| 경로 | 트리거 | `checked_out_at` |
| --- | --- | --- |
| 명시적 체크아웃 | 사용자 요청 | `now` |
| 자동 퇴실 | 종료 시각 경과 (배치) | **`end_time`** |

- **슬롯 반환 없음, 환불 없음.** 예약은 시간 점유권 구매다. 조기 반납을 허용하면 부분 환불 계산 → 남은 슬롯 재판매 → 재판매된 슬롯에 원래 사용자가 재입장 시도로 연쇄된다.
- **체크아웃은 되돌릴 수 없다.** 실수로 눌렀다면 종료 시각 전까지 키를 재발급받으면 된다(활성 키 1개 제약 안에서). UI에 확인 다이얼로그를 둔다.
- **체크아웃을 안 한 것은 잘못이 아니다.** 방을 끝까지 썼다는 뜻이며 가장 흔한 경우다. 페널티 없음.

### 8-5. 키 공유

**예약당 활성 키 1개, 예약자 본인만.** 공유·양도 없음.

키를 공유 가능하게 하면 출입 로그의 감사 가치가 0이 된다. "누가 들어갔는가"에 답할 수 없는 출입 기록은 기록이 아니다. 동행자 개념은 초대 도메인(초대 발송·수락·인원 제한·동행자 선입장 여부)을 필요로 하므로 범위 밖이다.

## 9. 예약 가능 여부 판단 규칙

각 검사를 독립 규칙 객체로 분리한다. 규칙 단위로 테스트가 쪼개지고, 추가 시 클래스 하나만 늘어난다.

```java
interface ReservationRule {
    RuleResult check(ReservationContext ctx);
}
```

| 규칙 | 검사 내용 |
| --- | --- |
| `MemberActiveRule` | 관리자에게 차단(정지)된 사용자인가 |
| `WithinOperatingHoursRule` | 공간 운영시간 내인가 |
| `SlotAlignmentRule` | 30분 배수인가 |
| `NotPastRule` | 과거 시간인가 |
| `NoSelfOverlapRule` | **같은 사용자**가 그 시간에 다른 예약을 갖고 있는가 |
| `MaxDurationRule` | 1회 최대 예약 시간을 넘는가 |
| `MaxActiveReservationRule` | 사용자 동시 보유 예약 한도를 넘는가 |
| `SufficientBalanceRule` | 크레딧 잔액이 충분한가 (사전 안내용) |

**슬롯 가용성은 이 목록에 포함하지 않는다** (4-2 참조).

`SufficientBalanceRule`도 사전 검사일 뿐이며, 최종 판정은 조건부 UPDATE의 영향 행 수다. 규칙으로도 두는 이유는 잔액 부족을 미리 알려주는 편이 UX상 낫기 때문(슬롯은 조회 API가 그 역할을 한다).

## 10. 제외한 기능과 그 이유

> 무엇을 넣었는지보다 무엇을 왜 안 넣었는지가 설계 역량을 보여준다.

| 제외 | 이유 |
| --- | --- |
| **예약 변경(시간대 이동)** | 기존 슬롯을 해제한 뒤 신규 확보에 실패하거나 사용자가 번복하면 원래 자리를 복구할 수 없다(그 사이 타 사용자 점유 가능). 되돌릴 수 없는 작업은 사용자가 명시적으로 취소를 선택하게 한다. **연장은 기존 슬롯을 유지하므로 제공한다.** |
| **예약 대기(대기번호)·승격** | 회의실은 다른 시간대를 고르면 되므로 "기다릴 의사"가 약하다. 도입 시 승격 결제 시점, 승격 후 미결제 처리, 알림 인프라, 대기 중 정지·가격 변동 등 상태 기계가 줄줄이 따라온다. |
| **관리자 점검 시간** | 새 개념으로 만들면 토큰·예약·취소 전부에 예외가 생긴다. 필요 시 `reservation.type = BLOCK`(관리자 명의 예약)으로 모델링하면 새 개념이 0개가 되지만, 이번 범위에서는 제외. |
| **셀프 크레딧 충전** | 현금 → 크레딧 전환은 PG 문제 그 자체다. 도입하면 크레딧을 선택한 이유가 사라진다. |
| **크레딧 회수** | 정산·분쟁 처리를 연다. |
| **출입 키 공유·동행자 초대** | 초대 도메인이 별도로 필요하며 출입 로그의 감사 가치를 훼손한다. |
| **HOLD 시간의 사용자 연장** | 만료 시각을 사용자가 늘릴 수 있으면 자리 선점 어뷰징이 가능하다. |

### 10-1. 관리자 가격 수정이 확정 예약에 미치는 영향

**확정된 예약은 절대 깨지 않는다.** 예약 확정은 약속이며, 관리자의 가격 수정이 이미 성립한 약속을 취소할 권한은 없다. 가격 변동은 `price_per_slot_snapshot`으로 해결한다.

### 10-2. 상태 변화는 변화를 일으킨 쪽이 알린다 (push, not poll)

주기적 폴링은 ① 자원 낭비 ② 주기만큼의 지연 ③ 조회 시점과 처리 시점 사이의 또 다른 경합을 만든다. 취소 → 토큰 폐기, 취소 → 슬롯 반환 등 모든 연쇄 처리에 이 원칙을 적용한다.


## 12. 테스트 목록

> 문서에 적은 규칙은 전부 테스트로 존재해야 한다. 규칙 하나 = 테스트 하나.

### 동시성

- 같은 슬롯에 20개 동시 요청 → 정확히 1건 성공, 19건 409, 실패 요청의 예약·슬롯 데이터 잔존 없음
- 만료된 HELD가 있는 슬롯에 신규 예약 → 성공 (배치 미실행 상태에서도)
- 같은 `Idempotency-Key`로 결제 3회 → 차감 1회
- 연장 ↔ 신규 동시 요청 → 하나만 성공
- 같은 예약에 연장 요청 2회 동시 → 하나만 성공
- 같은 예약에 서로 다른 `Idempotency-Key`로 결제 N건 동시 → 정확히 1건 성공, 차감 1회, 나머지는 409
- 같은 `Idempotency-Key`로 결제 N건 동시 → 차감 1회, 이후 같은 키 재요청은 최초 응답 그대로
- 같은 예약에 본인 취소 N건 동시(더블 클릭) → 정확히 1건 성공, 환불 1회
- 본인 취소 ↔ 관리자 강제 취소 동시 → 정확히 1건 성공, 환불 1회
- 같은 예약에 도어 토큰 발급 N건 동시 → 활성 토큰 정확히 1개, 진 요청은 409(500 아님)
  - 연장 ↔ 본인 취소 동시 → 취소는 항상 성공, 최종 CANCELLED·슬롯 0개, 환불액 = 실제 결제 총액(연장이 먼저면 연장분 포함), 잔액 = 초기값 + 원 예약 총액
  - 시간대가 일부만 겹치는 HOLD 동시(부분 겹침·포함) → 정확히 1건 성공, 나머지 409(500 아님), 진 요청의 예약·슬롯 잔존 없음
  - 맞닿은 시간대 HOLD 동시(14:00~15:00, 15:00~16:00) → 둘 다 성공, 슬롯은 각자 2개

### 크레딧

- 잔액 부족 시 예약 확정 실패 + 슬롯 롤백
- 동시 결제 2건이 잔액을 초과 차감하지 않음
- `SUM(credit_transaction.amount) == member.balance`
- 50% 환불 시 `REFUND` + `PENALTY` 두 건 기록
- - 결제 실패(잔액 부족) 후 충전하고 같은 `Idempotency-Key`로 재시도 → 성공 (실패한 요청은 키를 소진하지 않음)
- 연장 성공 → 원 예약 단가 × 추가 슬롯 수만큼만 차감, `RESERVATION_CHARGE` 1건 / 연장 실패(슬롯 충돌·잔액 부족) → 차감·추가 슬롯 없음(롤백)
- 연장한 예약을 시작 1시간 전까지 취소 → 연장분 포함 전액 환불
- 강제 취소: `CONFIRMED`·`IN_USE`는 `total_amount` 전액 `REFUND`(위약금 없음, 시작 임박 포함), `HELD`는 환불 없음

### 상태 전이

- 허용되지 않는 전이 6종 각각 거절 (3-3)
- `HELD` 상태에서 토큰 발급 시도 → 거절
- 취소 후 재취소 → 409
- 시작 이후 취소 시도 → 거절 (체크인 여부 무관)
- 종료 상태 예약 강제 취소, 이미 강제 취소된 예약 재강제 취소 → 409, 환불 없음

### 시간 경계

체크인: `start-1s` / `start` / `start+15m` / `start+15m+1s`
재입장: `checked_in_at` / `end-1s` / `end`
HOLD: `hold_expires_at-1s` / `hold_expires_at`
HOLD 결제: `now == hold_expires_at`는 확정하지 않는다(`now < hold_expires_at`만 확정). 만료 쿼리의 `<=`와 경계가 맞물린다
연장 종료 시각: `closing` 정각(통과) / `closing+30m`(거절) / 30분 미정렬·초 단위 값(거절) / 자정 넘김(거절) / 기존 종료 시각과 같거나 이른 값(거절)

`Clock`을 주입해 대기 없이 검증한다.

### 인가

- 타인 예약 조회·취소·토큰 발급 거절 (일반 회원)
- **관리자도** 타인 예약 취소·토큰 발급 불가
- 일반 회원의 크레딧 지급 API 호출 거절
- 관리자의 자기 자신 크레딧 지급 거절
- 정지 계정의 기존 Access Token 요청 거절

### 가격

- 공간 가격 변경 후 기존 예약 금액 유지, 신규 예약에만 반영
- HOLD 중 가격 변경 → 결제 시 `space.version` 불일치로 거절
- 클라이언트가 조작한 금액을 보내도 서버 계산 금액으로 청구

## 13. 남은 논의 — 노쇼 환불률

현재 확정값은 **노쇼 0%**이며, 강사 피드백에 따라 재검토 중이다.

검토된 대안 중 **"노쇼 30% 환불"은 권장하지 않는다.** 시작 직전 취소가 50%인데 노쇼가 30%면 차이가 20%뿐이라, "취소 누르기 귀찮으면 그냥 안 가도 된다"가 성립한다. 취소를 유도하는 것이 정책 목적인데 그 유인이 약해진다.

대안으로 검토할 만한 것:

- **현금성 환급 0%를 유지하되, 다음 예약에만 쓸 수 있는 보상 크레딧 일부 지급.** 사용자 체감 손실은 줄이면서 취소 유인은 유지된다. 다만 크레딧에 종류가 생겨 복잡도가 올라가므로 채택은 신중히 한다.
- **약관 동의 시점과 예약 상세 화면에 환불 규정을 명시**하고, 취소 버튼에 현재 시점 기준 환불액을 표시한다(정책 변경 없이 컴플레인을 줄이는 방법).
