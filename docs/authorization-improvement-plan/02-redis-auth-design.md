# Redis를 활용한 인증·인가 설계 초안

> 상태: 팀 검토용 설계안 · 구현 완료 아님  
> 앞 문서: [도입 범위와 판단](01-redis-adoption-scope.md) · 다음 문서: [단계별 실행 계획](03-auth-improvement-roadmap.md)

## 1. 책임 구분

| 구성 요소 | 책임 |
| --- | --- |
| JWT | 발급자가 서명한 사용자 식별·권한·만료 정보 전달 |
| Spring Security | 토큰 검증, 인증 객체 구성, 경로·역할 인가 |
| Redis | 토큰·로그인 세션의 폐기 상태, 재발급 상태, 요청 횟수 제한 |
| 관계형 DB | 회원 및 외부 계정 연결의 원본, 영속 인증 버전 후보, 예약 소유권과 업무 데이터 |
| 도메인 서비스 | 예약 소유권·회원 상태·예약 상태 등 업무별 접근 정책 |

인증은 “누구인가”, 인가는 “이 작업을 해도 되는가”의 판단이다. Redis를 추가해도 예약 소유권 확인 책임이 사라지지는 않는다.

## 2. 토큰 단위 Access Token 폐기

### 발급과 요청 검사

1. Access Token마다 고유한 `jti`를 발급한다.
2. 서명·만료·허용 알고리즘 및 필요한 claim을 검증한다.
3. 검증된 jti의 폐기 기록을 Redis에서 조회한다.
4. 폐기됐다면 거절하고, 정상이라면 기존 SecurityContext를 구성한다.

키 초안은 다음과 같다. 환경·서비스 접두사는 실제 설정에서 추가한다.

| 키 | 값 | 수명 |
| --- | --- | --- |
| `auth:revoked:access:{jti}` | 폐기 표시 | 토큰의 남은 유효기간 + 검증에서 허용하는 시계 오차 |

JWT 원문을 Redis 키나 로그에 남기지 않는다. 만료 토큰은 먼저 거절하므로 0 이하 TTL로 키를 만들지 않는다.

### 로그아웃 경로 변경

현재 `/logout`은 Refresh 쿠키를 받고 Access Token 필터를 건너뛴다. 따라서 필터에 폐기 조회만 추가해도 로그아웃 시 Access Token을 폐기할 수 있는 것은 아니다.

- 로그아웃 시 전달받은 Access Token을 검증해 폐기할 jti를 구한다.
- Refresh Token과 Access Token이 같은 회원·로그인 세션에 속하는지 검증한다.
- Refresh 폐기, Access 폐기 기록, 쿠키 삭제의 성공 기준을 정한다.
- Access가 만료됐더라도 유효한 Refresh 세션의 종료는 가능하도록 API 정책을 구분한다.
- Redis 반영 실패 시 서버 폐기가 완료됐다고 응답하지 않는다. 클라이언트 쿠키 삭제와 서버 폐기 완료를 구분한다.

### 토큰 하나와 기기 로그아웃의 차이

jti 하나를 폐기해도 같은 로그인에서 이전에 발급한 다른 Access Token까지 모두 폐기되지는 않는다. 따라서 **1단계 jti 폐기의 완료 범위는 전달된 토큰 하나의 차단**이다.

“현재 기기 로그아웃”을 보장하려면 Access Token에 로그인 세션 식별자 `sid`를 포함하고 요청마다 해당 세션의 활성 상태도 확인하는 방안을 권장 후보로 둔다. 여기서 세션은 Redis의 논리적 로그인 기록이며 반드시 HTTP 세션을 뜻하지는 않는다.

이 구조에서는 sid 폐기가 해당 로그인에서 발급한 토큰들을 함께 차단한다. 토큰 단위 폐기가 별도로 필요하지 않다면 jti 폐기 목록의 장기 유지 필요성도 재평가한다. 여러 방식을 무조건 중첩하지 않는다.

## 3. 회원 전체 차단과 권한 변경

제안 후보는 DB에 영속 `authVersion`을 두고 Redis에 현재 상태·버전을 반영하는 방식이다. JWT에도 발급 시의 버전을 넣는다.

- 전체 로그아웃, 정지, 탈퇴, 비밀번호 변경·재설정, 역할 변경 시 필요한 범위의 버전을 갱신한다.
- JWT 버전과 현재 버전이 다르면 거절한다.
- 정지 해제 시 이전 버전으로 되돌리지 않는다.
- 새 로그인·재발급도 활성 회원 상태와 유효 세션을 확인해야 한다.

`auth:member:{memberId}`에 상태·버전을 저장하는 방안은 제안이며 확정 스키마가 아니다. 이 정보를 캐시처럼 임의 만료시켜 누락을 “정상”으로 해석하면 안 된다. 버전만 비교해서도 정지 상태 검사를 생략하지 않도록 설계한다.

### DB와 Redis 동기화

두 저장소는 자동으로 하나의 트랜잭션이 되지 않는다. DB 변경 후 Redis 반영이 실패하면 기존 토큰이 일시적으로 통과할 수 있는 구간이 생긴다.

팀은 다음 두 항목을 분리해서 정의해야 한다.

1. 정지·폐기 API는 Redis 반영까지 확인한 뒤에만 “차단 완료”로 응답한다.
2. 실패한 변경은 영속 재시도 기록(예: outbox)이나 보정 작업으로 복구한다. 재시도만으로 실패 구간의 즉시 차단이 보장되는 것은 아니다.

엄격한 차단 시간이 필요하면 회원·세션 차단을 먼저 설치하는 절차와 보상, 반영 대기 상태, 해당 구간의 요청 차단 정책까지 추가로 정한다. 전역 fail-closed는 Redis 접속 오류에 대응하지만, 정상 접속 가능한 Redis의 오래된 값까지 스스로 감지하지는 못한다.

차단 보장은 반영 후 시작하는 인증 검사에 대한 것이다. 이미 인증을 통과해 실행 중인 결제를 소급 취소하는 기능이 아니다.

## 4. Refresh Token Rotation과 재사용 탐지

현재 구현은 DB에서 토큰 해시를 검증하고 Access Token만 새로 발급한다. 변경 후에는 재발급 성공마다 Refresh Token도 교체한다.

### 논리 데이터 후보

| 데이터 | 용도 |
| --- | --- |
| `sid`, `memberId` | 로그인 세션과 회원 연결 |
| `familyId` | 같은 로그인에서 회전한 토큰 계열 연결 |
| 현재 Refresh 토큰 해시 | 현재 유효한 토큰 검증 |
| 토큰 상태 및 이전 사용 기록 | ACTIVE / USED / REVOKED, 사용한 토큰의 재사용 식별 |
| 생성·만료·사용 시각 | 절대 만료, 유휴 만료, 감사와 복구 |

원문 대신 안전한 해시와 필요한 메타데이터를 저장한다. 사용한 토큰을 곧바로 완전히 삭제하면 “알 수 없는 토큰”과 “이미 쓴 토큰”을 구분하기 어려우므로, 계열의 허용 수명에 맞춘 제한된 사용 기록을 둔다.

### 교체 절차

1. 회원 상태와 세션·토큰의 유효성을 확인한다.
2. 기존 토큰의 ACTIVE 상태를 확인하고 USED로 전환한다.
3. 새 토큰 해시를 등록하고 현재 토큰 포인터를 교체한다.
4. 새 Access Token과 Refresh 쿠키를 응답한다.

Redis 내 확인·교체는 Lua 또는 동등한 원자적 방식으로 묶는다. DB 회원 상태 확인과 Redis 변경은 별도 경계이므로 정지·탈퇴와 재발급의 경합도 테스트한다. Redis Cluster 도입 시 여러 키를 한 스크립트에서 다루기 위한 동일 슬롯 배치도 별도 설계한다.

### 재사용과 정상 중복 요청

- 기본 제안: 같은 Refresh Token의 교체는 한 번만 성공한다.
- 이미 사용한 토큰의 재사용이 확인되면 해당 family 또는 sid를 폐기하는 정책을 검토한다.
- 가족 토큰 폐기는 Access Token까지 자동 폐기하지 않는다. 즉시 차단하려면 sid 검사 또는 그에 준하는 연계가 필요하다.
- 공격과 다중 탭의 정상 동시 재발급을 완벽히 구분할 수 없으므로 프론트의 재발급 요청 합치기와 서버 정책을 함께 결정한다.
- 교체 성공 후 응답 유실 시 재로그인을 요구할지, 제한된 안전한 재시도 체계를 둘지 합의한다. 임의로 이전 토큰을 다시 활성화하지 않는다.
- 반복 회전으로 로그인 수명이 무제한 늘어나지 않도록 절대 만료와 유휴 만료 정책을 구분한다.

### 기존 DB 기록에서 전환

첫 도입은 기존 Refresh DB 저장을 유지한 채 Access 폐기부터 구현할 수 있다. Redis로 옮기는 시점에는 하나의 검증 원본을 정한다. DB와 Redis 중 아무 곳에서나 유효하면 통과시키는 fallback은 폐기 토큰을 되살릴 수 있다.

기간이 짧은 프로젝트에서는 전환 시 기존 Refresh를 일괄 무효화하고 재로그인을 요구하는 방안이 단순하다. 무중단 이전이 필요하면 토큰 버전별 검증 경로와 전환 종료 시점을 별도로 설계한다.

## 5. 로그인·재발급 요청 제한

우선 대상은 로그인과 재발급이다. 모든 업무 API에 동일 제한을 걸지 않는다.

| 항목 | 제안 |
| --- | --- |
| 알고리즘 | Sorted Set 기반 Sliding Window Log |
| 저장 | score=서버 기준 요청 시각, member=충돌하지 않는 요청 식별자 |
| 원자성 | 오래된 기록 제거·개수 확인·허용 기록·TTL 설정을 하나의 Lua로 처리 |
| 제한 기준 | IP별 제한과 정규화한 계정 식별자별 제한의 조합 검토 |
| 응답 | HTTP 429, 다음 허용 시점에 맞는 Retry-After |
| 수치 | 팀 합의 및 실험 후 확정. 임의 예시를 운영 정책으로 사용하지 않음 |

계정 ID를 키에 넣을 때 개인정보 노출과 열거 위험을 검토하고 필요 시 키용 HMAC 등을 사용한다. 원본 토큰은 키에 쓰지 않는다. 프록시 헤더는 신뢰하는 프록시에서 전달한 값만 사용한다.

IP만 제한하면 공유망 사용자를 함께 막을 수 있고, 계정만 제한하면 공격자가 특정 계정을 지속적으로 막을 수 있다. 임계값·짧은 지연·복구 방식의 균형을 정한다. Redis 요청 제한을 우회하는 인스턴스별 메모리 대체 경로는 전역 한도를 보장하지 못한다.

요청 기록과 키 수는 제한하고 만료시킨다. 시간은 서버 간 차이를 고려해 일관된 기준을 사용한다. 인증 API 제한은 남용 완화 기능이며 대규모 DDoS 방어 전체를 대체하지 않는다.

## 6. 장애·유실 정책

권장 초안은 **인증 판정이 불가능하면 보호 요청을 통과시키지 않는 것**이다. 토큰 무효와 인프라 장애는 응답을 구분한다.

| 상황 | 기본 제안 |
| --- | --- |
| 서명 오류·만료·폐기 토큰 | 401 |
| 정상 인증이지만 역할·소유권 부족 | 403 또는 합의한 리소스 은닉용 404 |
| 요청 한도 초과 | 429 |
| Redis 장애로 인증 판정 불가 | 503 등 일시 장애 응답, 자동 허용 금지 |
| 필수 활성 세션·회원 보안 정보 누락 | 거절 또는 명시적 복구 경로. 일반 요청에서 무조건 DB 재조회하지 않음 |
| 공개 공간 조회 | 인증을 필요로 하지 않는 경로의 지속 제공 가능성을 별도 검증 |

**denylist만 사용하는 경우 키 부재는 정상 상태와 기록 유실을 구분하지 못한다.** Redis가 재시작되어 빈 저장소가 됐는데 접속이 성공한다고 이전 토큰을 통과시키면 차단이 풀린다.

지속성·복제·백업 정책과 함께, 복구 완료 전 인증 트래픽 차단 또는 보안 세대 변경으로 기존 토큰 전체 무효화하는 절차를 정한다. 활성 sid를 반드시 조회하는 구조는 기록 유실 시 재로그인을 요구하도록 설계할 수 있다. 어느 경우에도 데이터 유실을 단순한 캐시 미스로 처리하지 않는다.

인증 상태는 일반 조회 캐시와 퇴출·수명 정책을 구분한다. 보안 기록이 메모리 부족으로 제거되지 않도록 용량과 정책을 정하고, 기록 쓰기 실패도 오류로 처리한다. 네트워크 접근 제한·최소 권한·비밀값 관리도 배포 범위에 포함한다.

## 7. 필수 검증

- 로그아웃 전 성공하던 토큰이 폐기 반영 후 거절된다.
- 단일 jti, 현재 sid, 회원 전체의 폐기 범위가 정책과 일치한다.
- 정지 해제 후 옛 토큰이 다시 유효해지지 않는다.
- 같은 Refresh Token으로 동시 교체 시 의도한 한 번만 성공한다.
- 이전 토큰 재사용, 응답 유실, 다중 탭의 결과가 합의한 정책과 일치한다.
- Redis 중단·재시작·키 유실·DB 동기화 실패 때 우회 인증이 발생하지 않는다.
- 요청 제한의 동시성·창 경계·429와 재허용을 확인한다.
- p50/p95/p99, 성공 처리량, 오류율, Redis 지연·메모리를 기록한다.
