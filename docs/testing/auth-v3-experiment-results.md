# V3 인증 저장소 이전 실험 결과

> 상태(2026-10-21 최종 판단): **배포 환경은 V2(DB 세션 검증)를 유지한다.** V3는 세션 검증과 RT 처리를 Redis로 이전한 실험 구현으로 보존하고, dev 병합과 운영 도입은 보류한다. 로그인 요청 제한과 이메일 인증 임시 상태는 DB 구현을 유지한다.
>
> 이 문서는 V3 실험의 과정, 검증, 성능 결과와 판단 근거를 모은 중심 문서다. 현재 운영 인증 정책([인증 정책](../decisions/authentication-policy.md)), ERD([ERD](../architecture/erd.md)), 배포 절차는 V2 기준이며 이 문서가 바꾸지 않는다. 설계 경과는 [V3 설계](../plans/auth/v3-redis-design.md), 단계별 실행 기록은 [테스트 결과 §0-V3](test-results.md)에 있다.
>
> 기준: 문서는 `origin/dev` `01508ddb3890a91d3be83451134ec50cba2516da`에서 작성했다. V3 코드는 로컬 실험 브랜치 `auth/improvement/v3`(HEAD `d9b6139d731009e5963eaf95349f4d3e62f0f34c`)에 있으며 2026-10-21 기준 원격에 Push되지 않았고 dev에 병합되지 않았다.

## 1. 판단의 흐름

1. **V2의 출발점.** 로그아웃과 계정 상태 변경(정지, 탈퇴, 비밀번호 재설정)을 이미 발급된 토큰에 즉시 반영하기 위해, V2는 보호 요청마다 DB에서 세션과 회원 상태를 확인한다. V2는 PR #350으로 dev에 병합됐다(`4051bb3`, 2026-10-19).
2. **V3의 목적.** 이 인증용 DB 접근 비용을 줄이기 위해 보호 API의 세션 검증을 Redis로 옮겼다. RT 상태, Rotation, 재사용 탐지도 Redis로 옮겼다. Redis로 무상태성을 되돌리는 것이 목적은 아니었다.
3. **구현 중 보완.** DB와 Redis 사이의 실패 처리, 계정 변경과 refresh의 경합, 자동 정지 때의 Redis 세션 삭제 재시도를 보완했다(§3).
4. **회귀 검증.** 전체 백엔드 회귀 1,065개가 통과했다(§4).
5. **성능 측정.** 보호 API와 RT Rotation을 같은 설정의 k6 시나리오로 V2, V3 각각 3회씩 측정했다(§5).
6. **관측 결과.** 보호 API 전체 응답 시간에서는 일관된 개선을 확인하지 못했다. Rotation에서는 p50 감소가 관찰됐다. p95 대표값(반복별 중앙값)도 낮았지만 반복 범위가 겹쳤다.
7. **측정하지 못한 것.** 세션 검증 단계만의 지연과 DB 자원 감소는 따로 측정하지 않았다. 실행 순서와 로컬 환경의 영향도 분리하지 못했다(§6).
8. **결론.** 지금까지 확인한 이득에 비해 Redis 운영과 장애 복구의 복잡성(§7)이 크다고 보고, V2 운영을 유지하고 V3 도입을 보류한다.

## 2. 범위를 좁힌 경과

초기 계획(2026-10-15)은 세션, RT, 요청 제한, 이메일 인증 임시 상태를 모두 Redis로 옮기는 것이었다. 구현을 진행하며 두 번 좁혔다.

- **2026-10-20**: 이메일 인증 임시 상태(Guard, Challenge, Grant)는 DB에 둔다. 인증 최종 잠금에 따른 자동 정지가 회원의 전체 세션을 끊는 V2 연결은 V3 세션 저장소에서도 유지한다.
- **2026-10-21**: 로그인 요청 제한은 Redis로 옮기지 않고 V2의 DB 구현(`login_attempt_bucket`, 이메일별 UTC 15분 10회)을 유지한다. 이메일 소문자 통일 등 식별 정책도 바꾸지 않는다. 현재 확인된 병목 근거와 추가 변경 비용을 고려해 핵심 인증 경로에 집중하기 위한 결정이며, Redis로 정확한 제한을 구현할 수 없어서가 아니다. 같은 날 V2/V3 비교 대상도 보호 API와 RT Rotation 두 경로로 정했다.

최종 실험 범위는 (1) 일반 보호 API의 로그인 세션 검증, (2) RT 상태 저장, Rotation, 재사용 탐지다.

## 3. 구현 요약

- **보호 요청**: JWT 서명과 만료를 검증한 뒤 Redis Lua 한 번으로 세션(회원 ID, generation, 절대 만료)을 판정한다. 인증용 DB 조회는 없다. `/api/v1/members/me` 같은 업무 데이터 조회는 계속 DB에서 처리한다.
- **refresh**: RT 이력 대조와 회전은 Redis Lua로 처리하지만, 회원 상태와 세션 소유를 확인하는 DB 회원, 세션 잠금 조회는 남는다. 따라서 Rotation은 DB 비용이 없어진 경로가 아니다.
- **계정 변경 처리 순서**는 경로마다 다르다.
  - 관리자 정지, 탈퇴, 비밀번호 재설정: 회원 행을 잠근 뒤 Redis generation을 먼저 교체하고 DB 세션을 폐기한다. Redis 교체가 실패하면 503으로 응답하고 DB 변경을 롤백한다. Redis 교체 뒤 DB가 실패하면 세션은 무효인 채로 남는다.
  - 인증 최종 잠금에 따른 자동 정지: 인증 확인 트랜잭션이 Guard 최종 잠금을 먼저 커밋한다. 이어지는 정지 트랜잭션이 Guard, 회원 순서로 잠그고(관리자 복구와 같은 순서), DB 세션 폐기, 회원 정지, 감사 로그와 함께 활성 세션별 Redis 삭제 작업(V27 `auth_session_revocation_retry`)을 저장해 커밋한다. 커밋 뒤 해당 세션 키를 즉시 삭제하고, 실패한 작업은 재시도 스케줄러가 다시 처리한다. generation은 바꾸지 않는다.
- **구현 중 보완한 결함**(리뷰 기준): Redis 장애 때 인증 최종 잠금까지 롤백되던 문제, namespace 기본값 부재, 비활성 회원 출입 거절 감사 로그 누락, 자동 정지와 관리자 복구의 경합.
- **알려진 한계**: 보호 요청이 DB 회원 상태를 읽지 않으므로, 서비스를 거치지 않고 DB의 `member.status`만 직접 바꾸면 기존 AT는 차단되지 않는다(refresh와 로그인은 거절된다).
- 관련 로컬 커밋: 세션 이전 `cab2ad1`, RT 이전 `229517c`, 회귀 테스트 보완 `27262ab`. V27 재시도 테이블은 실험 브랜치의 스키마이며 dev나 운영에 적용된 마이그레이션이 아니다.

## 5. 성능 비교

### 5.1 측정 설계 경과

- V2 k6 탐색은 보호 API, RT 회전, 로그인 제한 429 세 경로를 10, 50, 100 RPS로 실행했다고 보고됐다(리뷰어가 결과 파일을 직접 확인하지 않음). 2026-10-21에 로그인 요청 제한을 범위에서 빼면서 비교 대상을 보호 API와 RT Rotation으로 좁혔다. 429 탐색은 V2 기록으로만 남는다.
- 측정 도구(k6 스크립트, 실행기, 격리 DB와 Redis compose, 픽스처 도구, `perf` 프로필)는 V3 작업 트리에 미커밋으로만 있고 저장소에 포함하지 않았다. 고정 도착률(`constant-arrival-rate`)로 요청률을 고정하고, 준비, 워밍업, 측정 단계를 태그로 나눈다. 측정 구간에 시작해 구간 종료 전에 완료된 요청만 집계한다.

### 5.2 조건

- protect(`GET /api/v1/members/me`)와 rotation(`POST /api/v1/auth/refresh`), 버전과 시나리오별 3회.
- 100 RPS, pre-allocated VU와 max VU 각 100, 워밍업 10초, 측정 60초, 실행마다 전용 계정 100개. 정상 응답은 모두 200이었다.
- 양쪽 공통 환경(아티팩트 메타데이터): JDK 21.0.12.1, MySQL 8.4.11, `utf8mb4_unicode_ci`, HikariCP 최대 10, k6 2.3.0, Darwin arm64. 앱 인스턴스와 로그 수준은 `not-provided`로 기록됐다. summary의 dropped iterations는 null이므로 0으로 단정하지 않는다(원시 결과에는 드롭 표본이 없다).
- 코드: V2는 HEAD `4f6aacda3c03b9d579bdef05814622e0eb12cac3`, V3는 HEAD `d9b6139d731009e5963eaf95349f4d3e62f0f34c`. k6 요청, 집계, perf 실행 파일의 해시는 양쪽이 같다. 두 쪽 모두 perf용 예약 완료 스케줄러 조건 변경이 작업 트리에 있었고, 이 설정은 기준 커밋만으로 재현되지 않는다. `source-state.json`은 k6 시작 시점의 작업 트리 해시이며, 별도로 기동한 앱이 그 소스로 빌드됐다는 증명은 아니다.
- V2 측정 HEAD `4f6aacd`는 dev 병합 커밋 `4051bb3`과 `backend/src/main` 기준 파일 4개가 다르다(`SecurityConfig`, `MemberResponse`, `StatsController`, `application.yml`). V3 HEAD에는 인증 외 dev 변경(관리자 회원 상세, 공통 예외 응답, 비활성 회원 출입 로그 등)도 들어 있어, 이 비교는 인증 변경만의 차이가 아니다.

## 6. 해석의 한계

- **구현 사실**: 일반 보호 요청의 세션 인증 판정을 DB에서 Redis로 옮겼다. 업무 데이터 DB 조회와 refresh의 DB 잠금 조회는 남았다.
- **관측 결과**: API 전체 응답 시간 기준으로 protect에서는 일관된 개선을 확인하지 못했고, rotation에서는 p50 감소가 관찰됐다(p95는 범위 겹침).
- **측정하지 않은 것**: 세션 검증 단계만의 지연, DB CPU와 커넥션 대기 같은 DB 자원 변화, Redis 호출 지연. 따라서 관측된 차이의 원인이나 세션 검증 자체의 개선 폭을 말할 수 없다.
- **실행 순서**: V2 6회(10:56~11:12 KST)를 모두 마친 뒤 V3 7회(11:15~11:32)를 실행했다. p95 약 20~25 ms 수준은 V2 protect 2회차와 V2 rotation 2회차 중반 이후에도 같은 코드로 나타났고, V3 실행은 모두 이 수준이었다. 버전 효과와 시간대, 환경 효과를 분리하지 못했다.
- **자원 공유**: 앱, MySQL, Redis, k6가 한 대의 로컬 Mac에서 함께 실행됐고 DB와 Redis는 Docker 포트 포워딩을 거친다. 호스트 부하는 기록하지 않았다.
- **데이터 상태**: V2 DB는 이전 탐색 데이터가 남은 볼륨, V3 DB는 새로 준비한 볼륨이다. 두 볼륨의 데이터 규모는 기록되지 않았다.
- **메타데이터**: 앱 기동 시각과 재기동 여부, Redis 버전, 앱 로그는 보존되지 않았다.
- **처리량**: 고정 100 RPS에서 사용된 VU는 최대 6개라 포화와 거리가 멀다. 최대 처리량은 판단할 수 없다.

따라서 "Redis 때문에 느려졌다", "Redis가 효과가 없다", "DB 부하가 줄었다", "규모가 작아서 효과가 없다"는 결론을 내리지 않는다. 결과는 이 조건에서의 관측치로만 다룬다.

## 7. 운영 판단과 V3의 운영 부담

V2 유지를 결정할 때 함께 고려한 V3 운영 부담이다. 실제 운영 장애와 복구 검증은 수행하지 않았다.

- Redis가 응답하지 않으면 보호 API가 503(`AUTHENTICATION_SERVICE_UNAVAILABLE`)으로 거절된다. 인증 가용성이 Redis에 의존한다.
- 세션 키가 없으면 거절하므로, Redis 데이터 유실이나 초기화 시 모든 기존 로그인은 재로그인이 필요하다. 과거 스냅샷을 복원하면 이미 소비된 RT가 다시 유효하게 보일 수 있어, 트래픽을 멈추고 새 namespace로 전환하는 절차가 필요하다.
- 자동 정지 후 Redis 세션 삭제가 실패하면, 삭제될 때까지 해당 세션의 기존 AT가 보호 요청에 쓰일 수 있다. 재시도 스케줄러 주기(기본 5초)는 최대 반영 지연의 보장이 아니며, Redis 장애가 이어지면 지연도 이어진다.
- 도입하려면 운영 Redis, `AUTH_REDIS_NAMESPACE`, V27 적용이 필요하고, 전환 시 기존 DB 세션과 RT에는 Redis 상태가 없어 전원 재로그인이 필요하다. V3와 V2 서버를 섞어 운영하는 것은 지원하지 않는다.
- 엄격한 RT 재사용 탐지에서 응답 유실 뒤 구 RT로 재시도하면 세션이 폐기되는 것은 V2와 같은 정책이며 V3 고유의 부담은 아니다.

다시 검토한다면 V2와 V3를 번갈아 실행하는 재측정, 실행 전후 DB와 Redis 서버 지표 수집, 실행 메타데이터 보강이 원인을 가르는 데 먼저 필요하다.
