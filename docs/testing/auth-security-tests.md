## 1. 레드 테스트를 유지하는 이유

이 테스트들은 V2에서 요구하는 동작을 먼저 단언하여 현재 V1의 한계를 재현한다. V1에서 실패하고 V2와 V3에서 통과하는 동일 시나리오를 발표와 회귀 검증에 활용한다.

작성 시점(PR head)의 선택은 기본 테스트 실행에 포함하는 것이었다(현재 설정은 위 구분표 참조). V1의 전체 CI 실패를 숨기지 않고 의도적 실패 목록과 일반 회귀 실패를 구분한다. 테스트 분리나 성공 처리 우회를 이 문서의 전제로 삼지 않는다.

“실패가 의도적”이라는 것은 예외나 환경 오류가 발생해도 된다는 의미가 아니다. 준비 데이터 생성과 요청이 정상적으로 수행되어 목표 보안 단언에서 실패해야 한다.

## 3. 11개 테스트의 의미

| 번호 | 테스트 | 현재 V1에서 드러나는 동작 | V2 통과 기준 |
| --- | --- | --- | --- |
| 1 | 로그아웃하면 기존 Access Token은 즉시 폐기된다 | 로그아웃 후 기존 AT가 보호 API에서 200 | 기존 AT가 401 |
| 2 | 비밀번호 재설정이 성공하면 기존 Access Token은 즉시 폐기된다 | 비밀번호 변경 후에도 기존 AT 사용 가능 | 기존 AT가 401 |
| 3 | Refresh Token은 재사용할 수 없다 | 같은 RT로 갱신을 반복할 수 있음 | 사용한 RT의 다음 제출은 401 |
| 4 | 회원이 정지되면 기존 Access Token도 즉시 폐기된다 | 상태 변경이 기존 AT 검증에 반영되지 않음 | 정지 후 기존 AT가 401 |
| 5 | 반복 로그인 실패는 요청 제한 응답을 반환한다 | 반복 실패에도 요청 제한 없이 인증 실패 응답 | 테스트 기준 초과 요청에 429 |
| 6 | 정상 사용자는 RT Rotation 후 새 RT로 계속 갱신할 수 있다 | refresh가 새 RT 쿠키를 반환하지 않음 | RT1 → RT2 → RT3 갱신 성공, 새 RT 발급 |
| 7 | 비밀번호 재설정 후 기존 Refresh Token은 폐기된다 | 이전 RT로 새 AT 발급 가능 | 이전 RT의 refresh가 401 |
| 8 | 비밀번호 재설정은 여러 로그인 세션의 AT와 RT를 모두 폐기한다 | 여러 로그인에서 발급한 기존 인증이 유지됨 | 두 로그인 각각의 AT·RT 모두 401 |
| 9 | 회원 정지 후 복구해도 정지 전 AT와 RT는 다시 살아나지 않는다 | 복구 후 이전 인증 수단 사용 가능 | 복구 뒤에도 기존 AT·RT 모두 401 |
| 10 | 회원탈퇴 후 기존 Access Token은 보호 API에서 거부된다 | 탈퇴 후 기존 AT로 보호 API 접근 가능 | 기존 AT가 401 |
| 11 | 동일 Refresh Token 동시 사용은 정확히 하나만 성공한다 | 동시 요청 둘 다 성공 | 정확히 하나 200, 다른 하나 401 |

### 3.1 로그아웃과 비밀번호 변경의 차이 — 1·2·7·8

로그아웃은 어떤 세션을 종료하는지가 핵심이다. 비밀번호 재설정은 계정 복구이므로 모든 기존 세션을 종료하는 기준이다. 단일 AT 거부 테스트만으로 모든 기기의 RT까지 폐기됐다고 결론 내릴 수 없다.

8번은 두 번 로그인하여 별도로 발급한 RT를 사용한다. 동일 시각의 AT 문자열이 같을 수 있으므로 토큰 문자열의 차이만으로 세션 분리 여부를 판단하지 않는다. V2에서는 실제 sid 연결도 검증하는 것이 좋다.

### 3.2 Rotation과 재사용 대응 — 3·6·11

3번은 사용한 토큰을 다시 수락하지 않는지, 6번은 정상적인 다음 토큰으로 계속 사용할 수 있는지, 11번은 동시에 제출되어도 한 번만 교체되는지 확인한다. 서로 대체할 수 없는 검증이다.

3번이 통과해도 RT1 재사용 탐지 후 RT2와 관련 AT까지 폐기되는 정책은 아직 증명되지 않는다. 재사용 대응 범위가 정해지면 별도 시나리오로 확인해야 한다.

11번의 한 번 성공은 HTTP 갱신 성공 횟수다. 이후 패배 요청을 재사용 공격으로 취급하여 전체 family를 폐기하는 정책을 선택하면, 먼저 성공한 RT도 이후 무효화될 수 있다. 이 결과는 정상 사용자 다중 탭·응답 유실 정책과 함께 명시해야 한다.

### 3.3 회원 상태와 폐기의 지속성 — 4·9·10

4번은 회원 상태 변경이 보호 API에 반영되는지 확인하며, 준비 과정에서 DB 상태를 직접 변경한다. 관리자 정지 API의 모든 부수 효과까지 검증하는 테스트는 아니다.

9번은 실제 관리자 정지·복구 API를 거친 뒤 이전 인증을 확인한다. 상태를 ACTIVE로 되돌려도 폐기된 세션은 되살아나지 않아야 한다.

10번은 실제 탈퇴 요청 이후 기존 AT 거부를 확인한다. 탈퇴 후 RT, 데이터 보존, 예약·환불 정책 등 전체 탈퇴 요구사항을 이 테스트 하나로 검증했다고 해석하지 않는다.

### 3.4 요청 제한의 검증 범위 — 5

현재 시나리오는 로그인 실패 5회 이후 다음 요청에 429를 기대한다. 이메일별 제한과 IP별 제한이 각각 적용되는지, 제한 기간이 지나면 재허용되는지, 인증번호·refresh에도 제한이 있는지는 증명하지 않는다.

해당 수치는 현재 테스트의 기대값이다. 최종 정책 확정 시 테스트 설정과 정책표를 일치시키고 변경 이유를 남긴다.

## 4. 동시성 테스트 구성

동시 요청의 준비 데이터는 TransactionTemplate로 커밋하여 작업 스레드에서 조회할 수 있게 한다. 클래스 전체의 테스트 트랜잭션 안에만 데이터를 두면 다른 스레드가 볼 수 없어, 보안 경합이 아닌 데이터 준비 실패를 테스트할 수 있다.

두 작업 스레드는 준비 완료 신호를 보낸 뒤 시작 신호를 함께 기다린다. 각각 동일 RT를 제출하고 응답을 수집한다. 타임아웃과 작업 스레드 예외를 확인하고 executor를 종료한다.

검증할 것은 성공 개수뿐 아니라 나머지 응답이 의도한 거부인지 여부다. 한 요청이 500으로 실패해도 성공 개수는 하나가 될 수 있으므로 200 하나와 401 하나를 함께 단언한다.

시작 신호를 맞추는 방식만으로 모든 실행에서 같은 DB 명령이 정확히 겹친다고 보장되지는 않는다. V2 구현 후 트랜잭션 경계와 상태 변경을 검토하고, 필요 시 경합 반복 검증을 수행한다. 환경에 따른 우연한 실패를 보안 보장으로 사용하지 않는다.

## 5. 정상 기능 회귀 테스트

PasswordResetIntegrationTest의 “재설정 후 새 비밀번호 로그인”은 V1에서도 통과해야 한다. 기존 기능을 유지한다는 근거이므로 레드 테스트에서 분리했다. 현재 검토 결과는 해당 클래스 5개 통과다.

EmailSignupIntegrationTest는 입력 실패 후 grant 재시도와 최종 소비를 확인하는 회귀 근거다. 최신 CI의 실패 11개에 포함되지 않는다.

VerificationMemberStatusIntegrationTest는 1·2차 ACTIVE 유지와 최종 정지를 각각 검증한다. 이것은 미래 V2 목표가 아니라 V1 정책 결함의 재발 방지 테스트다.

## 6. 실행 방법

프로젝트 루트에서 backend로 이동한 뒤 Java 21 및 Testcontainers를 실행할 Docker 환경을 준비한다.

```bash
cd backend
./gradlew test --tests "com.ovengers.slotkey.auth.controller.V2SecurityRedTest"
./gradlew test --tests "com.ovengers.slotkey.auth.service.EmailSignupIntegrationTest"
./gradlew test --tests "com.ovengers.slotkey.auth.service.PasswordResetIntegrationTest"
./gradlew test --tests "com.ovengers.slotkey.auth.service.VerificationMemberStatusIntegrationTest"
./gradlew test
```

현재 소스에서는 `V2SecurityRedTest`가 `@Disabled`이므로 첫 명령도 11개를 건너뜀으로 보고한다. V1 실패 재현이나 V2 통과 확인에는 `@Disabled` 해제가 필요하다.

위 명령은 각각 선택 실행 또는 전체 실행에 사용한다. 같은 실행에서 모두 반복할 필요는 없다. 실행 결과가 캐시·UP-TO-DATE라면 새 실행과 구분해 기록한다.

HTML 보고서는 backend/build/reports/tests/test/index.html, XML 결과는 backend/build/test-results/test/에서 확인한다.
